## 决策-010 短号中心/流转市场 Tab 归属

> **日期**：2026-07-25
> **状态**：已确认
> **关联**：Node产品文档-v1.0、Node产品说明（宣讲版）、流转市场方案、短号中心方案

### 背景
短号中心与流转市场的 Tab 归属在宣讲版（Tab 3 交易/商城）和技术版 v1.0（Tab 5 身份）之间存在矛盾，引发全库一致性问题。

### 结论
**短号中心与流转市场统一归属 Tab 3 交易/商城**。

### 理由
1. 短号中心负责短号的发行（购买/领取）与持有管理，属交易语义
2. 流转市场负责短号与商品码的二手处置，属交易/处置语义
3. 与商城一级发行同属交易范畴，应同 Tab 归属
4. Tab 5 身份聚焦身份权益、安全保障与凭证通行，不承担资产处置职能

### 影响范围
- 技术版 v1.0：7.6/7.7 节、4 大快捷入口归属、2.1 节架构图等
- 流转市场方案：0.2/0.3 节、2.1 节决策矩阵、2.2 节架构图等
- 短号中心方案：入口位置、模块归属描述
- 宣讲版：已对齐 Tab 3，无需修改

### 历史演变
- v1.0（2026-07-09）PRD 总纲：2 Tab 旧架构（冷钱包舱 + 服务舱）
- v1.0（2026-07-25）Node产品文档-v1.0：5 Tab 架构，短号中心/流转市场归 Tab 5 身份

- **日期**: 2026-07-16
- **背景**: v2.1 代销为"单件代销、无库存、按成交结算",但实际分销场景中代销应按一定库存数量批量进行,由上级设定方案规则(起代量/梯度供货价/库存上限/补货阈值)。原设计缺少库存管理维度,代理无法管控代销库存余量、补货时机、销量收益。同时用户明确"商品详情不需要收藏和客服能力",需精简底部操作栏
- **可选项**:
  - A. 保持单件代销无库存——简单但脱离实际分销场景,代理无法管控库存
  - B. 代销改为按库存数量批量,上级设定方案规则——符合主流分销(云集/贝店),代理可管控库存与补货
  - C. 代销完全等同囤货(实物库存)——与代销"不收货"定位冲突
- **决策**: 采用方案 B。代销改为按库存数量批量,上级设定方案规则,虚拟库存管理
  1. **代销批量方案(上级设定)**:每个可代销商品由 L1 设定起代量/单次上限/梯度供货价/补货阈值
  2. **梯度供货价**:按数量分档(如 10件139U/50件129U/100件119U),数量越多单价越低,激励批量
  3. **代销申请流程(详情页入口)**:详情页"申请代销"按钮 → 弹出批量申请弹窗 → 展示方案规则+梯度供货价+数量选择器+实时费用明细 → 确认申请提交 L1 审核
  4. **虚拟库存管理**:代销库存进入代理商品池(代理不收货,但管理库存数量),代理中心展示剩余/已售/已赚差价/补货阈值
  5. **补货机制**:剩余库存低于补货阈值时标红"需补货",代理可再次申请代销追加库存
  6. **梯度供货价锁定**:申请代销时的梯度供货价锁定,不随后续 L1 调价变动
  7. **详情页底部精简**:去掉收藏和客服按钮,代销商品只保留"申请代销+立即购买",自主商品只保留"立即购买"
  8. **代销收益结算**:L2 差价 = L3 实付零售价 − L2 申请时锁定的梯度供货价
  9. **代销方案设定入口(L1 视角)**:L1 可在代理中心为每个可代销商品设定/调整方案,方案变更对新申请生效
- **理由**:
  - 主流分销电商(云集/贝店)代销都是批量进货+库存管理,非单件代销
  - 梯度供货价激励代理批量拿货,数量越多单价越低,符合批发逻辑
  - 虚拟库存管理让代理可管控代销库存余量和补货时机,避免"卖空不知"
  - 补货阈值机制自动提醒,降低代理断货风险
  - 供货价锁定保护代理权益,L1 后续调价不影响已代销库存
  - 详情页精简(去收藏/客服)聚焦核心交易动作(代销+购买),符合 C 端极简设计
- **影响**:
  - 更新 [mall_demo.html](file:///d:/HelloWorld/Company_Project/Node/pm/原型/商城/mall_demo.html) 为 v2.2
  - 更新 [Node商城模块设计方案](file:///d:/HelloWorld/Company_Project/Node/pm/文档库/03-方案/Node商城模块设计方案.md) 4.3.2 节(代销模式流程重写)+ 4.3.1 双轨对比表
  - 后端代销服务需新增:代销方案管理(L1 设定)/代销库存管理(虚拟库存)/补货提醒/梯度供货价锁定
  - 商品数据结构新增 agencyPlan 字段(minQty/maxQty/tiers/restockThreshold)
  - 代理商品管理页新增库存进度条/已售/已赚差价/补货按钮
  - 不影响:14 项架构决策(严格层级/代销官方直发/指导价区间等全部保留)

  4. **代理中心重构**:去掉"申请代理"和"上架商品"快捷功能,改为商品管理/销售订单/收货地址/店铺设置 4 个管理职能
  5. **删除 view-agent-apply 视图**:申请代理功能完全下沉到详情页

  7. **代理中心新增"代销引导提示卡"**:提示用户"去商城详情页点击一键代销",保持路径可发现性
  8. **代理中心新增"我的代销商品概览"**:横向滚动卡片快速查看代销商品和差价
  9. **隐藏上架商品入口**:view-add-product 代码保留(未来可恢复),但入口全部隐藏
- **理由**:
  - 主流分销电商(云集/贝店/有赞/拼多多)的代理入口都在商品详情页,代理中心是管理后台,无独立申请流程
  - 所见即所得:用户看到商品即可一键代销,转化路径最短

- **日期**: 2026-07-16
- **背景**: v1.0 商城定位为 Aeon R9 渠道四"购买即绑定"的落地载体,采用扁平化设计(全平台分销商商品统一展示,不区分买家层级)。实际运营发现与 Node 分销团队体系脱节:分销团队是层级化的(官方→L1→L2→L3),但商城是扁平的,代理无法管控下级看到的商品;仅有"直购"一种交易形态,缺少代理模式(批发/代销),代理盈利空间单一;"热门分销员"推荐位偏离商品本质且与层级代理逻辑冲突
- **可选项**: 详见 [Node商城模块设计方案 v2.0](file:///d:/HelloWorld/Company_Project/Node/pm/文档库/03-方案/Node商城模块设计方案.md) 第0.2节决策汇总(14项)
- **决策**: 采用 v2.0 层级化代理商城方案,含 14 项架构决策
  - **架构核心(7项)**:
    1. **商城可见范围**:严格层级,下级只看直推上级(L1)商品池,不看全平台
    2. **代理模式**:双轨并行,P1 先做代销(一件代发),P2 做囤货(自主经销)
    3. **官方触达**:纯层级,官方不对 C 端,只对 L1 代理开放商品
    4. **代销发货**:官方直发终端,L1 代销官方商品,L2 下单后官方直发 L2
    5. **定价权**:官方设零售指导价区间,L1 在区间内自主定价
    6. **永久关系提示**:移到结算页(详情页纯商品信息),遵循 Aeon R9 知情确认铁律
    7. **商品详情字段**:精简至价格+名称+详情+商品图(1主图+≤2副图,共≤3张)
  - **次级规则(7项)**:
    8. 代理申请门槛:任意已绑定下级 + 上级审核通过
    9. 代销代理价:等级统一代理价(官方按 L1/L2/L3 等级定供货价)
    10. 缺货兜底:显示"缺货·可通知上级补货",L2 通知 L1,不穿透官方(保纯层级)
    11. 批发定价(P2 囤货):阶梯数量+等级折扣结合(10/50/100件,L1/L2/L3不同价)
    12. 商品图规则:1主图(封面)+最多2副图,共≤3张

## 决策-006 Aeon R9 集成 Node 的架构决策

- **日期**: 2026-07-09
- **背景**: 引入 Aeon R9 冷钱包上下级永久绑定方案,需要确定如何在 Node 产品中落地。核心矛盾是 Node 现状为"单身份驱动的资产 App",而 Aeon R9 需要的是"多身份可切换的账号服务",身份粒度不同
- **可选项**: 详见 [Aeon R9集成Node产品架构演变方案](file:///d:/HelloWorld/Company_Project/Node/pm/文档库/03-方案/Aeon%20R9集成Node产品架构演变方案.md) 第2章
- **决策**: 采用 3 Tab 重组方案
  1. **Tab 1 保持纯粹**:冷钱包不引入任何业务模块(参考主流 Web3 钱包 MetaMask/Phantom/Trust)
  2. **Tab 2 重命名**:服务舱→身份(待最终考究),保险库升级为全 App 安全基座,向 Tab 1/3 暴露 `isBoundAddress` 校验
  3. **Tab 3 新增**:账号(Aeon R9 落点),核心是身份切换器 + 推广/团队/邀请/佣金/待分配池
  4. **绑定上级入口**:放 Tab 3 推广中心内(非 Tab 1),因为绑定是"加入推广体系"属账号服务,签名能力是 Node 全局能力可跨 Tab 拉起
  5. **身份切换器范围**:仅 Web3 钱包地址,Web2 凭证不参与关系绑定
  6. **Tab 1/2 不跟随 Tab 3 切换**:Tab 3 独立视角,Tab 1/2 保持全局单地址模式
  7. **邀请返利归属**:明细全在 Tab 3(邀请关系管理+返利明细都是账号视角)
- **理由**:
  - Tab 1 纯粹性:参考主流 Web3 钱包,冷钱包 Tab 1 均不掺杂推广/关系/社交逻辑
  - 绑定归 Tab 3:之前考虑放 Tab 1 是技术视角(签名上链),但用户认知里绑定是加入推广体系,且签名是全局能力不依赖 Tab 1
  - 身份切换仅 Web3:关系在链上以地址为真身,Web2 凭证不参与
  - 不跟随切换:避免破坏 Tab 1/2 现有架构,Tab 3 独立视角更灵活
- **影响**:
  - 起草 [Aeon R9集成Node产品架构演变方案](file:///d:/HelloWorld/Company_Project/Node/pm/文档库/03-方案/Aeon%20R9集成Node产品架构演变方案.md) 作为技术对接文档
