## 开篇：遇见 Node

### 一句话定位

**Node 是一个纯 Web3 自管钱包与数字通行证管理中枢**，围绕链上钱包地址，把“资产—关系—权益—身份—应用”五件事拧成一股绳。

### 我们在解决什么问题

Web3 时代，用户面对的是三个割裂的痛点：

| 痛点        | 现状                   | Node 的解法                      |
| --------- | -------------------- | ----------------------------- |
| **资产自管难** | 私钥管理门槛高、设备绑定弱、女巫攻击频发 | 本地加密 + 设备指纹硬约束，一台设备同时刻只能绑一个钱包 |
| **关系不可信** | 推荐关系随时可改、归因不清、佣金可赖账  | 链上一次写入永久不可改，5 渠道归因裁决，佣金成交即结算  |
| **权益不流通** | 短号、商品码、卡密散落各处，处置渠道匮乏 | 统一抽象为链上资产，二级市场支持一口价/拍卖/租赁/赠送  |

### 产品三大铁律

1. **私钥永不上链、永不上云** —— 本地加密存储，设备指纹硬约束
2. **关系永久，迁移受限** —— 上下级一次绑定终身有效，唯一可动关系的口子是多签治理
3. **地址即身份** —— 算钱、绑定、鉴权只信链上地址，短号/Web2 凭证仅作辅助

> 这三条是不可破坏的底线，所有产品决策都必须让位于它们。

### 1.1 五大 Tab 一级架构

Node App 由 5 个一级 Tab 构成，通过底部胶囊导航切换。**Tab 顺序**：钱包 → 团队 → 交易 → 应用中心 → 身份。

```
┌──────────────────────────────────────────────────────────┐
│  Tab 1: 钱包 — 纯资产操作                                  │
│   资产看板 / Swap 兑换 / 水龙头 / 收发 / 钱包管理         │
├──────────────────────────────────────────────────────────┤
│  Tab 2: 团队 — 永久关系网络                                │
│   推广中心 / 我的团队 / 邀请中心 / 佣金明细                │
├──────────────────────────────────────────────────────────┤
│  Tab 3: 交易/商城 — 统一商品池 + 级差返利                  │
│   官方商品池 / 直购下单 / 订单 / 持有码 /                 │
│   短号中心 / 流转市场 / 唯一码库存                        │
├──────────────────────────────────────────────────────────┤
│  Tab 4: 应用中心 — 第三方应用分发                          │
│   官方精选 / IM 社交 / 跨境电商 / Web3 类 / 我的          │
├──────────────────────────────────────────────────────────┤
│  Tab 5: 身份 — Web3 权益与凭证                            │
│   福利特权 / 保险库 / DID 通行证 / DApp 探索              │
└──────────────────────────────────────────────────────────┘
```

**为什么是这个顺序？**

- 钱包在前：用户第一诉求是“我的资产在哪”
- 团队居二：关系网络是后续所有商业逻辑的基础
- 交易居中：商业引擎，承接钱包的支付能力与团队的关系网络
- 应用中心靠后：生态扩展，不影响核心闭环
- 身份殿后：权益与凭证的聚合收口

### 1.2 三层次定位

```
┌─────────────────────────────────────────┐
│  C 端 App 层（5 Tab）                    │
│   用户直接操作：资产管理/关系绑定/       │
│   商品交易/应用使用                      │
├─────────────────────────────────────────┤
│  B 端配套层（服务管理后台）              │
│   运营配置：商品上架/参数/权益/审计       │
├─────────────────────────────────────────┤
│  基础设施层（链上合约 + 链下服务）        │
│   链上：关系存证/商品/返利/流转           │
│   链下：数据索引/归因/中继/结算           │
└─────────────────────────────────────────┘
```

**关键设计**：用户只感知 C 端 App，链上链下复杂性全部屏蔽。B 端后台是运营工具，不暴露给 C 端。

### 1.3 模块协同关系

```
Tab1 钱包 ──── 提供全局钱包（购买身份/付款地址）─────┐
                                                     │
Tab5 保险库 ─── 设备指纹校验（绑定/购买前置闸门）─────┤
                                                     │
Tab2 团队 ──── 永久上下级关系决定级差返利分润链 ─────┤
        └── 团队积分由 Tab3 购买累加                  │

Tab3 交易/商城 ─── 直购成交触发归因 + 返利 ◄─────────┘
        └── 商品码作为资产可进入流转市场

Tab4 应用中心 ─── 独立抽成体系，不参与团队归因

**一句话理解**：钱包付钱，团队定关系，保险库管安全，三者共同支撑交易商城的商业闭环；应用中心是独立生态，身份是权益收口。

## 第二章：核心商业引擎

Node 的商业闭环由六大引擎协同驱动，缺一不可。前五大引擎聚焦"商品池 + 关系 + 返利"的团队分润闭环；第六大引擎独立运作，承载应用生态变现。

### 2.1 引擎一：统一商品池

**传统分销商城的问题**：层级商品池导致下级看不到全平台商品、价格不透明、库存割裂。

**Node 的解法**：所有用户共享同一个官方商品池、同一个价格。

| 维度   | 传统分级商城        | Node 统一商品池 |
| ---- | ------------- | ---------- |
| 商品来源 | 各级代理自主上架      | 仅官方上架      |
| 价格   | 指导价区间，代理可自主定价 | 全平台同价      |
| 库存   | 层级调拨，库存分散     | 官方统一管理     |
| 用户所见 | 只看直推上级商品池     | 全平台统一商品池   |

**用户感知**：打开商城，所有人看到的是同一份商品列表、同一个价格、同一个库存。没有“我的上级卖什么”的差异感。

### 2.2 引擎二：级差返利

**核心机制**：用户购买商品后，沿其上线链向上取 3 层，按各层上线“自己的等级”派发返利。

**关键概念（必须分清）**：

| 概念           | 含义                      | 类比          |
| ------------ | ----------------------- | ----------- |
| **等级 rank**  | 每个人自己的代理级别（L1..L10）     | 你的“职级”      |
| **层级 layer** | 单笔订单里沿上线链的深度位（L1/L2/L3） | 这笔订单里你的“位置” |

**返利规则**：

- 每层返利比例 = 该层上线“自己的等级”对应的返利比例
- L1（直接上级）比例最高，L2 次之，L3 最低
- 等级越高，返利比例越高（激励代理升级）

**举例**：买家小明购买 100U 商品，上线链为：

- L1 上级张三（等级 3）→ 拿 L1 份额，按张三等级 3 的比例返利
- L2 上级李四（等级 5）→ 拿 L2 份额，按李四等级 5 的比例返利
- L3 上级王五（等级 1）→ 拿 L3 份额，按王五等级 1 的比例返利

**关键点**：每层返利比例由该层上线“自己的等级”决定，与买家等级、与其他上线等级都无关。这保证了“普众公平”——你自己升到 L10，不会抬高上线等级，但会让你自己作为别人上线时返利更多。

### 2.3 引擎三：永久关系

**核心机制**：上下级关系链上一次写入，永久不可改。

**5 渠道归因裁决**（按优先级从高到低）：

| 优先级 | 信号             | 场景                      | 落点        |
| --- | -------------- | ----------------------- | --------- |
| 1   | 扫码绑定         | 当面/点对点扫码，可覆盖历史归因（最强信号）  | 团队推广中心·扫码 |
| 2   | 主动搜索短号绑定       | 用户主动搜索上级短号发起绑定          | 团队推广中心·搜索 |
| 3   | 邀请链接/Deep Link | 远程裂变（30 天窗口，last-touch） | 团队邀请中心    |
| 4   | 团队申请         | 用户主动搜索短号申请加入，上级审批通过后绑定  | 团队申请中心    |
| 5   | 无有效信号          | 进孤儿池，系统自动分配             | 系统自动      |

> 团队绑定是商城购买的硬前置，用户必须通过上述 5 渠道之一完成绑定，成为买家后才能在商城下单。扫码/搜索短号绑定是最常见的主动绑定方式。

**用户感知**：

- 扫码/搜索短号绑定上级 → 永久有效，不可改
- 退货只退钱，不解除关系
- 唯一可动关系的口子是平台多签治理（特殊情况人工干预）

### 2.4 引擎四：动态压缩

**传统分销的问题**：上线不达标（等级 0）时，这层返利名额浪费，下级吃亏。

**Node 的解法**：未达标上线自动跳过，名额上卷给下一个合格上线。

**举例**：买家小明购买 100U 商品，上线链为：

- L1 上级张三（等级 0，不达标）→ ❌ 跳过
- L2 上级李四（等级 3，达标）→ ✅ 接管 L1 份额（按李四等级 3 取 L1 比例）
- L3 上级王五（等级 5，达标）→ ✅ 接管 L2 份额（按王五等级 5 取 L2 比例）

**关键点**：返利总名额不变（始终 3 层），不合格上线被“压缩”跳过，名额上卷给合格上线。这保证了：

- 激励有效：不达标的上线拿不到钱，必须升级才能分润
- 名额不浪费：合格上线能多拿，激励他们积极发展团队

### 2.5 引擎五：双积分体系

**传统分销的问题**：只看个人业绩 → “空团长”现象（只靠下级业绩升级，自己不做事）。

**Node 的解法**：双积分并行，低级看个人，高级看团队。

| 积分类型     | 用途         | 获取方式            | 升级作用      |
| -------- | ---------- | --------------- | --------- |
| **个人积分** | L1→L2 升级燃料 | 购买“个人积分商品”      | 低级升级主要看个人 |
| **团队积分** | L3+ 升级燃料   | 下级购买“团队积分商品”时累加 | 高级升级必须看团队 |

**关键设计**：

- 个人积分防止“白嫖”——你想升级，自己得先有贡献
- 团队积分防止“空团长”——高级别必须有真实团队支撑
- 两者独立计算，不可互相替代

**用户感知**：升 L1/L2 主要靠自己买货；升 L3 及以上必须靠团队买货。这逼迫高级代理必须真正经营团队，而不是躺平收租。

### 2.6 引擎六：应用中心推广分发

**传统应用市场的痛点**：流量被头部应用商店垄断，开发者获客成本高、留存低；用户需要在多个应用间重复注册，身份割裂。

**Node 的解法**：把钱包的链上流量直接转化为第三方应用的分发与变现通道，平台从中抽成，合作方获得精准用户、用户获得一站式 DApp 入口。

| 维度 | 传统应用市场 | Node 应用中心 |
| --- | --- | --- |
| 流量来源 | 应用商店搜索竞价 | 钱包原生用户（自带身份与资产） |
| 用户身份 | 每个应用独立注册 | DID 通行证统一签名登录 |
| 分发模式 | 仅下载/跳转 | 分发抽成 + 推广位 + 交易抽成 + 生态联合 |
| 结算周期 | 平台掌控，T+30/T+60 | 分发 T+7 / 交易抽成 T+30 / 广告 T+30 |
| 合规风险 | 平台承担全部审核责任 | 合作方自带资质，Node 仅做资质审核与流量分发 |

**四大变现通道**（详见第六章平台收入结构总表）：

- **分发抽成**：用户经 Node 下载/安装 App，平台抽佣（T+7 结算）
- **推广位广告**：合作方投放 Banner/推广位，平台收广告费（T+30 结算）
- **交易抽成**：用户经 Node 进入 App 完成交易，平台按交易额抽成（T+30 结算）
- **生态联合**：HRCs 代币合作方的联合营销与跨生态空投（按协议）

**关键设计**：

- **不参与团队归因**：应用中心是独立抽成体系，不绑定上下级、不分润给上线
- **合规优先**：加密货币类应用严格资质审核，禁止内嵌 DApp 浏览器，由合作方承担自身合规责任
- **DID 联动**：用户用 Node 钱包地址或 DID 通行证登录第三方应用，无需重复注册
- **跨平台一致**：iOS 退化为应用导航站（跳转 App Store），Android 可直接分发 APK

**用户感知**：

- 用户在 Tab 4 浏览应用 → 通过 Node 钱包直接登录合作 App → 无需注册即用
- 合作方上架 App → 获得钱包流量入口 → 按 T+7/T+30 结算抽成
- 平台不直接承担加密交易合规责任，仅做资质审核与流量分发

> **与前五大引擎的边界**：引擎一至五构成"商品池 → 关系 → 返利"的团队分润闭环；引擎六独立运作，是平台单方抽成的流量变现通道，不参与团队分润。两者并行不冲突。

## 第三章：用户旅程

### 3.1 五种角色演进

```
游客 ──绑定团队──► 买家 ──升级──► 代理 ──升级──► 高级代理
 (未绑定)       (已绑定,rank=0)  (rank 1..2)   (rank 3..10)
```

| 角色       | 入口        | 核心能力                   | 限制      |
| -------- | --------- | ---------------------- | ------- |
| **游客**   | 下载 App 即可 | 浏览商品池（不可购买，需先绑定团队）     | 无购买、无返利、无升级 |
| **买家**   | 绑定团队/扫码绑定 | 浏览 + 购买商品 + 订单 + 持有码 + 流转市场 | 无返利、无升级 |
| **代理**   | 等级升到 1+   | 买家全部 + 返利领取 + 升级管理     | 无       |
| **高级代理** | 等级升到 3+   | 代理全部 + 可发布社区任务         | 无       |
| **矿工**   | 平台多签地址    | 后台运营（商品/审核/参数/资金）      | 仅平台方    |

### 3.2 从下载到代理的完整路径

```
1. 下载 App
   ↓
2. 创建/导入钱包（Tab 1）→ 本地加密存储私钥
   ↓
3. 激活保险库（Tab 5）→ 设备指纹绑定
   ↓
4. 绑定团队上级（Tab 2 推广中心）→ 扫码 / 搜索短号 / 接受邀请
   ↓
5. 上级审批通过 → 设备指纹 + 上下级关系绑定同步上链 → 成为买家
   ↓
6. 进入商城（Tab 3）→ 浏览商品池 → 选商品下单
   ↓
7. 购买“积分商品” → 累加个人积分
   ↓
8. 积分达标 → 申请升级（Tab 2 我的团队）→ 成为代理（rank 1+）
   ↓
9. 代理可领取返利（Tab 2 佣金明细）→ 一键领取
   ↓
10. 发展下级 → 下级购买累加团队积分 → 升级到高级代理
```

**关键触点说明**：

- **第 4-5 步**：必须先在 Tab 2 推广中心完成团队绑定（扫码/搜索短号/接受邀请），成为买家后才能在商城购买。这是"先绑定团队后购买"的硬约束
- **第 6 步**：游客可浏览商品池，但下单需先绑定团队上级（不可跳过）
- **第 8 步**：升级需同时满足个人积分和团队积分门槛（高级别）
- **第 9 步**：返利成交即结算，按商品价格冻结 7/14/30 天后可领（防退货刷单，详见 4.2）

### 3.3 角色信息展示

**C 端不展示的内容**（避免信息过载）：

- 购买者视角的“上级分佣明细”——内部数据
- 订单状态时间线——内部流程
- 双视角浮层（购买视角/上线视角）——仅产品/研发演示用

**C 端展示的内容**：

- 角色徽章（游客/买家/代理）

#### 钱包地址与短号的关系

这是 Node 体系内最容易混淆的一组概念，必须讲清楚：

| 概念       | 本质                  | 数量                 | 是否可改      |
| -------- | ------------------- | ------------------ | --------- |
| **钱包地址** | 链上唯一真身，算钱/绑定/鉴权只信地址 | 一个身份可有多个钱包地址       | 不可改       |

**用户感知**：

**白名单逻辑**（与等级(rank)/持仓挂钩）：

| Swap 操作                  | 白名单要求                           | 理由             |
| ------------------------ | ------------------------------- | -------------- |
| RC ↔ USDRs（同链基础）         | 无                               | 入门级，新用户必备      |
| USDT ↔ USDRs（跨链入金）       | 无                               | 入金主通道，不应设卡     |

**设计要点**：白名单采用“等级(rank) OR 持仓门槛”双维度，平衡风控与用户准入。等级越高，可操作的 Swap 额度越大，激励用户升级。

**返佣时间期限**（防退货刷单的核心机制）：

**为什么需要冻结期？**

- 返佣在成交时即时分配到上线名下，但处于“冻结”状态，不可领取
- 确认收货后进入冻结期倒计时

**动态压缩（已上线）**：上线等级不达标时自动跳过，名额上卷给合格上线，保证激励不浪费。

**烧断保护（规划中）**：当上级等级低于下级时触发（弱上级吃强下级场景），处理“上级已升级但弱于下级”的不合理分配。机制细节正在评审优化，确保返佣名额给到真正“够格”的上线，同时通过积分补偿保护实际推广者的利益。

> 完整机制说明详见技术版 4.6.4 节。能力成熟度详见附录。

#### 关系转移机制（重要）

**核心规则**：上下级关系绑定到**钱包地址**而非"人"。当用户需要换绑钱包地址时，原有的上下级关系自动随地址转移，无需重新建立绑定。

| 场景 | 转移机制 | 关系处理 |
| --- | --- | --- |
| **换设备** | 新设备导入同一钱包私钥 | 关系不变（地址未变） |
| **换钱包地址** | 旧地址资产转移至新地址 | **关系随地址转移**：旧地址的关系自动失效，新地址承接原关系（含上下级链路、积分、等级） |
| **多地址管理** | 一个身份可持有多个钱包地址 | 用户可切换"主用地址"，关系绑定在主用地址上 |
| **地址丢失** | 旧地址私钥丢失，无法访问 | 需走多签治理流程迁移关系到新地址（时间锁 + 矿工审核） |

**关键设计**：

- 关系绑定的客体是**钱包地址**，不是手机号、设备或身份证
- 换绑钱包地址时，关系链路上线 / 下线自动跟随，**无需上级重新审批**
- 等级、积分、佣金等状态均挂在钱包地址上，地址转移即资产与关系一并转移
- 这是"地址即身份"铁律的延伸——关系是地址的属性，不是人的属性

**用户感知**：

- 用户更换钱包地址 → 提交地址迁移申请 → 矿工审核通过 → 关系与资产一并迁移到新地址
- 上级 / 下级无需任何操作，关系链路自动延续
- 旧地址作废，新地址承接全部链上状态

> **设计要点**：这是 Node 体系内**唯一不通过多签治理就能"动关系"的合法路径**——因为关系绑在地址上，地址迁移本质是"换容器"而非"换关系"。这保证了用户对资产与关系的完全主权，同时避免通过多签治理动关系带来的治理成本。

### 4.3 交易/商城（Tab 3）—— 统一商品池 + 级差返利

- 保密商品链上仅存哈希，真实卡密链下管理

> **术语统一**：本文中“唯一码”是商品库存的底层单位；C 端功能入口沿用“🎫持有码”（即用户名下已购唯一码）；流转市场里作为资产品类时称“商品码”。三者指同一对象的不同语境叫法。

#### 订单管理

**4 Tab 分类**（语义互斥，默认选中“进行中”）：

| Tab | 包含状态               |
| --- | ------------------ |

#### 短号中心

**三 Tab 设计**：

| 💾 我的短号 | 列出已绑定的全部短号（一个身份可绑多个靓号 + 1 个免费号）                |

**短号资产管理**：

### 4.4 应用中心（Tab 4）—— 第三方应用分发

**定位**：把 Node 钱包的用户流量转化为 App 分发收入，纯平台抽成模式，不参与团队归因。

**核心商业逻辑**：合作方将 App 上架到商城，用户通过商城进入/下载/连接这些 App，平台从中抽取佣金。**不涉及分销/上下级绑定**。

**与 Tab 3 商城的边界**：

| 维度   | Tab 3 商品商城       | Tab 4 应用市场     |
| ---- | ---------------- | -------------- |
| 标的物  | 实物/虚拟/服务商品（单次交易） | 第三方应用（持续分发）    |
| 上架方  | 仅官方上架            | 合作方（开发者/商家）    |
| 归因机制 | 团队绑定前置（先绑定后购买）   | 平台抽成，不绑定上下级    |
| 佣金流向 | L1/L2/L3 多级分账    | 平台单方抽成         |
| 结算周期 | 成交即结算            | 周期结算（T+7/T+30） |

**信息架构**：

```
Tab4: 应用中心
├ 顶部：搜索栏 + 我的应用入口
├ Banner（应用市场整体介绍）
├ 金刚位（5 个）：
│   ├ 官方精选 → 自家 IM 工具列表
│   ├ IM 社交 → IM App 列表
│   ├ 跨境电商 → 电商 App 列表
│   ├ Web3 类 → App + DApp 列表
│   └ 我的 → 最近打开历史 + 上架申请
└ 精选 DApp → 持续收录中
```

**iOS / Android 差异**：

- iOS：只能跳转 App Store（欧盟 DMA 侧载除外），退化为"应用导航站"
- Android：可直接分发 APK，是真正的"应用市场"
- 两端 UI 一致，差异仅在跳转逻辑

> **🛡️ 合规即护城河**：加密 / 钱包类应用在各大应用商店的上架门槛极高，多数团队因资质缺失被拒之门外。Node 采取「合规优先」设计——平台自身不承载加密货币直接交易、不内嵌 DApp 浏览器、对合作方做资质与安全双重审核——这不是限制，而是让合作方能**安全、可持续地借 Node 流量落地**的核心优势。

#### 上架要求与行业规定

**合作方上架 App 需满足的合规要求**（重要，涉及应用能否在各应用商店上架）：

**iOS App Store 审核（严格）**：

- 加密货币/钱包类应用审核极严，直接以“币安钱包”等名称涉及加密交易功能的 App 在部分地区无法直接上架
- **禁止内嵌 DApp 浏览器**：苹果政策明确移除内置 DApp 浏览器（Trust Wallet 案例）
- 涉及加密货币购买/持有的应用，需通过受监管司法管辖区的认证服务
- 钱包类应用需提供合规资质，否则审核被拒

**Google Play 政策（2024 年起强制）**：

- 加密货币钱包开发商在 15 个主要司法管辖区（含美国/英国/欧盟）上架前，**必须获得政府颁发的许可证**
- 美国地区：加密钱包应用需在 FinCEN（金融犯罪执法网络）登记为货币服务业务（MSB）
- 必须提供联邦执照，否则不予上架

**国内安卓商店**：

- 涉及加密货币/区块链的应用国内不允许上架
- 需提供软著、ICP 备案、应用安全评估
- Node 在国内主要通过自有渠道分发，不走应用商店

**Node 应用中心的上架策略**：

| 上架类型              | 合规要求                 | Node 的角色       |
| ----------------- | -------------------- | -------------- |
| **自家 IM 工具**      | 自有资质，走正常应用商店审核       | 官方精选推荐         |
| **第三方 IM/电商 App** | 合作方提供合规资质            | 导航跳转，不参与分发     |
| **Web3 DApp**     | 走 DApp 收录导航模式，不内嵌浏览器 | 跳转系统浏览器或 Tab 1 |
| **加密货币相关 App**    | 合作方需提供当地合规许可证        | 严格审核，拒绝无资质应用   |

**合作方上架流程**：

```
1. 合作方提交上架申请（Tab 4 → 我的 → 上架申请）
2. Node 平台审核：
   ├─ 资质审核（营业执照/ICP/加密货币许可证）
   ├─ 应用安全评估（病毒/恶意代码/隐私政策）
   ├─ 内容合规审核（违法/违规内容）
   └─ 业务模式审核（是否符合 Node 生态定位）
3. 审核通过 → 签署合作协议（确定抽成比例）
4. 上架应用中心
5. 持续运营监控（违规下架机制）
```

**收益模式**：

| 收益类型     | 说明                         | 结算周期 |
| -------- | -------------------------- | ---- |
| **分发收益** | 用户通过 Node 下载/安装 App，平台抽成   | T+7  |
| **推广收益** | 合作方投放推广位/Banner，平台收广告费     | T+30 |
| **交易抽成** | 用户通过 Node 进入 App 完成交易，平台抽成 | T+30 |
| **生态联合** | HRCs 代币合作方的联合营销收益          | 按协议  |

> **合规红线**：Node 应用中心不参与加密货币的直接交易功能，仅做应用导航与分发。涉及加密交易的功能由第三方 App 自身承担合规责任，Node 仅做资质审核与流量分发。

### 4.5 身份（Tab 5）—— Web3 权益与凭证聚合

**定位**：Web3 身份的权益与凭证集中地，聚焦“身份权益 + 安全基座 + 凭证通行”三件事。

```
Tab 5: 身份
├ 福利特权（空投/资产/互动）
├ 安全与保障
│   ├ 保险库（Vault，全 App 安全基座）
│   └ 数字身份通行证（DID Pass）
└ DApp 探索（持续扩展）
```

> **模块归属说明**：短号中心与流转市场虽是链上资产管理功能，但属于交易/处置语义，已归属 Tab 3 交易/商城（见 4.3 节）。Tab 5 身份聚焦身份权益、安全保障与凭证通行，不再承担资产处置职能。

#### 福利特权

**基础能力**：

| 福利类型     | 说明                         |
| -------- | -------------------------- |
| **空投福利** | 平台定期空投 USDRs/HRCs 给符合条件的用户 |
| **资产福利** | 体验商品、试用权益、限时卡券             |
| **互动福利** | 签到、任务、活动奖励                 |

**领取条件**：所有福利领取都需通过设备指纹绑定校验（反女巫）。

#### 保险库（Vault）—— 全 App 安全基座

**核心机制**：

| 能力         | 说明                         |
| ---------- | -------------------------- |
| **设备指纹绑定** | 一台物理设备同一时刻只能绑定一个钱包（反女巫硬约束） |
| **冷密钥生成**  | 基于设备指纹生成非对称密钥对，私钥永不上传      |
| **前置闸门**   | 福利领取/团队绑定/商城购买的前置校验        |

**与其他模块的关联（重要）**：

| 模块   | 设备指纹要求      | 说明                        |
| ---- | ----------- | ------------------------- |
| 福利特权 | ✅ 必须        | 领取空投/资产/互动福利前需绑定设备指纹      |
| 团队   | ✅ 必须        | 绑定上下级关系前需绑定设备指纹           |
| 商城   | ✅ 必须 + 团队身份 | 商城购买需同时满足设备指纹绑定 + 团队身份绑定  |
| 应用中心 | ❌ 不强制       | 应用下载/使用不强制设备指纹（但部分权益领取需要） |
| 身份   | ✅ 必须        | 短号绑定/DID 通行证激活需设备指纹       |

> **设计要点**：设备指纹是全 App 的安全基座，福利/团队/商城三大核心场景都强制要求设备指纹唯一绑定。商城还需额外完成团队身份绑定（先绑定团队后购买）。这保证了"一个真人一个钱包"的反女巫底线。

**保险库延伸能力（未来扩展，待详细设计）**：

| 延伸能力       | 说明                             | 价值                       |
| ---------- | ------------------------------ | ------------------------ |
| **钥匙管理**   | 多种密钥的统一管理（钱包私钥/DID 签名钥/设备指纹密钥） | 一站式密钥管理，降低用户管理成本         |
| **资产托管信托** | 基于设备指纹 + 多签的资产托管服务             | 高价值资产的安全托管（如遗产继承、大额资产托管） |
| **保险库服务**  | 资产保险、紧急冻结、找回机制                 | 资产丢失/被盗后的兜底保障            |
| **联合签名**   | 多设备多签确认                        | 重要操作需多设备确认（如大额转账）        |

> **延伸说明**：保险库未来可承载更多“资产安全信托”能力，例如：用户可设定“遗产继承人”地址，长期不活跃后资产自动转入；或设定“大额转账需双设备确认”等。这些延伸能力已在产品规划中，将随核心功能稳定后逐步落地。

#### DID 通行证 —— 数字身份连接器

**核心能力**：作为外部应用的“登录钥匙”。

**登录流程**：

```
第三方 App（IM/DApp/合作应用）
  → 拉起 Node 授权面板
  → 用户选择签名主体（Web3 钱包地址 或 Web2 本地凭证）
  → 输入 6 位本地 PIN 码
  → Node 本地私钥签名
  → 返回签名凭证 → 完成登录
```

**与应用身份节点打通**：

| 打通场景        | 说明                                   |
| ----------- | ------------------------------------ |
| **IM 应用**   | 用户用 Node 钱包地址登录 IM，IM 内可直接调起 Node 转账 |
| **DApp**    | DApp 通过 Node 钱包连接，无需自建钱包体系           |
| **Web2 应用** | Web2 应用通过 Node DID 实现无密码登录（零知识证明）    |
| **跨应用身份**   | 一个 Node 身份通行多个应用，无需重复注册              |

**未来愿景**：Node 作为 Web3 时代的签名基础设施——

- 用户带一个钱包地址即可通行全生态
- 外部应用无需自建用户体系，接入 Node 即可获得身份能力
- 所有应用的身份验证都通过 Node 本地签名完成，私钥永不离开设备
- AI Agent 可作为用户的链上代理，自动完成签名授权、资产管理等操作

## 第五章：流转市场 —— 二级资产处置中心

> 短号中心与流转市场均归属 Tab 3 交易/商城（详见 4.3 节）。短号中心负责短号的发行（购买/领取）与持有管理，流转市场负责短号与商品码的二手处置。本章重点讲流转市场，短号中心的具体能力见 4.3 节。

### 5.1 定位

**用户名下所有链上资产（短号 + 商品码）的二手处置中心**。卖家在此挂单出售/出租/拍卖自己持有的资产，买家在此浏览并成交。

**与一级市场的边界**（同属 Tab 3 交易/商城，但业务规则不同）：

| 维度     | 商城一级发行      | 流转市场二级处置    |
| ------ | ----------- | ----------- |
| 资产生命周期 | 一级发行        | 二级处置        |
| 角色     | 官方发行新商品     | 用户处置既有资产    |
| 是否触发归因 | 团队绑定前置（购买前必须完成绑定） | **不触发**（铁律） |
| 是否分润   | 触发级差返利分配    | **不触发**（铁律） |

> **铁律**：流转市场所有渠道流水不纳入代理奖励分润。二级市场是“资产处置”不是“团队裂变”。

### 5.2 四大渠道

| 渠道      | 适用场景            | 特点               |
| ------- | --------------- | ---------------- |
| **一口价** | 主渠道，快速变现        | 天生 0% 手续费，货款全付卖家 |
| **拍卖**  | 高价靓号、限量资产       | 竞价模式，2.5% 手续费    |
| **租赁**  | 使用权分离（ERC-4907） | 所有权不动，租客获得使用权    |
| **赠送**  | 即时过户给指定地址       | 不在市场挂单，但订单中心可见记录 |

### 5.3 资产类型

流转市场支持 7 类资产：

| 资产品类     | 图标           | 适用渠道               |
| -------- | ------------ | ------------------ |
| 💎 靓号短号  | 豹子/顺子/吉尾号    | 一口价 / 拍卖 / 租赁 / 赠送 |
| 🎁 免费号短号 | 10-12 位无靓号特征 | 一口价 / 赠送           |
| 🛒 实物商品码 | 硬件钥匙等        | 一口价 / 赠送           |
| 🎫 虚拟兑换码 | 会员卡/兑换券      | 一口价 / 拍卖 / 租赁 / 赠送 |
| 🛎️ 服务包码 | 咨询/服务时长      | 一口价 / 租赁 / 赠送      |
| 🔒 保密商品码 | 链下脱敏展示       | 一口价 / 拍卖 / 赠送      |

### 5.4 市场主视图

**对齐主流市场心智**（OpenSea / Blur / Magic Eden）：

```
流转市场（单视图 · 无底部 Tab）
├ 🏪 市场浏览（唯一主视图 · 买方视角）
│   ├ Header：返回 + 标题 + 🔍搜索 + 👤我的（右上角）
│   ├ 渠道分类快捷切换（全部 / 一口价 / 拍卖 / 租赁）
│   ├ 资产类型筛选（7 类单选）
│   ├ 排序条（挂单数 + 排序方式）
│   └ 挂单网格（2 列，覆盖 7 类资产）
│
└ 👤 我的（全屏页 · 右上角入口进入）
    ├ 资产概览卡（持有数 / 在售挂单 / 累计收益 / 估值）
    ├ 我的资产（可流转）· [挂售][详情]   ← 卖家挂售入口
    ├ 我的挂单（在售）· [撤单][详情]
    ├ 我的出租（进行中）· [结束租赁]
    └ 订单记录（跨渠道）· 卖出/购买/租赁/赠送
```

**设计要点**：

- 市场单视图，无底部 Tab，减少导航层级
- 渠道快捷切换让买家按成交模式筛选
- 挂售按钮仅出现在“我的 → 我的资产”卡片上，不在市场视图暴露

### 5.5 资产可处置性

并非所有持有资产都可进入流转市场：

| 资产状态           | 可挂售 | 可拍卖 | 可租赁 | 可赠送 |
| -------------- | --- | --- | --- | --- |
| 短号 - 已绑定       | ✅   | ✅   | ✅   | ✅   |
| 短号 - 转移中/已挂售   | ❌   | ❌   | ❌   | ❌   |
| 商品码 - 可售（未售出）  | ❌   | ❌   | ❌   | ❌   |
| 商品码 - 已售       | ✅   | ✅   | ✅   | ✅   |
| 商品码 - 已退（永久作废） | ❌   | ❌   | ❌   | ❌   |

### 5.6 各渠道能力详解

#### 一口价渠道

| 能力   | 说明                           |
| ---- | ---------------------------- |
| 挂单   | 卖家定价 → 资产锁定 → 等待买家           |
| 购买   | 买家支付 → 货款全付卖家（0% 手续费） → 资产过户 |
| 撤单   | 卖家可随时撤单 → 资产解锁               |
| 强制撤单 | 矿工可强制撤单（异常订单处理）              |

#### 拍卖渠道

| 能力   | 说明                      |
| ---- | ----------------------- |
| 挂拍   | 卖家设起拍价 + 加价幅度 + 拍卖时长    |
| 出价   | 买家出价，资金锁定               |
| 成交   | 拍卖结束，最高价者得，2.5% 手续费     |
| 强制结算 | 拍卖异常时，矿工可强制结算（防卖家恶意不交付） |
| 强制取消 | 矿工可强制取消拍卖（异常情况）         |
| 退款提取 | 未中标者可提取退款               |

> **风控设计**：拍卖渠道包含强制结算/强制取消/退款提取三大风控能力，防止卖家恶意不交付或拍卖异常卡死。

#### 租赁渠道（ERC-4907 使用权分离）

| 能力    | 说明                      |
| ----- | ----------------------- |
| 出租    | 出租方设定租金 + 租期 + 是否独占     |
| 承租    | 租客支付租金 → 获得使用权（所有权不动）   |
| 独占模式  | 独占租赁期间资产锁定，不可再挂售/赠送     |
| 非独占模式 | 非独占租赁不锁，可同时挂售（需提示租客）    |
| 结束租赁  | 出租方/矿工可提前终止；租客只能到期后自动结束 |

**租赁适用场景**：

- 靓号短号出租（让别人临时使用你的靓号）
- 虚拟兑换码出租（会员卡/兑换券使用权）
- 服务包码出租（按时长付费）

#### 赠送渠道

| 能力   | 说明                         |
| ---- | -------------------------- |
| 赠送   | 号主付手续费后立即过户给指定地址           |
| 非挂单  | 赠送不在市场挂单弹窗暴露，入口在短号中心/商品详情页 |
| 订单可见 | 赠送记录在订单中心可见                |

> **设计说明**：赠送是“即时过户”语义，非“挂单等待买家”。放在挂单弹窗与一口价/拍卖并列会导致语义混淆，因此入口独立在短号中心/商品详情页。

### 5.7 未来扩展渠道（P2/P3）

| 渠道        | 优先级  | 说明                   |
| --------- | ---- | -------------------- |
| **荷兰拍**   | P3   | 线性降价模型，适合清仓/动态定价     |
| **集邮挖矿**  | P3   | 集齐特定组合获得奖励（获得方式，非处置） |
| **碎片化流转** | 暂不启动 | 合规风险高，暂不开放           |

### 5.8 流转市场风控

| 风险            | 防御机制           |
| ------------- | -------------- |
| 双挂（同一资产挂多个渠道） | 跨渠道锁           |
| 恶意挂单          | 矿工可强制撤单        |
| 拍卖异常          | 强制结算/强制取消/退款提取 |
| 保密商品卡密泄露      | 链下脱敏展示，仅显示哈希   |
| 退货商品二次流转      | 已退码永久作废，不可流转   |
| 跨网络限制         | 短号跨网络流转在合约层拦截  |

### 6.5 商业闭环图

```
用户下载 App
    ↓
创建钱包（Tab 1）→ 水龙头领 Gas（零成本入门）
    ↓
绑定团队上级（Tab 2 推广中心）→ 扫码 / 搜索短号 / 接受邀请 → 成为买家
    ↓

    ↓

    ↓

3. **资产飞轮**：购买 → 持有 → 流转 → 增值 → 再投资

## 第七章：安全与风控

### 7.1 资产安全

| 维度   | 机制                  |
| ---- | ------------------- |
| 私钥存储 | 本地加密存储，永不上链、永不上云    |
| 导出私钥 | 需 PIN 码，明文展示 + 警告提示 |
| 设备指纹 | 一台设备同时刻只能绑一个钱包（反女巫） |
| 冷密钥  | 基于设备指纹生成，私钥永不上传     |
| 多签钱包 | 矿工权限地址必须多签（防盗抽干资金）  |

### 7.2 关系安全

| 维度     | 机制                  |
| ------ | ------------------- |
| 永久绑定   | 上下级关系一次写入，永久不可改     |
| 退货不退关系 | 退货只退钱，不解除绑定         |
| 地址迁移转移 | 换绑钱包地址时关系自动随地址转移（合法路径，无需多签） |
| 治理迁移   | 地址丢失等极端场景需多签 + 时间锁（详见 4.2 关系转移机制） |
| 5 渠道归因 | 多信号裁决，避免单一渠道作弊      |

### 7.3 反女巫与反刷单

| 风险                   | 防御机制                |
| -------------------- | ------------------- |
| 女巫攻击（批量注册）           | 设备指纹排他绑定            |
| 刷单升级（小号买货→大号升级→小号退货） | 退货率风控 + 矿工可手动降级     |
| 返利刷单（领奖后退货）          | 退货前置校验奖励退回状态        |
| 保密商品卡密泄露             | 链上存哈希 + 链下映射，禁止明文上链 |
| Gas 刷量（Faucet 滥用）    | 设备指纹 + IP 频次 + 防重放  |

### 7.4 资金安全

| 维度      | 机制                        |
| ------- | ------------------------- |
| 退货退款    | 矿工多签审核，防单点作恶              |
| 大额 Swap | 白名单分级（等级(rank) 门槛 + 持仓门槛） |
| 流转市场挂单  | 跨渠道锁，防双挂                  |
| 拍卖结算    | 强制结算/取消/退款机制              |

## 第八章：演进路径与合作机会

### 8.1 产品演进简述

Node 由原“IM 开放服务生态矩阵”独立剥离，集成 Aeon R9 关系网络，演进为当前的 5 Tab 形态。演进逻辑：

```
IM 开放服务生态矩阵
  → 业务解耦，Node 独立为纯 Web3 自管钱包 App
  → Aeon R9 集成，5 Tab 形态成型
  → 当前：5 大模块框架与核心功能已完成
  → 未来：Node 作为 Web3 时代的签名基础设施
```

### 8.2 当前进度

**5 个 Tab 的框架与基本功能已全部完成**，包括：

- 钱包：资产看板 / Swap / 水龙头 / 钱包管理
- 团队：推广中心 / 我的团队 / 佣金明细 / 邀请中心
- 交易/商城：统一商品池 / 直购下单 / 订单管理 / 持有码 / 短号中心 / 流转市场
- 应用中心：MVP 信息架构
- 身份：福利特权 / 保险库 / DID 通行证

部分细节与延伸功能（如社区制任务、烧断机制、保险库信托能力、跨链 Bridge、荷兰拍、应用中心合作方接入与 CPS 抽成等）仍在规划与开发中，不影响核心商业闭环的跑通。

### 8.3 合作机会

#### 商品供应合作

**合作方式**：通过矿工后台上架商品，共享全平台流量

**适合品类**：硬件设备、虚拟卡密、服务包、积分包

**合作价值**：无需自建分销渠道，借助 Node 的级差返利机制快速裂变

#### 应用分发合作

**合作方式**：Tab 4 应用中心上架 App

**适合类型**：IM 社交、跨境电商、Web3 DApp

**合作价值**：获得钱包用户流量，平台抽成模式，无需自建用户体系

#### 生态联合合作

**合作方式**：HRCs 代币合作、跨生态空投

**适合对象**：Web3 生态项目方

**合作价值**：联合营销、用户互通、资产跨链

#### 技术接入合作

**合作方式**：DID 通行证作为登录钥匙

**适合对象**：第三方 DApp、Web2 应用

**合作价值**：用户无需重复注册，Node 钱包提供签名基础设施

### 8.4 愿景

**近期**（1 个月内）：5 Tab 核心功能上线公测，跑通“钱包 → 团队 → 商城”商业闭环；流转市场三渠道（一口价/拍卖/租赁）同步开放。

**中期**（1-3 个月）：应用中心首批合作方接入；DID 通行证打通首批第三方应用；保险库延伸能力（钥匙管理/资产托管）启动设计。

**远期**（3-6 个月）：Node 成为 Web3 时代的签名基础设施——用户带一个钱包地址即可通行全生态，AI Agent 作为智能助手融入产品各环节（智能客服、风控、推广策略生成等）。

> **阶段量化目标（待补充）**：公测激活钱包数 / GMV / 代理数 / 流转市场成交额等硬指标，待项目方与运营团队确认真实目标后补入；当前阶段以「能力就绪度 + 时间轴」代替，避免对外披露未经确认的预测数字。
