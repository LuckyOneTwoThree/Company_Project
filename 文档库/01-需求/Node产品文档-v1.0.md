## 1. 产品概述

### 1.1 产品定位

**Node 是一个纯 Web3 Native 的自管钱包与数字通行证管理中枢**，围绕链上钱包地址构建"资产—关系—权益—身份—应用"五位一体的产品体系。

产品从原"IM 开放服务生态矩阵"中独立剥离，聚焦三件事：

1. **自管冷钱包**：用户链上资产的本地安全钥匙箱
2. **关系网络层**：基于链上地址的永久上下级绑定与多级返佣分账
3. **服务舱**：围绕钱包地址构建的福利、安全、身份、应用服务

### 1.2 核心价值主张

| 维度 | 价值 |
|---|---|
| **资产安全** | 私钥永不上链、永不上云，本地 Keychain 加密存储，设备指纹硬约束防女巫 |
| **关系永久** | 链上 `referrerOf` set-once 永久绑定，5 渠道归因裁决，不可篡改 |
| **多级返佣** | 级差制返利模型，3 层上线分润，烧伤压缩机制保证激励有效 |
| **资产流转** | 短号、商品码统一抽象为 SKU 资产，二级市场支持一口价/拍卖/租赁三渠道 |
| **生态拓展** | 应用市场作为第三方应用分发入口，连接 IM/电商/Web3 生态 |

### 1.3 产品边界

| 范畴 | 包含 | 不包含 |
|---|---|---|
| **C 端 App** | 5 Tab：钱包/团队/交易/应用中心/身份（详见 2.1 节顺序约定） | IM 聊天通讯（已剥离为独立 App） |
| **B 端配套** | 服务管理后台（运营配置/合约/参数/权益/审计/权限） | IM 开放服务统一后台（已剥离） |
| **身份体系** | Web3 钱包地址（主）+ Web2 本地凭证（辅） | 平台托管钱包余额、云端账号体系 |
| **存储** | 本地 Keychain 加密存储 + 链上关系存证 | 云端不存"地址↔Web2 账号"映射 |

### 1.4 核心设计原则

1. **纯 Web3 Native 架构**：产品引导仅提供 Web3 自管钱包创建与导入，不设传统 Web2 注册/登录入口
2. **本地凭证存储，云端无状态**：Web2 凭证仅保存在本地 Keychain，云端绝不存储"地址↔Web2 账号"映射
3. **地址即身份**：链上钱包地址是唯一真身，算钱/绑定/鉴权只信地址；短号、Web2 凭证仅作索引与登录辅助
4. **数字身份连接器（DID Provider）**：作为外部应用的"登录钥匙"，第三方 App 拉起 Node 授权面板签名登录
5. **设备指纹硬约束**：保险库的设备指纹是绑定/领福利的前置闸门，一台物理设备同一时刻只能绑定一个钱包（反女巫）
6. **关系永久，迁移受限**：上下级关系 set-once，唯一可动关系的口子是 miner 多签 + 时间锁的治理迁移

### 1.5 演变背景

```
阶段1 (2026-06): IM开放服务生态矩阵
  ├ IM App(聊天+发现页)
  ├ 福利特权中心(WebView嵌入)
  ├ 安全保险库(WebView嵌入)
  └ 冷钱包(WebView嵌入)

阶段2 (2026-07): 业务解耦，Node独立
  Node = 纯Web3自管钱包App
  ├ 冷钱包舱(资产看板/Swap/Faucet/收发)
  └ 服务舱(福利/保险库/DID通行证)

阶段3 (2026-07 至今): Aeon R9 集成，5 Tab 形态成型
  Node 5 Tab 架构
  ├ Tab1 钱包(资产操作)
  ├ Tab2 团队(Aeon R9 关系网络落点)
  ├ Tab3 交易/商城(统一商品池+级差返利)
  ├ Tab4 应用中心(第三方应用分发)
  └ Tab5 身份(Web3身份的权益与凭证)

阶段4 (未来): Node作为签名基础设施
  外部应用 → 连接Node → 签名登录 → 返回Proof
```

## 3. 模块一：钱包（Tab 1）

### 3.1 定位

面向 C 端用户的链上资产管理入口，参考主流 Web3 钱包（MetaMask/Phantom/Trust Wallet/Rainbow/Coinbase Wallet）设计惯例，**Tab 1 保持纯粹，不引入任何业务/关系/推广逻辑**。

### 3.2 功能清单

| 子模块 | 功能 | 状态 | 优先级 |
|---|---|---|---|
| 资产看板 | 总估值 + 代币列表（RC/USDRs/HRCs/RSTs） | 原型完成 | P1 |
| Swap 兑换 | 自主链代币两两兑换 + 滑点控制 + 智能路由 | 原型完成，联调中 | P1 |
| Faucet 领取 | 每 24h 领 5 RC，Gas 不足平台代发（EIP-2771） | 原型完成，联调中 | P1 |
| 币种详情 | 余额 + 操作入口 + 价格走势 + 交易记录 | 原型完成 | P2 |
| 发送/接收 | 链上转账 | 占位 | P2 |
| 钱包管理 | 创建/导入/重命名/导出私钥/销毁注销 | 原型完成 | P1 |

### 3.3 代币体系

| 符号 | 名称 | 链 | 用途 |
|---|---|---|---|
| RC | RC Token | 自主链 | Gas 原生代币，Faucet 领取对象 |
| USDRs | USDR Stable | 自主链 | 平台主要代币，空投/返利币种 |
| HRCs | HRC Token | 自主链 | 生态联合 Token |
| RSTs | RST Token | 自主链 | 储备代币 |

### 3.4 核心技术方案

#### 3.4.1 Swap 兑换

- **自建 AMM 流动性池**：恒定乘积公式 `x * y = k`
- **两代路由**：直连 + USDRs 中转
- **滑点保护**：前端算 `MinAmountOut` + 合约级 `INSUFFICIENT_OUTPUT_AMOUNT` 校验
- **滑点档位**：4 档可选（0.1% / 0.5% / 1% / 3%）

#### 3.4.2 免 Gas Faucet

- **EIP-2771 元交易**：用户签名，Relayer 代付 Gas 提交
- **兼容普通 EOA 钱包**：无需合约钱包改造
- **防刷三重机制**：设备指纹排他 + IP 频次限制 + nonce 防重放
- **资金池**：50,000 RC，每地址每 24h 领 5 RC

#### 3.4.3 社区制 Faucet（v2.0 新增，对应评审 P0-6）

在基础 Faucet 之上叠加社区制任务激励：

| 维度 | 规则 |
|---|---|
| 基础领取 | 每 24h 领 5 RC 保留（新用户入门保障） |
| 任务发布方 | 首期仅平台 + 代理（rank≥3）可发布，普通用户仅接受任务 |
| 首期任务类型 | 地推类（邀请绑定）+ 体验类（首次 Swap/绑定短号/激活保险库） |
| 奖励来源 | 平台任务走 Gas Tank；代理任务走代理预算（需锁定押金 50 USDT） |
| 奖励代币 | RC（与基础 Faucet 一致，避免与购买返佣积分双算） |
| 防伪 | 首期仅做链上可验证任务（地推绑定/首次 Swap），链下任务后续再上 |

#### 3.4.4 Swap 白名单（对应评审 P0-7）

采用双维度白名单（团队等级 rank OR 持仓门槛），平衡风控与用户准入：

| Swap 操作 | 白名单要求 | 理由 |
|---|---|---|
| RC ↔ USDRs（同链基础） | 无白名单 | 入门级，新用户必备 |
| USDT ↔ USDRs（跨链入金） | 无白名单 | 入金主通道，不应设卡 |
| HRCs 相关 Swap | rank≥3 | 生态联合 Token，需生态贡献门槛 |
| 大额 Swap（≥1000 USDT 等值） | rank≥5 OR 持仓≥5000 USDR | 防风控 + 反洗钱 |
| 超大额 Swap（≥10000 USDT 等值） | rank≥7 OR 持仓≥20000 USDR | 严风控 |

#### 3.4.5 跨链 Bridge（对应评审 P2-4）

- **首期**：接入 LayerZero（成熟度高、生态广）
- **远期**：自建 Bridge（降低成本、提升控制力）
- **Bridge 费率**：由用户承担

### 3.5 钱包管理

| 操作 | 说明 |
|---|---|
| 创建钱包 | 本地生成私钥，Keychain 加密存储，导出助记词备份 |
| 导入钱包 | 助记词/私钥导入，本地存储，不上云 |
| 重命名 | 修改钱包显示名（本地） |
| 导出私钥 | 输入 PIN 码后明文展示，警告用户妥善保管 |
| 销毁注销 | 清除本地私钥与缓存，链上资产需先转出 |

## 4. 模块二：团队（Tab 2）

### 4.1 定位

Aeon R9 冷钱包上下级永久绑定方案的产品落点，核心是**基于链上地址的永久上下级关系绑定 + 5 渠道归因 + 多级佣金分账 + 治理迁移**。

**三铁律**（不可破坏）：
1. **set-once**：上下级关系一次性写入，永久不可改
2. **退货不退关系**：退货只退钱，不解除绑定
3. **设备指纹校验**：绑定前必须通过 DeviceRegistry 校验

- **💎 购买靓号**：查价 + 位数筛选（5/6/7/8 位）+ 推荐列表 + 定价规则
  - 5 位基价 1000U，每多一位 ×0.9
  - 豹子 ×50 / 顺子 ×20 / 四连同 ×10 / 葫芦 ×8 / 双对 ×5 / 吉尾 ×3
- **🎁 免费号**：随机生成 10 个 10-12 位候选号 + 换一批 + 领取选中号（每个身份仅可免费领取 1 次）

#### 4.3.4 绑定上级流程

```
1. 未加入团队的用户在初始页通过 扫码 / 搜索短号 找到上级
2. 确认上级信息后发送申请(不上链)
3. 上级在"团队申请·加我的"Tab 收到申请 → 审批(接受/拒绝)
4. 接受后可选转 gas(默认0.05可自定义/可不转)
5. 下级收到"已同意"通知 → 申请进度页直接展示确认详情
6. 下级点击"确认加入" → 拉起 PIN 码签名 → EIP-712 离线签名
7. 设备指纹绑定 + 关系绑定一起上链完成 → 进入团队主页
```

**关键约束**：
- 设备指纹绑定与上下级关系绑定在上链确认时同步完成，不再前置检测
- 邀请能力需通过白名单验证（点击二维码/邀请/团队申请时触发）
- 团队申请页采用双 Tab 设计（"我邀请的"和"加我的"）
- 上级接受申请时可选择是否转 gas（默认不发送）

#### 4.6.2 返佣模型（级差制）

**等级 vs 层级**（严格区分，不可混淆）：

| 维度 | 含义 | 范围 |
|---|---|---|
| 等级 rank | 横向：以自己为起点的"团队级别" | L1..L10 |
| 层级 layer | 纵向：单个订单里沿上线链的深度位 | +1/+2/+3 |

**派发规则**：每层返利按该层上线"自己的等级"取 `rebateBps[rank][layer]`，不受下游等级影响。

**返佣分账比例**：L1 20% / L2 14% / L3 10% + 7/6 + 2（待财务确认）

#### 4.6.3 返佣时间期限（对应评审 P0-3、P0-4）

**默认冻结期：7 天**（确认收货后 7 天内佣金处于 pending，不可领）

**高价商品分级**：

| 商品价格 | 冻结期 |
|---|---|
| 单价 < 500 USDT | 7 天 |
| 500 USDT ≤ 单价 < 2000 USDT | 14 天 |
| 单价 ≥ 2000 USDT | 30 天 |

**确认收货上链机制**：

1. **买家主动确认**：买家调 `GoodsMarket.confirmReceive(refId)`，触发佣金 `releaseTime` 开始计时
2. **自动确认兜底**：发货后 15 天未确认，系统自动确认（keeper 或 miner 手动触发 `autoConfirmReceive`）
3. **虚拟商品**：发货即确认（无物流，立即开始冻结计时）

**等级权益**：rank≥5 代理可申请"提前结算"作为等级权益（miner 审核后缩短冻结期）。

#### 4.6.4 烧断机制（对应评审 P0-1、P0-2、P2-1、P2-2，建议方案待定）

> **重要说明**：当前 `AgentReward` 合约实际只有 `compression` 动态压缩机制（跳过 `level=0` 的未达标上线，名额上卷），**没有"上层 rank 小于下层 rank 触发烧断"的逻辑**。烧断机制属于评审建议方案，是否在合约层扩展实现待团队确认。

**烧断定义（建议方案）**：上层 rank 小于下层 rank 时触发烧断（弱上级吃强下级）。

**烧断佣金去向（B+D 组合，建议方案）**：

1. 沿 E 链向上找第一个 `rank ≥ 触发烧断的下层 rank` 的上线 → 上卷发放
2. 若 `maxBurnSkips`（默认 10 步）内找不到合格者 → 等值转化为 `AgentPoints` 铸给**被烧断的下级**（即买单的实际推广者），作为补偿
3. 资金不流出生态（不进 treasury、不进黑洞）

**layer1 兜底（建议方案）**：

- `burnStartLayer = 2`（即 layer1 永远不烧断）
- 直推上级无论 rank 高低，都拿 layer1 返佣
- layer2、layer3 才进入烧断检查

**可配置性（建议方案）**：

- `AgentLevel` 新增 `burnEnabled`（bool，默认 false）和 `burnStartLayer`（uint8，默认 2）
- miner 可通过 `setBurnEnabled(bool)` 和 `setBurnStartLayer(uint8)` 调整
- 部署时默认关闭，运营评估后开启

**与 compression 共存（建议方案）**：

- 先 compression（跳过 rank=0）
- 再烧断检查（rank<下层 rank）
- 两者独立配置，互不影响

**当前合约实际行为**（仅 compression）：
- 某层上线 `level=0` → 跳过，名额上卷给上面下一个合格上线
- `maxCompressionSkips = 20`（默认，硬上限 100，防 gas 爆炸）
- **不会因"上层 rank < 下层 rank"触发任何特殊处理**

## 5. 模块三：交易/商城（Tab 3）

### 5.1 定位

**统一商品池 + 级差返利** 的 Web3 商城：所有用户共享同一商品池，购买行为触发沿上线链 N 层级差分润，等级决定返利比例。

> **三大核心决策**（对齐合约基准）：
>
> | 决策 | 含义 | 产品影响 |
> |---|---|---|
> | **仅官方上架** | 矿工统一上架商品、统一定价、统一管库存 | 无 C 端商家入驻流程 |
> | **全平台统一商品池** | 所有用户看到同一商品池、同一价格 | 无代理层级商品池概念 |
> | **取消代销概念** | 无代销、无 Z 价、无上下级库存调拨 | 商品详情页仅"立即购买" |

### 5.2 设计哲学

| 哲学 | 体现 |
|---|---|
| 等级唯一 | `level[addr]` 0..10，无"个人等级/团队等级"之分 |
| 积分双轨 | 个人积分（basis=0）/ 团队积分（basis=1），逐级配置 |
| 自身达标 | A 是 L10 不会抬高上线等级，普众公平 |
| 动态压缩 | 未达标上线跳过、名额上卷，避免名额浪费 |
| 普众参与 | rank=0 也可购买，仅影响"自己作为上线时是否合格" |

### 5.3 用户角色

| 角色 | E 链绑定 | rank | 核心权限 | 入口限制 |
|---|---|---|---|---|
| **游客** | ❌ 未绑定 | - | 浏览 + 购买（首次购买触发归因绑定） | 无代理中心 |
| **买家** | ✅ 已绑定 | 0 | 浏览 + 购买 + 订单 + 持有码 | 无代理中心 |
| **代理** | ✅ 已绑定 | 1..10 | 买家全部 + 代理中心 + 返利 + 升级 | 全功能 |

> 矿工视角属于后台运营系统（r9-admin），不在 C 端原型展示。

**关键概念澄清**：

| 概念 | 符号 | 范围 | 含义 | 决定 |
|---|---|---|---|---|
| **等级 rank** | L1..L10 | 个人 | 代理级别，每个人独立 | 返利比例 |
| **层级 layer** | L1/L2/L3 | 订单 | 沿上线链的深度位 | 分润深度位 |

> 关系链中 L3a 等级可以大于 L2a（兄弟节点等级倒挂），完全合法、符合设计预期。

### 5.4 商品模型

#### 5.4.1 商品类型分类

| 类型 | pointsPerUnit | feedTeamPoints | secretCode | 典型场景 |
|---|---|---|---|---|
| **实物商品** | 0 | false | false | 硬件设备 |
| **虚拟商品** | 0 | false | true | 卡密/激活码 |
| **级别服务商品** | >0 | true | false | 升级服务包 |
| **积分商品** | >0 | false | false | 纯积分包 |

#### 5.4.2 商品定价规则

- **多币定价**：`price[productId][token]`，0 表示不接受该币
- **统一价**：全平台同价，不分代理层级
- **数量折扣阶梯**：`tiers[]=(minQty, bps)`
  - bps = 支付原价比例（7000=70%、6000=60%）
  - 取满足条件的最高 minQty 那档
  - 默认 10000=原价

#### 5.4.3 保密商品（secretCode）

- 商品级开关，开启后：
  - 链上仅存哈希，**绝不上链明文卡密**（攻击者扫描历史 calldata 无法还原）
  - 真实卡密由链下数据库管理
  - 购买后用户凭订单 refId 调链下 API 领取
- 业务场景：高价值卡密、激活码

#### 5.4.4 直写奖励（rewards[]）

商品可配置直写奖励，给买家自身（独立于上线返利）：

| 模式 | 含义 | 示例 |
|---|---|---|
| mode 0 | 固定金额 × qty | 买硬件送 100 USDR/件 |
| mode 1 | 按成交价比例 bps | 买会员返 5% USDR |

> **配置不可单独删除**：只能 `clearRewardCfg` 清空全部，再重新配置。

### 5.5 唯一码库存模型

#### 5.5.1 状态机

```
0 未设 (unset) → 1 可售 (available) → 2 已售 (sold) → 3 已退 (returned)
```

**关键约束**：
- 500 库存 = 500 个唯一码
- 退货后状态变 3，**永久作废**（合约无重置方法）
- 已退码无法再次导入销售
- `productCodes` 视图仅返回可售码列表

#### 5.5.2 关键方法

| 方法 | 谁可调 | 功能 |
|---|---|---|
| `importCodes(productId, bytes32[])` | 仅 miner | 批量导入唯一码 |
| `availableStock(productId)` | 所有人 | 查询可售库存数量 |
| `productCodes(productId)` | 所有人/受限 | 查询可售码列表；保密商品仅 miner 可读 |
| `myCodes()` | 所有人(本人) | 查询自己的持有码 |
| `ownedCodesOf(addr)` | gated：仅本人或 miner | 查询某地址的持有码 |
| `orderCodes(refId)` | 所有人 | 查询某订单包含的码列表 |
| `codeStatus(codeId)` | 所有人 | 查询单个码状态 |
| `codeOwner(codeId)` | 所有人 | 查询码当前持有人 |
| `quote(productId, qty, payToken)` | 所有人 | 预览总价（返回 gross + net） |

### 5.6 购买流程

#### 5.6.1 单次购买的数据流（合约层）

```
用户 buyer.buy(productId, qty, payToken)
   │
   ├─① 校验序列：
   │   ├─ 黑名单校验 !banned[msg.sender]
   │   ├─ 白名单校验（whitelistEnabled 时 whitelist[msg.sender]）
   │   ├─ 商品存在且上架 p.exists && p.active
   │   ├─ MOQ 校验 qty > 0 && qty >= p.minOrderQty
   │   ├─ 币种校验 price[productId][payToken] > 0
   │   └─ 库存校验 avail.length >= qty
   ├─①b 阶梯折扣算价：gross = unit * qty；net = gross * tierBps / 10000
   ├─①c transferFrom 收款到 GoodsMarket 合约本身
   ├─①d 订单生成：refId = keccak256(abi.encode(block.chainid, productId, orderCounter++))
   ├─② 从唯一码台账分配 qty 个码给 buyer（codeStatus: 1→2）
   ├─③ 若商品配 rewards[] → 逐条 RewardClaim.addReward(buyer) // 买家自身奖励（⚠️ 无 try/catch，失败则整单 revert）
   ├─④ 若 pointsPerUnit > 0 → AgentPoints.mint(buyer, points) // 升级燃料（try/catch）
   │     └─ feedTeamPoints=true → AgentLevel.recordPoints() // 沿 E 链 teamDepth 层累加团队积分（try/catch）
   └─⑤ AgentReward.onPurchase(buyer, productId, gross, net, payToken, refId)
         └─ 整体被 buy 的 try/catch 包裹，失败仅 emit RebateHookFailed
         └─ 沿 ReferralRegistry(E) 上线链取 N 层（默认3层）
              └─ 每层按"该层上线自身等级"查 rebateBps[rank][layer]
              └─ compression 开：跳过 level=0 的未达标上线，名额上卷
              └─ 逐层 RewardClaim.addReward(agent, rebate)
```

#### 5.6.2 韧性设计差异（重要）

| 钩子 | 失败处理 | 失败后果 |
|---|---|---|
| 直写奖励（rewards[]） | **无 try/catch** | addReward revert → buy 整单 revert → 购买失败 |
| AgentPoints.mint | try/catch | 主交易成功，仅积分未发 |
| AgentLevel.recordPoints | try/catch | 主交易成功，仅团队积分未累加 |
| AgentReward.onPurchase | **整体被 buy 的 try/catch 包裹** + emit RebateHookFailed | 主交易成功，仅返利未发 |

#### 5.6.3 购买前置操作

1. **授权**：买家先调 `IERC20.approve(GoodsMarket, amount)` 授权代币
2. **预览**：调 `quote(productId, qty, payToken)` 预览总价
3. **绑定检查**（前端）：查询 `referrerOf(buyer)`
   - 未绑定：结算页提示"本次购买将触发归因绑定到邀请人"
   - 已绑定：结算页展示上线链 + 返利预览

### 5.7 级差返利体系

#### 5.7.1 两个维度（核心）

| 维度 | 方向 | 范围 | 决定 |
|---|---|---|---|
| **等级 rank** | 横向（个人） | 0..10 | 返利比例 `rebateBps[rank][layer]` |
| **层级 layer** | 纵向（订单） | 1..rebateLayers | 分润深度位 |

#### 5.7.2 返利矩阵示例（rank × layer）

| rank | L1 返利 | L2 返利 | L3 返利 |
|---|---|---|---|
| 1 | 15.0% | 8.0% | 2.0% |
| 5 | 19.0% | 10.0% | 3.0% |
| 10 | 25.0% | 13.0% | 5.0% |

**配置规则**：
- 单元上限 10000 bps = 100%
- 建议**高 rank 行 ≥ 低 rank 行**
- `rebateLayers` 默认 3，硬上限 `MAX_REBATE_LAYERS=10`
- `basis`：0=原价 gross（默认）/ 1=成交价 net

#### 5.7.3 动态压缩（compression）

- **开**（默认）：某层上线 `level=0`（未达标/未激活）→ 跳过，名额上卷给上面下一个合格上线
- **关**：该层作废（浪费一个名额）
- `maxCompressionSkips = 20`（默认，硬上限 100，防 gas 爆炸）

**场景示例**：
```
买家 X 购买 100U 商品，上线链：
  ├─ L1 张三 rank=0 → ❌ 跳过(compression)
  ├─ L2 李四 rank=3 → ✅ 拿 L1 份额(上卷，按李四 rank3 取 layer1 比例 = 17%)
  └─ L3 王五 rank=5 → ✅ 拿 L2 份额(上卷，按王五 rank5 取 layer2 比例 = 10%)
```

#### 5.7.4 多币路由

- 每个支付币种部署一份独立 RewardClaim 实例（单币）
- `AgentReward.claimFor[payToken]` 路由到对应实例
- 返利与支付同币、精度一致

#### 5.7.5 安全护栏

| 护栏 | 字段 | 默认值 | 作用 |
|---|---|---|---|
| `minRebate` | 去尘阈值 | 0 | 低于此值不发，省 gas |
| `maxRebatePerLayer` | 单层封顶 | 0(不限) | 防异常大额 |
| `maxTotalPerOrder` | 整单池封顶 | 0(不限) | 防资金异常 |
| `maxCompressionSkips` | 压缩上卷步数 | 20 | 防 gas 爆炸 |

### 5.8 等级与升级体系

#### 5.8.1 等级字段

- 等级 0：未达标代理（无返利资格）
- 等级 1..10：合格代理（按 rank 取 rebateBps）
- **等级是状态**，积分是累积量

#### 5.8.2 升级燃料（双轨积分）

| 积分 | 合约 | 来源 | 用途 |
|---|---|---|---|
| **个人积分** | AgentPoints (Soulbound ERC20, decimals=6) | GoodsMarket 购买时 mint / miner 手动 mint | basis=0 时作判据 |
| **团队积分** | AgentLevel.teamPoints | recordPoints 沿 E 链 teamDepth 层累加（含本人） | basis=1 时作判据 |

**AgentPoints 特性**：
- Soulbound：transfer/approve 全 revert
- mint/burn 按 refId 幂等
- decimals=6（1.5 积分 = 链上 1500000）

#### 5.8.3 升级门槛（双基准）

| level | threshold | basis | 含义 |
|---|---|---|---|
| 1 | 100 | 0 | 100 个人积分 |
| 2 | 500 | 0 | 500 个人积分 |
| 3 | 1000 | 1 | 1000 团队积分（开始需要团队） |
| 5 | 20000 | 1 | 20000 团队积分 |
| 10 | 1000000 | 1 | 100 万团队积分 |

**设计哲学**：低级（1-2）个人达标，高级（3-10）团队达标（防光杆司令）。

#### 5.8.4 升级流程

```
1. 用户 requestUpgrade(targetLevel)
   ├─ 校验 targetLevel > 当前 level 且 ≤ MAX_LEVEL
   ├─ 取目标级 basis:thresholdBasis[targetLevel]
   ├─ 按 basis 取当前 metric（个人积分或团队积分）
   └─ 快照 metric + basis 入队 UpgradeRequest

2. miner 审核队列
   ├─ 凭快照判断(可信任)
   └─ 或调当前值判断(更严格)

3. miner approveUpgrade(id, enforceThreshold)
   ├─ enforceThreshold=true: 强制链上校验当前 metric >= threshold
   ├─ enforceThreshold=false: 信任 miner 链下审核
   └─ level[user] = targetLevel

4. 或 miner minerSetLevel(user, level) 直接设定
   └─ 用于购买级别服务商品审核 / 手动补录
```

#### 5.8.5 关键约束

- **团队积分不回退**：合约层没有扣减 teamPoints 的方法，退货时不会自动扣减，已累计的永久保留
- **等级不自动降级**：等级只能通过 `minerSetLevel` 手动调整，即使后续积分低于门槛也不会自动降级
- **快照防作弊**：申请时快照 metric，miner 审核期间积分波动也能凭快照判断

### 5.9 奖励领取体系（RewardClaim）

#### 5.9.1 额度制模型

- 用户随时自领（claim）
- **无中继、无 miner 手动发放**
- 单币实例：构造锁定一个 `token`
- `claimable = allocation - claimedAmount`

#### 5.9.2 两类撤销

| 撤销类型 | 方法 | 场景 | 行为 |
|---|---|---|---|
| **未领撤销** | `revokeReward(refId)` | 活动到期/防刷单 | 只回收未领部分，已领动不了 |
| **已领退回** | `returnReward(refId, amount)` | 退货退款前置 | 用户主动转回已领奖励币，可分多次部分退回 |

#### 5.9.3 预算护栏与偿付校验

- `addReward` 内置偿付校验：合约必须已充值到能覆盖全部未领额度，否则拒绝写入（`RC: underfunded`）
- `rescue(amount)` 仅能提走"余额 - 未领额度"的盈余，动不了用户应得

### 5.10 退货流程

#### 5.10.1 完整流程

```
1. 买家 returnRequest(refId, codeId)
   ├─ 校验 o.exists && !o.returned
   ├─ 校验 o.buyer == msg.sender
   ├─ 校验 codeOwner[codeId] == msg.sender && codeProduct[codeId] == o.productId
   └─ 创建 ReturnReq 入队

2. 买家前置（业务流程要求）: 若已领奖励，先 returnReward(refId, amount)
   ├─ 需先 approve RewardClaim 合约
   └─ 调 RewardClaim.returnReward(refId, amount) 转回已领奖励币

3. miner 审核 getReturnRequest(id)
   ├─ 业务责任：先检查 returnReward 状态，确认已领奖励已退回
   └─ 决定 approveReturn 或 rejectReturn

4. miner approveReturn(id, refundAmount)
   ├─ r.open = false（先标记关闭）
   ├─ o.returned = true（先标记整单已退）
   ├─ try agentReward.revokeOrder(r.refId) {} catch {}（try/catch 保护）
   │   └─ revokeOrder 内逐层 try/catch RewardClaim.revokeReward
   ├─ 回收唯一码（codeStatus: 2→3, codeOwner 清空）
   ├─ 退款 transfer 到买家（refundAmount > 0 时；= 0 时跳过 transfer）
   └─ emit ReturnApproved

5. 或 miner rejectReturn(id)
   └─ emit ReturnRejected
```

#### 5.10.2 P0 漏洞：直写奖励在退货时无法自动撤销（严重）

**合约事实**：
- 直写奖励的 `directRefId = keccak256(abi.encode(refId, 82, i))`，其中 `i` 是 rewards[] 数组下标
- 该 `directRefId` 只传给 RewardClaim.addReward，不会写入 `AgentReward._orderRefIds`
- `approveReturn` 只调 `agentReward.revokeOrder(refId)`，遍历的是 `_orderRefIds[refId]`（仅级差返利的 layerRefId）
- **直写奖励完全不会被撤销** → 买家仍可领走该直写奖励 → 项目资金流失

**P0 级修复方案（矿工后台硬性流程，前端硬编码、不可跳过）**：

```
1. 查商品配置：rewardsOf(productId) 拿到所有 RewardCfg.claim 实例地址
2. 对每条配置计算 directRefId = keccak256(abi.encode(refId, uint8(82), i))
3. 查每条直写奖励状态：RewardClaim(claim).rewards(directRefId)
   ├─ 已 revoked=true → 跳过
   ├─ 未 revoked 且 returnedAmount < amount → 需处理
4. 对未撤销的直写奖励，尝试 revokeReward：
   ├─ 若 unclaimed >= amount → 调 RewardClaim(claim).revokeReward(directRefId) 强制撤销
   └─ 若 unclaimed < amount（用户已 claim 部分/全部）→ 必须 returnReward（用户主动退回）
       ├─ 用户不配合 → 禁用 approveReturn 按钮，转人工处理
       └─ 用户 returnReward 后 → 校验 returnedAmount >= amount → 解禁 approveReturn
5. 所有直写奖励均 revoked=true 或 returnedAmount>=amount → 才允许 approveReturn
```

#### 5.10.3 P1 漏洞：approveReturn 不校验奖励已退回状态

**合约事实**：
- `approveReturn` 完全没有校验 `RewardClaim.rewards[refId].returnedAmount`
- 完全没有校验 `RewardClaim.rewards[refId].revoked`
- 直接执行 `transfer(r.buyer, refundAmount)`
- `revokeOrder` 内部对 `revokeReward` 的 try/catch 失败被吞，approveReturn 继续执行退款
- **用户既拿奖励又拿退款，合约层完全不阻止**

**P1 级修复方案（r9-admin 前端硬编码校验）**：

```typescript
// 矿工审核退货前的强制校验逻辑
async function canApproveReturn(refId, productId) {
  // 1. 校验级差返利是否已撤销/已退回
  const layerRefIds = await agentReward.orderRefIdsOf(refId);
  for (const layerRefId of layerRefIds) {
    const r = await rewardClaim.rewards(layerRefId);
    if (!r.revoked && r.returnedAmount < r.amount) {
      return { ok: false, reason: `上线返利 ${layerRefId} 未退回` };
    }
  }
  // 2. 校验直写奖励是否已撤销/已退回（见 P0 漏洞）
  const rewardCfgs = await goodsMarket.rewardsOf(productId);
  for (let i = 0; i < rewardCfgs.length; i++) {
    const directRefId = keccak256(encodePacked(refId, 82, i));
    const r = await RewardClaim(rewardCfgs[i].claim).rewards(directRefId);
    if (r.user !== ZeroAddress && !r.revoked && r.returnedAmount < r.amount) {
      return { ok: false, reason: `直写奖励 #${i} 未退回` };
    }
  }
  return { ok: true };
}

// 矿工界面按钮状态
<Button disabled={!canApproveReturn.ok} onClick={approveReturn}>
  {canApproveReturn.ok ? '同意退货' : `阻止：${canApproveReturn.reason}`}
</Button>
```

#### 5.10.4 部分退货的严重限制（重要）

> **合约层 `returnRequest` 只支持单码退货，且 approveReturn 后整个订单标记为 `returned=true`，后续其他码无法再申请退货。**

**实际行为**：
- 买家可以批量 `returnRequest` 多个码入队
- 但只要 miner 审核通过一个 `approveReturn`，整个订单标记为 returned
- 后续其他码的 `returnRequest` 会因 `!o.returned` 校验失败而 revert
- **实际只能退一个码**

**推荐方案 A：整单退 + 重新买剩余**：
1. 矿工 approveReturn 整单退款
2. 买家重新购买剩余 qty-1 件
3. 钱货两清后重新发码

**绝对禁止**：
- ❌ 前端不要提供"部分退货"按钮（即使合约层有 returnRequest）
- ❌ 不要尝试通过多次 returnRequest + 多次 approveReturn 实现部分退货（合约已禁此路径）

#### 5.10.5 关键约束

- **"已领奖励必须先退回"是业务流程要求，非合约硬条件**：合约层 `approveReturn` 不校验，依赖 miner 审核责任
- **approveReturn 隐藏行为**：`r.open = false` 和 `o.returned = true` 在 `revokeOrder` 之前设置，即使 revokeOrder 失败也标记为已退
- **关系不变**：E 链 referrerOf 永久，退货不退关系
- **码状态变 3**：退货后永久作废，合约无重置方法，无法再次 importCodes
- **refundAmount 由 miner 决定**：合约不校验金额合理性，可以是 0、部分、全额、超额，矿工责任重大
- **refundAmount 来源**：从 GoodsMarket 合约余额中转给买家（非 treasury）

### 5.11 二手转卖市场（GoodsMarket 内）

#### 5.11.1 转卖两种方式

| 方式 | 方法 | 是否收费 | 场景 |
|---|---|---|---|
| **直转** | `transferItem(codeId, to)` | ❌ 不收费 | 赠送 / 私下交易 |
| **挂单** | `listItem(codeId, payToken, price)` + `buyListed(codeId)` | ✅ 收取 `resaleFeeBps` | 公开二手市场 |

> 注：`GoodsMarket.listItem` 为早期实现，新挂单推荐走独立的 `FixedPriceMarket` 渠道合约（见 [7.7 流转市场](#77-流转市场)）。GoodsMarket 内的二手转卖仅作为基础能力保留。

#### 5.11.2 关键特性

- **不触发分润**：转卖不走 `AgentReward.onPurchase`，沿 E 链不分润
- **不触发归因**：转卖不调 bindOnPurchase，关系不变
- **手续费可配**：`resaleFeeBps` 逐商品配置（如 500=5%）
- **自由定价**：卖家自定价格，无区间限制
- **多币支持**：挂单时指定 `payToken`

#### 5.11.3 转卖前置操作与限制

**transferItem 限制**：
- 不能转挂单中的码（合约校验 `!listings[codeId].active`）
- 必须先 `cancelListing` 才能转赠
- 已退货的码（codeStatus=3）无法转赠

**buyListed 限制**：
- 卖家不能自买（`msg.sender != l.seller`）
- 挂单信息与码所有权必须一致（`codeOwner[codeId] == l.seller`）

### 5.12 订单状态设计

#### 5.12.1 主辅分离架构

**设计原则**：
1. **合约是真相源**：用户可见状态由合约态派生，不发明合约不存在的状态
2. **主辅分离**：主状态（合约派生 4 态）+ 辅助态（链下物流/卡密），组合呈现给用户
3. **不混淆**：物流、卡密领取等纯链下流程作为独立扩展字段，不污染主状态
4. **无待付款**：合约 buy 是原子收款，不存在"待付款"状态

**主状态 4 态**（由合约派生）：

| 主状态 | 合约条件 | 触发 | 是否终态 |
|---|---|---|---|
| `created` | exists=true, returned=false, 无 open ReturnReq | Purchased 事件 | 否 |
| `return_requested` | exists=true, returned=false, 有 open ReturnReq | ReturnRequested 事件 | 否 |
| `returned` | returned=true | ReturnApproved 事件 | **是，不可逆** |
| `return_rejected` | exists=true, returned=false, 有已关闭 ReturnReq 且非 approved | ReturnRejected 事件 | 否（可再申请） |

**辅助状态**（链下业务态，独立字段）：
- 实物：`fulfillmentStatus` = pending_shipment → shipped → delivered
- 虚拟：`redeemStatus` = pending_redeem → redeemed
- 服务/积分：直接生效（无需辅助状态）

## 6. 模块四：应用中心（Tab 4）

### 6.1 定位

**第三方应用分发与平台抽成的商业化载体**。把 Node 钱包的用户流量转化为 App 分发收入。

**核心商业逻辑**：合作方（开发者/商家/服务商）将 App 上架到商城，用户通过商城进入/下载/连接这些 App，平台从中抽取佣金。**不涉及分销/上下级绑定，纯平台抽成模式**。

### 6.2 与 Tab 3 商城的边界

| 维度 | Tab 3 商品商城 | Tab 4 应用市场 |
|---|---|---|
| **标的物** | 实物/虚拟/服务商品（单次交易） | 第三方应用（持续分发） |
| **上架方** | 矿工（仅官方上架，无 C 端商家入驻流程） | 合作方（开发者/商家，无分销关系） |
| **归因机制** | bindOnPurchase 成交型永久绑定 | 平台抽成，不绑定上下级 |
| **佣金流向** | L1/L2/L3 多级分账 | 平台单方抽成（无分销链路） |
| **结算周期** | 成交即结算 | 周期结算（T+7/T+30） |
| **典型品类** | 硬件钥匙/权益包/服务包 | IM/跨境电商/Web3 DApp |

> **对齐基准**：Tab 3 商城上架方为 `onlyMiner`（`GoodsMarket.createProduct` / `updateProduct` / `setPrice` / `importCodes` 等全部仅 miner 可调），与 5.1 节"仅官方上架"决策一致。Tab 4 应用市场的合作方上架走独立的 App 上架申请流程，不参与 E 链分销体系。

### 6.3 MVP 信息架构

```

### 6.4 iOS / Android 平台差异

| 差异点 | iOS 实现 | Android 实现 |
|---|---|---|
| **应用分发能力** | 只能跳转 App Store（欧盟 DMA 侧载除外），不能分发 APK | 可直接分发 APK / 走 Google Play / 国内商店 |
| **深链协议** | Universal Links | App Links |
| **"打开"按钮逻辑** | 检测 Universal Link，失败跳 App Store | 检测 App Link，失败跳下载页/APK |
| **"我的应用"检测** | 无法检测，仅显示打开历史 | 可通过 PackageManager 查已装列表（MVP 统一用历史） |
| **DApp 浏览器** | 跳系统浏览器或 Tab1 浏览器 | 可内嵌 WebView（但 MVP 统一走跳转） |

> iOS 上 Tab4 退化为"应用导航站 + DApp 收录"，Android 上才是真正的"应用市场"。MVP 阶段两端 UI 一致，差异仅在跳转逻辑。

### 6.5 DApp 收录导航模式

### 7.3 福利特权

#### 7.3.1 定位

C 端用户的权益领取与消费入口，围绕钱包地址提供空投、资产权益、互动激励等运营场景。

#### 7.3.2 福利分类体系（对应评审 P1-3）

**双层结构**：

| 层级 | 分类 | 说明 |

**映射关系**：
- 空投 → airdrop
- 资产 → rebate + ecology + vip

一个福利方案可对应多个奖励合约（跨链/分批发放），支持单个合约手动领取 + 一键领取全部。

#### 7.3.5 钱包绑定校验

进入福利特权前检测钱包是否已绑定，未绑定则弹窗引导。

### 7.4 安全保险库（Vault）

#### 7.4.1 定位

高安全等级资产托管与鉴权框架，核心解决女巫攻击（批量注册薅羊毛）。**升级为全 App 安全基座**，向 Tab 1/2/3 暴露校验接口。

#### 7.4.2 核心价值三要素

1. **物理级防刷**：一台物理设备同一时刻只能绑定一个钱包
2. **用户隐私合规**：设备 ID 本地哈希加密，不上传 IMEI/MAC 原始数据
3. **作弊成本倒逼**：已激活指纹解绑需付 500 USDT，使作弊成本远超收益

#### 7.4.3 两阶段生命周期

| 指纹状态 | 触发条件 | 链上状态 | 解绑规则 |
|---|---|---|---|
| 待激活 | 完成本地签名向导 | 本地存根（未上链） | 免费，无冷却 |
| 已激活 | 首次领福利成功 | 广播存证（已上链） | 付费 500 USDT |

#### 7.4.4 钥匙等级体系（三阶段演进）

| 等级 | 钥匙类型 | 状态 |

| L1 | 设备指纹钥匙（当前） | 开发完成 |

### 7.5 数字身份通行证（DID Pass）

#### 7.5.1 定位

全屏管理子页面，由服务舱卡片拉起，提供多重身份的一站式管理。

#### 7.5.2 两层结构

1. **App 列表页（身份凭证中心）**：按应用维度展示已关联的数字身份概览
2. **App 身份管理页**：Tab 切换（Web3 钱包 / Web2 账号）+ 筛选（网络/类型）

#### 7.5.3 身份类型

| 类型 | 说明 | 存储位置 |
|---|---|---|
| Web3 钱包 | 多链自管钱包地址 | 本地 Keychain + 链上 |
| Web2 账号 | 手机号/邮箱/系统账号 | 仅本地 Keychain |

#### 7.5.4 关键约束

- 云端和数据库**绝不存储**"钱包地址与 Web2 账号"的映射关系
- 断开 Web2 凭证为纯客户端操作，不涉及服务器交互
- Web3 钱包注入采用"网络选择 → 钱包选择 → 确认注入"三步流程

#### 7.5.5 外部 App 授权签名登录

```
第三方App发起挑战 → Node展示授权弹窗 → 用户选身份 → 输PIN码 →
本地私钥签名Challenge → 返回Signature Proof → 完成登录

#### 7.5.6 应用身份节点（对应评审 P1-6）

**作为 P2 远期愿景，不纳入首期规划**：
- 首期 DID 保持现有"被动授权"模式
- "应用身份节点打通"作为远期愿景，在宣讲文档中提及但不承诺落地时间
- 后续根据用户反馈和业务需求评估是否立项

### 7.7 流转市场

**定位**：用户名下所有 SKU 资产（短号 + 商品码）的二手处置中心。聚合短号、商品码两种 SKU 资产的二手转卖、拍卖、租赁、赠送场景，提供用户视角下的统一流转入口与跨渠道订单管理能力。

**入口位置**：身份 Tab（Tab 5）下，与短号中心平级，作为独立卡片。

**与既有模块的边界**：

|---|---|---|---|
| **资产生命周期阶段** | 一级发行 | 持有管理 | 二级处置 |

**挂单弹窗**：
- **一口价**：定价 + 挂单时长

**关键风控**：

- **GoodsMarket.listItem 废弃**：新挂单一律走 FixedPriceMarket 渠道合约，避免双通道挂单造成前端展示分裂

**统一台账**：所有成交写入 `TradeLedger`，链下派生跨渠道订单中心，用户在一个页面看到自己所有渠道的挂单与历史（含赠送记录）。

## 8. 合约体系与风控机制

### 8.1 核心合约清单

| 合约 | 职责 | 持币 | 依赖 |
|---|---|---|---|
| **ReferralRegistry（E）** | 永久上下级关系（set-once）+ 迁移治理 | 否 | — |
| **DeviceRegistry** | 设备指纹绑定状态（供 ReferralRegistry 校验） | 否 | — |
| **RewardClaim（G）** | 额度制奖励落地：addReward 写额度、用户自领、revoke/return 撤销；每实例单币 | 是（奖池） | — |
| **GoodsMarket（H）** | 商品/虚拟品买卖：多商品·多 TOKEN 定价·折扣·唯一码库存·转卖·退货·黑白名单·上下架 | 是（收款 treasury） | RewardClaim · AgentPoints · AgentLevel · AgentReward · E |
| **AgentPoints（新）** | 升级燃料：soulbound ERC20（decimals=6，transfer/approve 全 revert），mint/burn 仅 pointsSource | 否 | — |
| **AgentLevel（I）** | 代理等级 1..10：读 AgentPoints 作燃料、达标+miner 审核升级、持 rebateBps[rank][layer] 返利表 | 否 | AgentPoints · E |
| **AgentReward（J）** | 购买触发的返利分配：沿 E 链取 N 层、按级差制算账、直写各 RewardClaim；不持币 | 否 | E · AgentLevel · RewardClaim · GoodsMarket |
| **FixedPriceMarket** | 一口价渠道（channelId=2） | 是（收款） | ISkuRegistry · TradeLedger |
| **AuctionHouse** | 拍卖渠道（channelId=3），含 forceSettle/forceCancel/withdrawRefund | 是（收款） | ISkuRegistry · TradeLedger |
| **RentalChannel** | 租赁渠道（channelId=5），ERC-4907 使用权分离 | 否 | ISkuRegistry · TradeLedger |
| **GiftChannel** | 赠送渠道（channelId=1），即时过户 | 否 | ISkuRegistry · TradeLedger |
| **TimedExchange** | 荷兰拍渠道（channelId=4），线性定价模型 | 是（收款） | ISkuRegistry · TradeLedger |
| **TradeLedger** | 统一台账，记录所有渠道成交 | 否 | — |
| **ISkuRegistry** | SKU 资产统一抽象（skuOwner/skuActive/channelTransfer/lockSku/unlockSku） | 否 | — |

### 8.2 一次商品购买的数据流

```
用户 buyer 调 GoodsMarket.buy(productId, qty, payToken)
── 同一笔交易内 ──
1) 校验 MOQ/黑白名单/上下架 → 按折扣阶梯算价 → transferFrom 收款 → treasury
2) 从唯一识别码台账分配 qty 个码给 buyer，记账（谁买了哪些码）
3) 若商品配了购买奖励 rewards[] → 逐条 RewardClaim.addReward(buyer, amount, refId)
   // 买家自身奖励
4) 若是「级别服务商品」→ AgentPoints.mint(buyer, points, refId)
   // 给买家加升级燃料
5) 调 AgentReward.onPurchase(buyer, productId, grossPrice, netPrice, payToken, refId)
   └─ 沿 ReferralRegistry(E) 上线链取 N 层
      └─ 每层按「该层上线自身等级」查 AgentLevel.rebateBps[rank][layer]（级差制）
      └─ compression 开：跳过未达标/未激活上线，名额上卷给上面下一个合格上线
      └─ 烧断开：上层 rank < 下层 rank 时触发烧断，上卷优先 + 找不到转积分给下级
      └─ 每层 RewardClaim.addReward(agent, rebate, refId') // 上线返利

各奖励接收人自付 gas 调 RewardClaim.claim() 领取（无中继、无 miner 手动）
```

### 8.3 风控机制

#### 8.3.1 直写奖励退货撤销（硬约束）

- **矿工后台在 approveReturn 前必须**通过 `directRefId=keccak256(abi.encode(refId, 82, i))` 调用 `RewardClaim.revokeReward`
- 否则用户可领取已退货商品的直写奖励
- **approveReturn 必须校验奖励退回状态**：前端硬编码校验所有 RewardClaim 实例的 `rewards[refId].revoked` 和 `returnedAmount≥amount`，任一不满足则禁用 approveReturn 按钮

#### 8.3.2 保密商品链上存哈希+链下映射

- **禁止在链上以任何形式明文流转实际卡密**
- 防止通过扫描 importCodes 历史 calldata 获取卡密
- 链上存哈希，链下维护哈希↔卡密映射

#### 8.3.3 miner 多签钱包

- **拥有 miner 权限的地址必须使用多签钱包**
- 防止 miner 钱包被盗后通过 approveReturn 输入大额 refundAmount 抽干 GoodsMarket 合约资金

#### 8.3.4 部分退货兜底

- 买家需整单退货
- 矿工按实际件数比例通过 refundAmount 退款
- 买家重新购买剩余部分

#### 8.3.5 AgentPoints/AgentLevel 异步对账

- 后端建立异步对账任务：监听 Purchased 事件计算理论应发积分
- 检索同区块同 refId 的 Minted/PointsRecorded 事件
- 不匹配则生成告警日志提醒矿工手动补发

#### 8.3.6 刷单风控

**刷子路径**：小号买货 → 累加团队积分升级大号 → 小号整单退货（零成本刷级）

**风控措施**：
- 建立退货风控模型，限制退货率
- 驳回疑似刷单者的升级请求
- 必要时矿工可手动调 `AgentLevel.minerSetLevel` 降级关联地址

### 8.4 FixedPriceMarket 手续费

- **FixedPriceMarket 合约无 setFeeBps 函数**，手续费固定为 0%
- 其他渠道（拍卖/租赁）可配置 feeBps

### 8.5 GiftChannel 语义

- `GiftChannel.gift()` 为**即时过户**，非挂单等待买家语义
- 不纳入挂单列表

### 8.6 lockSku 跨渠道锁

- **任一渠道挂单即锁定资产**
- 防止同一资产在多渠道重复挂单

### 8.7 拍卖合约功能

拍卖合约需包含：
- `forceSettle`：强制结算（矿工处理异常）
- `forceCancel`：强制取消（矿工处理异常）
- `withdrawRefund`：提取退款（出价者撤回）

## 9. B 端配套与合规策略

### 9.1 服务管理后台

#### 9.1.1 核心原则

| 原则 | 说明 |
|---|---|
| 服务独立于产品 | 服务在注册中心统一注册，各产品按需启用 |
| 配置按产品隔离 | 同一服务在不同产品中可配置不同参数 |
| 服务元数据驱动 | 服务代码声明任务定义和参数 Schema，后台同步渲染 |
| 中心化管理 | 一套后台统一管理，产品业务服务可分实例部署 |
| 全程可审计 | 配置变更、合约参数、发币、权益变更全部留痕 |

#### 9.1.2 功能模块

1. **服务注册中心**：服务统一注册，各产品按需启用
2. **产品服务配置**：按产品隔离的服务参数配置
3. **合约与链配置**：合约地址、所属链、奖励币种管理
4. **业务参数配置**：Faucet 资金池、Swap 汇率、保险库解绑费等
5. **用户权益与标签**：用户钱包绑定状态、权益领取记录
6. **审计日志**：所有关键操作留痕
7. **权限管理**：角色 + 产品二维权限（部门维度暂不实现）

### 9.2 合规策略（对应评审 P0-8）

#### 9.2.1 国内上架策略

**国内不上架，仅海外**：

1. **国内不上架**：Node 涉及加密货币交易（Swap/Faucet/代币），不符合国内监管要求
2. **海外上架**：优先 Google Play 国际区 + App Store 国际区（美国/新加坡/香港等）
3. **国内用户访问**：通过官网下载 APK（Android）/ TestFlight（iOS）灰度
4. **区域灰度**：按 Apple/Google Web3 政策分区域开放功能
5. **合规准备**：申请新加坡 MAS 牌照或香港 SFC 牌照

#### 9.2.2 实施要点

- **主体注册**：新加坡或香港设立运营主体
- **牌照申请**：新加坡 MAS（DPT 牌照）/ 香港 SFC（Type 1）
- **上架策略**：Apple 按"Wallet"类目提交，避免"Exchange"类目（审核更严）
- **区域灰度**：按 IP/地区禁用 Swap/Faucet 功能（如中国大陆 IP 仅钱包基础功能）
- **国内分发**：官网 APK + TestFlight + 团队代理地推
- **APK 安全**：官网提供 SHA256 校验，签名验证

### 9.3 财务业务参数（待对齐）
