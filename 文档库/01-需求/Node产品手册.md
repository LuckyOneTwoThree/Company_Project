## 开篇：遇见 Node

### 一句话定位

**Node 是一个纯 Web3 自管钱包与数字通行证管理中枢**，围绕链上钱包地址，把「资产—关系—权益—身份—应用」五件事拧成一股绳。

### 我们在解决什么问题

| 痛点        | 现状                   | Node 的解法                           |
| --------- | -------------------- | ---------------------------------- |
| **资产自管难** | 私钥管理门槛高、设备绑定弱、女巫攻击频发 | 本地加密 + 设备指纹硬约束，一台设备同时刻只能绑一个钱包      |
| **关系不可信** | 推荐关系随时可改、归因不清、佣金可赖账  | 链上一次写入永久不可改，5 渠道归因裁决，佣金成交即结算       |
| **权益不流通** | 短号、商品码、卡密散落各处，处置渠道匮乏 | 统一抽象为链上资产，二级市场支持一口价 / 拍卖 / 租赁 / 赠送 |

### 产品三大铁律

1. **私钥永不上链、永不上云** —— 本地加密存储，设备指纹硬约束
2. **关系永久，迁移受限** —— 上下级一次绑定终身有效，唯一可动关系的口子是多签治理与地址迁移
3. **地址即身份** —— 算钱、绑定、鉴权只信链上地址，短号 / Web2 凭证仅作辅助

> 这三条是不可破坏的底线，所有产品决策都必须让位于它们。

## 第一章 · 产品全貌

### 1.1 五大 Tab 一级架构

Node App 由 5 个一级 Tab 构成，通过底部胶囊导航切换。**Tab 顺序**：钱包 → 团队 → 交易·商城 → 应用中心 → 身份。

> **命名约定**：全文统一使用「交易·商城（Tab 3）」，不再混用「交易」「商城」两种简称。

```
┌──────────────────────────────────────────────────────────┐
│  Tab 1: 钱包 — 纯资产操作                                  │
│   资产看板 / Swap 兑换 / 水龙头 / 收发 / 钱包管理          │
├──────────────────────────────────────────────────────────┤
│  Tab 2: 团队 — 永久关系网络                                │
│   推广中心 / 我的团队 / 邀请中心 / 佣金明细                │
├──────────────────────────────────────────────────────────┤
│  Tab 3: 交易·商城 — 统一商品池 + 级差返利                  │
│   官方商品池 / 直购下单 / 订单 / 持有码                    │
│   短号中心 / 流转市场 / 唯一码库存                         │
├──────────────────────────────────────────────────────────┤
│  Tab 4: 应用中心 — 第三方应用分发                          │
│   官方精选 / IM 社交 / 跨境电商 / Web3 类 / 我的           │
├──────────────────────────────────────────────────────────┤
│  Tab 5: 身份 — Web3 权益与凭证                             │
│   福利特权 / 保险库 / DID 通行证 / DApp 探索               │
└──────────────────────────────────────────────────────────┘
```

**为什么是这个顺序？**

- 钱包在前：用户第一诉求是「我的资产在哪」
- 团队居二：关系网络是后续所有商业逻辑的基础
- 交易居中：商业引擎，承接钱包的支付能力与团队的关系网络
- 应用中心靠后：生态扩展，不影响核心闭环
- 身份殿后：权益与凭证的聚合收口

### 1.2 三层次定位

```
┌─────────────────────────────────────────┐
│  C 端 App 层（5 Tab）                    │
│   资产管理 / 关系绑定 / 商品交易 / 应用使用 │
├─────────────────────────────────────────┤
│  B 端配套层（服务管理后台）               │
│   运营配置：商品上架 / 参数 / 权益 / 审计   │
├─────────────────────────────────────────┤
│  基础设施层（链上合约 + 链下服务）         │
│   链上：关系存证 / 商品 / 返利 / 流转      │
│   链下：数据索引 / 归因 / 中继 / 结算      │
└─────────────────────────────────────────┘
```

**关键设计**：用户只感知 C 端 App，链上链下复杂性全部屏蔽。B 端后台是运营工具，不暴露给 C 端。

### 1.3 模块协同关系

```
Tab1 钱包 ──── 提供全局钱包（购买身份 / 付款地址）────┐
                                                     │
Tab5 保险库 ─── 设备指纹校验（绑定 / 购买前置闸门）───┤
                                                     │
Tab2 团队 ──── 永久上下级关系决定级差返利分润链 ──────┤
        └── 团队积分由 Tab3 购买累加                  │
                                                     ▼
Tab3 交易·商城 ─ 购买触发返利（归因在 Tab2 完成）◄────┘
        └── 商品码作为资产可进入流转市场

Tab4 应用中心 ─── 独立抽成体系，不参与团队归因
```

**一句话理解**：钱包付钱，团队定关系，保险库管安全，三者共同支撑交易·商城的商业闭环；应用中心是独立生态，身份是权益收口。

## 第二章 · 核心商业引擎

Node 的商业闭环由六大引擎协同驱动。前五大引擎聚焦「商品池 + 关系 + 返利」的团队分润闭环；第六大引擎独立运作，承载应用生态变现。

### 2.1 引擎一：统一商品池

**传统分销商城的问题**：层级商品池导致下级看不到全平台商品、价格不透明、库存割裂。

**Node 的解法**：所有用户共享同一个官方商品池、同一个价格。

| 维度   | 传统分级商城        | Node 统一商品池 |
| ---- | ------------- | ---------- |
| 商品来源 | 各级代理自主上架      | 仅官方上架      |
| 价格   | 指导价区间，代理可自主定价 | 全平台同价      |
| 库存   | 层级调拨，库存分散     | 官方统一管理     |
| 用户所见 | 只看直推上级商品池     | 全平台统一商品池   |

**用户感知**：打开商城，所有人看到同一份商品列表、同一个价格、同一个库存。没有「我的上级卖什么」的差异感。

### 2.2 引擎二：级差返利

**核心机制**：用户购买商品后，沿其上线链向上取 3 层，按各层上线「自己的等级」派发返利。

**关键概念（必须分清）**：

| 概念           | 含义                      | 类比          |
| ------------ | ----------------------- | ----------- |
| **等级 rank**  | 每个人自己的代理级别（L1..L10）     | 你的「职级」      |
| **层级 layer** | 单笔订单里沿上线链的深度位（L1/L2/L3） | 这笔订单里你的「位置」 |

**返利规则**：

- 每层返利比例 = 该层上线「自己的等级」对应的返利比例
- L1（直接上级）比例最高，L2 次之，L3 最低
- 等级越高，返利比例越高（激励代理升级）

**举例**：买家小明购买 100U 商品，上线链为：

- L1 上级张三（等级 3）→ 拿 L1 份额，按张三等级 3 的比例返利
- L2 上级李四（等级 5）→ 拿 L2 份额，按李四等级 5 的比例返利
- L3 上级王五（等级 1）→ 拿 L3 份额，按王五等级 1 的比例返利

**关键点**：每层返利比例由该层上线「自己的等级」决定，与买家等级、与其他上线等级都无关。这保证了「普众公平」。

> **参数口径**：返利层数当前配置为 3 层（合约支持可配置，上限见规格文档）；各等级各层的具体比例矩阵属运营参数，以《Node产品规格文档》为准。

### 2.3 引擎三：永久关系

**核心机制**：上下级关系链上一次写入，永久不可改。

**5 渠道归因裁决**（按优先级从高到低）：

| 优先级 | 信号               | 场景                       | 落点        |
| --- | ---------------- | ------------------------ | --------- |
| 1   | 扫码绑定             | 当面 / 点对点扫码，可覆盖历史归因（最强信号） | 团队推广中心·扫码 |
| 2   | 主动搜索短号绑定         | 用户主动搜索上级短号发起绑定           | 团队推广中心·搜索 |
| 3   | 邀请链接 / Deep Link | 远程裂变（30 天窗口，last-touch）  | 团队邀请中心    |
| 4   | 团队申请             | 用户主动搜索短号申请加入，上级审批通过后绑定   | 团队申请中心    |
| 5   | 无有效信号            | 进孤儿池，系统自动分配              | 系统自动      |

> 团队绑定是商城购买的硬前置：用户必须通过上述 5 渠道之一完成绑定、成为买家后，才能在商城下单。

**用户感知**：绑定后永久有效不可改；退货只退钱，不解除关系；唯一可动关系的口子是地址迁移（4.2）与平台多签治理。

### 2.4 引擎四：动态压缩

**传统分销的问题**：上线不达标（等级 0）时，这层返利名额浪费，下级吃亏。

**Node 的解法**：未达标上线自动跳过，名额上卷给下一个合格上线。

**举例**：买家小明购买 100U 商品——

- L1 上级张三（等级 0，不达标）→ ❌ 跳过
- L2 上级李四（等级 3，达标）→ ✅ 接管 L1 份额
- L3 上级王五（等级 5，达标）→ ✅ 接管 L2 份额

**关键点**：返利总名额不变（始终 3 层），不合格上线被压缩跳过。这保证激励有效、名额不浪费。

### 2.5 引擎五：双积分体系

**传统分销的问题**：只看个人业绩 → 「空团长」现象。

| 积分类型     | 用途         | 获取方式            | 升级作用      |
| -------- | ---------- | --------------- | --------- |
| **个人积分** | L1→L2 升级燃料 | 购买「个人积分商品」      | 低级升级主要看个人 |
| **团队积分** | L3+ 升级燃料   | 下级购买「团队积分商品」时累加 | 高级升级必须看团队 |

**关键设计**：个人积分防「白嫖」，团队积分防「空团长」，两者独立计算、不可互相替代。

### 2.6 引擎六：应用中心推广分发

**传统应用市场的痛点**：流量被头部应用商店垄断，开发者获客成本高；用户需在多个应用间重复注册，身份割裂。

**Node 的解法**：把钱包的链上流量直接转化为第三方应用的分发与变现通道。

| 维度   | 传统应用市场         | Node 应用中心                    |
| ---- | -------------- | ---------------------------- |
| 流量来源 | 应用商店搜索竞价       | 钱包原生用户（自带身份与资产）              |
| 用户身份 | 每个应用独立注册       | DID 通行证统一签名登录                |
| 分发模式 | 仅下载 / 跳转       | 分发抽成 + 推广位 + 交易抽成 + 生态联合     |
| 结算周期 | 平台掌控，T+30/T+60 | 分发 T+7 / 交易抽成 T+30 / 广告 T+30 |
| 合规风险 | 平台承担全部审核责任     | 合作方自带资质，Node 仅做资质审核与流量分发     |

**四大变现通道**（费率详见 6.4）：分发抽成（T+7）、推广位广告（T+30）、交易抽成（T+30）、生态联合（按协议）。

**关键设计**：不参与团队归因 · 合规优先 · DID 联动 · 跨平台一致（iOS 退化为应用导航站，Android 可直接分发 APK）。

> **与前五大引擎的边界**：引擎一至五构成「商品池 → 关系 → 返利」的团队分润闭环；引擎六独立运作，是平台单方抽成的流量变现通道，不参与团队分润。

## 第三章 · 用户旅程与角色体系

### 3.1 角色体系：四种用户角色 + 一种平台角色

<aside>  
⚠️

**术语提示**：本文档中的「矿工」指**平台侧的链上多签运营角色**，负责商品上架、审核、参数配置与资金管理，**与区块链共识意义上的矿工无关**。

</aside>

**四种用户角色的演进路径**：

```
游客 ──绑定团队──► 买家 ──升级──► 代理 ──升级──► 高级代理
(未绑定)        (已绑定, rank=0)  (rank 1..2)   (rank 3..10)
```

| 角色       | 入口        | 核心能力                      | 限制            |
| -------- | --------- | ------------------------- | ------------- |
| **游客**   | 下载 App 即可 | 浏览商品池（不可购买）               | 无购买、无返利、无升级   |
| **买家**   | 绑定团队上级    | 浏览 + 购买 + 订单 + 持有码 + 流转市场 | 无返利、无升级       |
| **代理**   | 个人积分达标升级  | 买家全部 + 返利领取 + 升级管理        | —             |
| **高级代理** | 团队积分达标    | 代理全部 + 可发布社区任务            | —             |

> **平台角色（不在用户演进链上）**：

| 角色       | 入口        | 核心能力                      | 限制            |
| -------- | --------- | ------------------------- | ------------- |
| **矿工**   | 平台多签地址    | 后台运营（商品 / 审核 / 参数 / 资金）   | 仅平台方          |

### 3.2 从下载到代理的完整路径

```
1. 下载 App
   ↓
2. 创建 / 导入钱包（Tab 1）→ 本地加密存储私钥
   ↓
3. 激活保险库（Tab 5）→ 设备指纹绑定
   ↓
4. 绑定团队上级（Tab 2 推广中心）→ 扫码 / 搜索短号 / 接受邀请
   ↓
5. 上级审批 → 下级确认加入 → PIN 签名 → 设备指纹 + 关系一并上链 → 成为买家
   ↓
6. 进入商城（Tab 3）→ 浏览商品池 → 选商品下单
   ↓
7. 购买「个人积分商品」→ 累加个人积分
   ↓
8. 积分达标 → 申请升级（Tab 2 我的团队）→ 成为代理（rank 1+）
   ↓
9. 代理领取返利（Tab 2 佣金明细）→ 冻结期满后一键领取
   ↓
10. 发展下级 → 下级购买累加团队积分 → 升级到高级代理
```

**关键触点**：

- **第 4–5 步**：团队绑定是商城购买的硬约束，不可跳过
- **第 8 步**：L3 及以上升级需同时满足个人积分与团队积分门槛
- **第 9 步**：返利成交即分配但处于冻结状态，按商品价格冻结 7/14/30 天（详见 4.2）

### 3.3 角色信息展示

### 4.1 钱包（Tab 1）—— 你的链上资产保险箱

**定位**：纯粹的资产管理入口，不混入任何业务 / 关系 / 推广逻辑。

| 功能          | 说明                        | 用户价值            |
| ----------- | ------------------------- | --------------- |
| 资产看板        | 总估值 + 代币明细                | 一眼看清「我有什么」      |
| Swap 兑换     | 自主链代币两两兑换 + 滑点保护 + 白名单分级  | 无需出 App 即可换币    |
| 水龙头（Faucet） | 基础领取 + 社区制任务激励            | 新用户零门槛起步 + 活跃激励 |
| 发送 / 接收     | 链上转账                      | 资产流转            |
| 钱包管理        | 创建 / 导入 / 重命名 / 导出私钥 / 销毁 | 完整的自管闭环         |

**代币体系**：RC（Gas 原生）· USDRs（平台主币）· HRCs（生态联合）· RSTs（储备）。完整口径见附录 C。

#### 钱包地址与短号的关系

| 概念       | 本质                      | 数量                   | 是否可改          |
| -------- | ----------------------- | -------------------- | ------------- |
| **钱包地址** | 链上唯一真身，算钱 / 绑定 / 鉴权只信地址 | 一个身份可有多个钱包地址         | 不可改           |
| **短号**   | 钱包地址的「易记别名」，链上资产        | 一个身份可绑多个短号（靓号 + 免费号） | 可转移 / 赠送 / 挂售 |

- 短号绑定到钱包地址（不是绑定到「人」）
- 同一时间仅一个短号设为「展示短号」
- 短号可跨地址转移（卖出、赠送）
- 别人记不住 `0x71C7...98A5`，但能记住 `#100068`

#### Swap 兑换与白名单

> **计价口径**：门槛金额以 **USDT 计价**（外部入金币种，作为价值基准），持仓门槛以 **USDRs 计量**（平台主币）。两者口径不同，见附录 C。

| Swap 操作                   | 白名单要求                              | 理由             |
| ------------------------- | ---------------------------------- | -------------- |
| RC ↔ USDRs（同链基础）          | 无                                  | 入门级，新用户必备      |
| USDT ↔ USDRs（跨链入金）        | 无                                  | 入金主通道，不应设卡     |
| HRCs 相关 Swap              | 等级 rank ≥ 3                        | 生态联合代币，需生态贡献门槛 |
| 大额 Swap（≥ 1000 USDT 等值）   | 等级 rank ≥ 5 **或** 持仓 ≥ 5000 USDRs  | 风控 + 反洗钱       |
| 超大额 Swap（≥ 10000 USDT 等值） | 等级 rank ≥ 7 **或** 持仓 ≥ 20000 USDRs | 严风控            |

**设计要点**：采用「等级 OR 持仓」双维度，平衡风控与用户准入。

#### 水龙头（Faucet）

**基础领取**：每 24h 领 5 RC，平台代付 Gas（元交易）；防刷三重机制（设备指纹排他 + IP 频次 + 防重放）；资金池 50,000 RC。

**社区制任务激励**（双向任务市场，🟡 见附录 D）：

| 维度     | 规则                                         |
| ------ | ------------------------------------------ |
| 基础领取   | 每 24h 领 5 RC 保留（新用户入门保障）                   |
| 任务发布方  | 首期仅平台 + 代理（rank ≥ 3）可发布，普通用户仅接受任务          |
| 首期任务类型 | 地推类（邀请绑定）+ 体验类（首次 Swap / 绑定短号 / 激活保险库）     |
| 奖励来源   | 平台任务走 Gas Tank；代理任务走代理预算（需锁定押金 50 USDT 等值） |
| 奖励代币   | RC（与基础领取一致，避免与购买返佣积分双算）                    |
| 防伪     | 首期仅做链上可验证任务，链下任务后续再上                       |

#### 团队积分转移（⚪ 规划中）

| 维度       | 规则                            |
| -------- | ----------------------------- |
| 转移对象     | 仅团队积分可转移，个人积分不可转移             |


#### 佣金明细与冻结期

```
┌─────────────────────────────────────┐
│  可领取佣金                          │
│  ┌─────────┬─────────┬─────────┐    │
│  │  USDRs  │   RC    │  HRCs   │    │
│  │  45.20  │  120.5  │   8.3   │    │
│  └─────────┴─────────┴─────────┘    │
│  [一键领取全部]                      │
└─────────────────────────────────────┘
```

**返佣冻结期**（防退货刷单的核心机制）：

| 商品价格（USDT 计价）   | 冻结期  |
| --------------- | ---- |
| 单价 < 500        | 7 天  |
| 500 ≤ 单价 < 2000 | 14 天 |
| 单价 ≥ 2000       | 30 天 |

- 返佣在成交时即时分配到上线名下，但处于「冻结」状态
- 确认收货后进入冻结期倒计时
- 冻结期内若发生退货，未领奖励自动撤销
- 冻结期满后转为可领取状态

**退货与返佣的关系**：

- 退货只退钱，**不解除上下级关系**
- 退货自动撤销该订单对应的未领取奖励
- **若上线已领取**：系统自动从其后续未领取佣金中抵扣，抵扣完成前不可发起新的领取（不依赖人工退回）
- 已退货商品的唯一码永久作废，不可二次销售

#### 烧断保护（⚪ 规划中）

**动态压缩（✅ 已上线）**：上线等级不达标时自动跳过，名额上卷给合格上线。

**烧断保护（⚪ 规划中）**：处理「上级等级低于下级」的不合理分配场景，确保返佣名额给到真正够格的上线，同时通过积分补偿保护实际推广者利益。机制细节评审中，详见规格文档「烧断机制」章节。

#### 关系转移机制（重要）

**核心规则**：上下级关系绑定到**钱包地址**而非「人」。

| 场景        | 转移机制          | 关系处理                   |
| --------- | ------------- | ---------------------- |
| **换设备**   | 新设备导入同一钱包私钥   | 关系不变（地址未变）             |
| **换钱包地址** | 旧地址资产转移至新地址   | 关系随地址转移（含上下级链路、积分、等级）  |
| **多地址管理** | 一个身份可持有多个钱包地址 | 关系绑定在「主用地址」上           |
| **地址丢失**  | 私钥丢失无法访问      | 需走多签治理流程迁移（时间锁 + 矿工审核） |

> **设计要点**：这是 Node 体系内唯一不通过多签治理就能「动关系」的合法路径——因为关系绑在地址上，地址迁移本质是「换容器」而非「换关系」。

**合规即护城河**：加密 / 钱包类应用在各大应用商店的上架门槛极高，多数团队因资质缺失被拒之门外。Node 采取「合规优先」设计——平台自身不承载加密货币直接交易、不内嵌 DApp 浏览器、对合作方做资质与安全双重审核——这不是限制，而是让合作方能安全、可持续地借 Node 流量落地的核心优势。

</aside>

**合作方上架流程**：

```
1. 提交上架申请（Tab 4 → 我的 → 上架申请）
2. Node 平台审核：
   ├─ 资质审核（营业执照 / ICP / 加密货币许可证）
   ├─ 应用安全评估（病毒 / 恶意代码 / 隐私政策）
   ├─ 内容合规审核
   └─ 业务模式审核（是否符合 Node 生态定位）
3. 审核通过 → 签署合作协议（确定抽成比例）
4. 上架应用中心
5. 持续运营监控（违规下架机制）
```

> 各司法管辖区的上架监管要求已抽出至 **附录 E · 合规参考**，本节不再展开。

**合规红线**：Node 应用中心不参与加密货币的直接交易功能，仅做应用导航与分发。涉及加密交易的功能由第三方 App 自身承担合规责任。

#### 福利特权

**三级钥匙体系**：

| 层级     | 钥匙类型        | 能力                                      | 状态    |
| ------ | ----------- | --------------------------------------- | ----- |
| **L1** | 设备指纹钥匙      | 反女巫闸门：一台设备同时刻只能绑一个钱包；冷密钥基于设备指纹生成，私钥永不上传 | ✅ 已上线 |
| **L2** | 生物特征钥匙（人脸等） | 高价值操作的二次确认                              | ⚪ 规划中 |

**与其他模块的关联**：

| 模块   | 设备指纹要求      | 说明                   |
| ---- | ----------- | -------------------- |
| 福利特权 | ✅ 必须        | 领取空投 / 资产 / 互动福利前需绑定 |

**保险库延伸能力（⚪ 规划中）**：钥匙管理 · 资产托管信托（遗产继承、大额托管）· 保险库服务（保险、紧急冻结、找回）· 联合签名（多设备多签确认）。

#### DID 通行证 —— 数字身份连接器

```
第三方 App（IM / DApp / 合作应用）
  → 拉起 Node 授权面板
  → 用户选择签名主体（Web3 钱包地址 或 Web2 本地凭证）
  → 输入 6 位本地 PIN 码
  → Node 本地私钥签名
  → 返回签名凭证 → 完成登录
```

**落地节奏**：首期 DID 仅做「被动授权」（第三方拉起 Node 授权面板完成签名登录），**不主动打通第三方应用身份节点**。以下为远期愿景：

| 打通场景        | 说明                               |
| ----------- | -------------------------------- |
| **IM 应用**   | 用 Node 地址登录 IM，IM 内可直接调起 Node 转账 |
| **DApp**    | DApp 通过 Node 钱包连接，无需自建钱包体系       |
| **Web2 应用** | 通过 Node DID 实现无密码登录              |
| **跨应用身份**   | 一个 Node 身份通行多个应用                 |

### 5.5 资产可处置性

<aside>  
📌

**读表须知**：下表的「可售 / 已售」是**商品码在平台库存体系中的状态**，不是买家视角的动作。`可售` = 尚在平台库存、未售给任何人；`已售` = 已发放到用户名下。因此「已售」的码才是用户可以二次处置的资产。

| 资产状态           | 归属方    | 可挂售 | 可拍卖 | 可租赁 | 可赠送 |

### 5.6 各渠道能力详解

**一口价**：挂单（卖家定价 → 资产锁定）· 购买（0% 手续费，货款全付卖家）· 撤单 · 矿工强制撤单。

**拍卖**：挂拍（起拍价 + 加价幅度 + 时长）· 出价（资金锁定）· 成交（最高价者得，2.5% 手续费）· 强制结算 / 强制取消 / 退款提取。

> **风控设计**：拍卖渠道的强制结算 / 强制取消 / 退款提取三项能力，用于防止卖家恶意不交付或拍卖异常卡死。

**租赁（ERC-4907 使用权分离）**：出租（租金 + 租期 + 是否独占）· 承租（租客获使用权，所有权不动）· 独占模式（期间资产锁定）· 非独占模式（可同时挂售，需提示租客）· 结束租赁（出租方 / 矿工可提前终止，租客只能到期结束）。

**赠送**：号主付手续费后立即过户；不在市场挂单，入口在短号中心 / 商品详情页；订单中心可见记录。

| --------- | ------ | -------------------- |
| **荷兰拍**   | **P3** | 线性降价模型，适合清仓 / 动态定价   |

## 第九章 · 常见问题（FAQ）

**Q1. 私钥丢了，Node 能帮我找回吗？**

不能。Node 是纯自管钱包，私钥仅加密存储在你的设备本地，平台不持有、不备份、不上云。请务必自行备份助记词 / 私钥。若地址私钥丢失导致无法访问，团队关系与积分可通过多签治理流程 + 时间锁迁移到新地址，但**资产本身无法找回**。

**Q2. 上下级关系绑错了，能解绑吗？**

不能自行解绑。关系是链上 set-once 写入、永久有效的。唯一的例外是：①更换钱包地址时关系随地址迁移（换容器不换关系）；②极端情况下由平台多签治理人工干预。这个设计是为了保证归因不可篡改、佣金不可赖账。

**Q3. 返利多久能到账？为什么有冻结期？**

返利在成交瞬间就分配到上线名下，但处于冻结状态。确认收货后开始冻结期倒计时：单价 < 500 USDT 冻结 7 天，500–2000 冻结 14 天，≥ 2000 冻结 30 天。冻结期是为了防止「买货领奖 → 立刻退货」的刷单套利。期满后在 Tab 2 佣金明细一键领取。

**Q4. 退货后返利怎么处理？会影响我的团队关系吗？**

退货只退钱，**不解除上下级关系**。该订单对应的未领取奖励自动撤销；若上线已经领取，系统会从其后续未领取佣金中自动抵扣。已退货商品的唯一码永久作废，不会二次销售。

**Q5. Node 的返利机制与传销有什么本质区别？**

三点关键区别：①**收益必须来自真实商品成交**，无成交即无返利，平台不提供任何静态收益或拉人头奖励；②**返利是分销佣金成本**，从商品毛利中支出，不是后来者的入金；③**不设入门费**，下载即可使用钱包、浏览商品，「代理能力商品」是推广工具与服务的采购，对价对应实际交付的能力，不购买不影响正常使用。详见「重要声明」第 2 条。

**Q6. 平台如果停止运营，我的资产还在吗？**

钱包资产完全由你的私钥控制，与平台运营状态无关，随时可用助记词在其他兼容钱包中恢复。链上资产（短号、已发放的商品码、返利余额）也存储在链上合约中。**依赖链下服务的部分**（如保密商品的卡密映射、订单物流状态）会受影响，这一点请知悉。

**Q7. 为什么商城必须先绑定团队才能买东西？**

为了保证每笔成交都有清晰、不可篡改的归因链路，从而让级差返利能够正确、自动地分配给对应上线。游客可以自由浏览商品与价格，只是下单需要先完成绑定。

**Q8. 一台手机能登录多个钱包吗？**

可以创建 / 导入多个钱包，但**同一时刻只能有一个钱包完成设备指纹绑定**。这是反女巫的硬约束，用于防止批量刷号。未完成设备指纹绑定的钱包无法绑定团队、领取福利或在商城下单。

**Q9. 短号和钱包地址是什么关系？短号能卖吗？**

短号是钱包地址的「易记别名」，本身是链上资产，绑定在地址上而非人上。一个地址可绑多个短号（靓号 + 1 个免费号），同一时间只有一个是「展示短号」。短号可以转移、赠送，也可以在流转市场挂售 / 拍卖 / 出租。

**Q10. 在流转市场买卖资产，会产生团队返利吗？**

不会。这是铁律：流转市场是二级资产处置市场，所有渠道的流水都不纳入代理奖励分润。一级市场（官方商品池）才触发级差返利。

**Q11. 合作方接入需要多久？抽成比例是多少？**

接入流程见 8.5。抽成比例目前采取一事一议的协议模式，具体费率**【待确认】**，请通过商务渠道洽谈。结算周期为分发 T+7、交易抽成与广告 T+30。

**Q12. Node 的合约经过第三方审计了吗？**

**【待确认】**——见 7.5 节，此项需项目方补充真实信息后方可对外发布。

## 附录 E · 合规参考

> 以下为公开资料整理，仅供参考，**不构成法律意见**。实际义务以合作方所在司法管辖区的专业意见为准。

### E.1 应用商店上架政策

**iOS App Store**：加密货币 / 钱包类应用审核极严；明确禁止内嵌 DApp 浏览器；涉及加密货币购买 / 持有的应用需通过受监管司法管辖区的认证服务；钱包类应用需提供合规资质。

**Google Play（2024 年起强制）**：加密货币钱包开发商在 15 个主要司法管辖区（含美国 / 英国 / 欧盟）上架前必须获得政府颁发的许可证；美国地区需在 FinCEN 登记为货币服务业务（MSB）。

**国内安卓商店**：涉及加密货币 / 区块链的应用不允许上架；需软著、ICP 备案、应用安全评估。Node 在国内主要通过自有渠道分发。

### E.2 主要司法管辖区监管概览

| 司法管辖区   | 监管机构        | 适用牌照            | 关键要点                |
| ------- | ----------- | --------------- | ------------------- |
| **新加坡** | MAS         | DPT 牌照          | 适合作为亚太总部，对加密业务相对友好  |
| **香港**  | SFC         | Type 1 / Type 7 | 2024 年起开放零售加密交易，需持牌 |
| **欧盟**  | ESMA + 各国监管 | MiCA 法规         | 统一欧盟加密资产监管框架        |
| **美国**  | FinCEN + 各州 | MSB 登记 + MTL    | 各州监管不同，合规成本极高       |
| **迪拜**  | VARA        | VA 服务商牌照        | 中东加密中心，对加密业务友好      |
