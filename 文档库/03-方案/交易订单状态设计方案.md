# 交易订单状态设计方案（产品视角）

> 对齐基准：6 份合约文档（GoodsMarket / TradeLedger / 交易 & 代理返利合约体系 / AgentLevel / AgentPoints / RewardClaim）
> 版本：v1.0
> 日期：2026-07-22

---

## 一、设计原则

1. **合约是真相源**：用户可见状态由合约态派生，不发明合约不存在的状态
2. **主辅分离**：主状态（合约派生 4 态）+ 辅助态（链下物流/卡密），组合呈现给用户
3. **不混淆**：物流、卡密领取等纯链下流程作为独立扩展字段，不污染主状态
4. **无待付款**：合约 buy 是原子收款，不存在"待付款"状态

---

## 二、主状态（合约派生，4 态）

| 主状态 | 合约条件 | 触发 | 是否终态 |
|---|---|---|---|
| `created` | exists=true, returned=false, 无 open ReturnReq | Purchased 事件 | 否 |
| `return_requested` | exists=true, returned=false, 有 open ReturnReq | ReturnRequested 事件 | 否 |
| `returned` | returned=true | ReturnApproved 事件 | **是，不可逆** |
| `return_rejected` | exists=true, returned=false, 有已关闭 ReturnReq 且非 approved | ReturnRejected 事件 | 否（可再申请） |

### 硬约束

- `returned` 后不可再申请退货（合约 `require(o.exists && !o.returned)` 会 revert）
- `return_rejected` 后可再申请（returned 仍为 false）
- 同一订单对不同 codeId 可多次发起退货申请（合约不阻止）
- `approveReturn` 后 `o.returned=true`，该 refId 不可再 `returnRequest`

## 三、辅助状态（链下业务态，独立字段）

### 3.1 实物商品（fulfillment_status）

```
pending_shipment → shipped → delivered
```

- 矿工后台操作触发，与合约无关
- 不改变主状态（主状态仍是 created）

### 3.2 虚拟商品（redeem_status）

```
pending_redeem → redeemed
```

- 链下 API 领取卡密触发
- 不改变主状态

### 3.3 服务/积分商品

```
直接生效（无需辅助状态）
```

- buy() 原子完成，积分在合约内 mint

## 五、状态判定逻辑（前端实现）

```javascript
// 主状态（合约派生）
// created / return_requested / returned / return_rejected

// 辅助态（链下业务）
// 实物: fulfillment_status = pending_shipment / shipped / delivered
// 虚拟: redeem_status = pending_redeem / redeemed

function getUserStatus(order) {
    // 1. 先判主状态
    if (order.status === 'returned') return '已退货';
    if (order.status === 'return_requested') return '退货申请中';
    if (order.status === 'return_rejected') return '退货被拒';
    
    // 2. 主状态为 created 时，按商品类型看辅助态
    if (order.status === 'created') {
        if (order.orderType === 'physical') {
            const fs = order.fulfillmentStatus;
            if (fs === 'pending_shipment') return '待发货';
            if (fs === 'shipped') return '已发货';
            if (fs === 'delivered') return '已完成';
            return '待发货';
        }
        if (order.orderType === 'virtual') {
            return order.redeemStatus === 'redeemed' ? '已完成' : '待领取';
        }
        // 服务/积分：即时完成
        return '已完成';
    }
}
```

## 八、Tab 筛选设计

订单列表顶部 4 个 Tab，分类语义**互斥**：交易进行中 / 交易完结 / 退货流程。

| Tab | 筛选条件 | 说明 |
|---|---|---|
| 全部 | 无 | 所有订单 |
| 进行中 | 待发货 + 待领取 + 已发货 | 交易流程未完结，需用户推进 |
| 已完成 | 已完成 | 交易流程完结 |
| 退货 | 退货申请中 + 已退货 + 退货被拒 | 退货相关全流程 |

**默认选中"进行中"**（用户最关心的）。

### 分类流转规则
- 用户发起退货申请后，订单自动从"进行中/已完成"流转到"退货"分类
- 撤销退货申请后，订单主状态回退为 `created`，重新归入"进行中"或"已完成"
- 退货被拒后仍留在"退货"分类（用户可重新申请或查看原因）
- "退货"分类覆盖退货全流程，用户发起退货后去"退货"Tab 即可查看进度

## 九、订单详情页状态展示

### 9.1 详情页展示内容

订单详情页展示以下区块（按顺序）：
1. **订单号** refId（可复制）
2. **商品信息**（图标/名称/类型/商品ID/数量）

5. **关联持有码**（codeId 列表，可跳转查看）
6. **退货流程时间线**（仅退货相关订单展示，见 9.2/9.3）
7. **退货被拒提示**（仅退货被拒订单展示，见 9.3）
8. **操作按钮**（按§七规则）

**详情页不展示**：
- 奖励明细（直写奖励/上线分润）—— 内部数据，不向用户暴露
- 订单状态时间线（timeline）—— 内部流程数据，不向用户暴露

## 十、关键交互规则

### 10.1 退货前置校验（退货被拒的常见原因）

用户点击"申请退货"时，前端先校验：
1. **已领奖励是否退回**：查 `RewardClaim.rewards(refId).returnedAmount >= amount`
2. **未满足则提示**："请先退回已领奖励 X USDR，[前往退回]"

### 10.2 确认收货（实物）

- 已发货状态下显示"确认收货"按钮
- 点击后调用链下接口标记 `fulfillment_status = delivered`
- 主状态仍为 `created`（合约层不变）
- 7 天未确认自动标记为 delivered

### 10.3 领取卡密（虚拟）

- 待领取状态下显示"领取卡密"按钮
- 点击后调链下 API，校验 `codeOwner == buyer && codeStatus == 2`
- 领取后标记 `redeem_status = redeemed`
- 主状态仍为 `created`

### 10.4 退货被拒后重新申请

- 退货被拒状态下显示"重新申请"按钮
- 点击重新打开退货表单（标题为"重新申请退货"）
- 表单顶部展示上次驳回原因，提示用户先处理
- 合约层：`returnRequest` 可再次调用（returned 仍为 false）

### 10.5 撤销退货申请

- 退货申请中状态下显示"撤销申请"按钮
- 点击后二次确认，确认后主状态回退为 `created`
- 清空 returnRequest 记录，添加 timeline 事件
- 订单重新归入"进行中"或"已完成"Tab 分类
- 合约层：链下撤销（合约无对应事件，仅业务层标记）

### 10.6 查看退货驳回原因

- 退货被拒状态下显示"查看原因"按钮
- 点击后 toast 展示驳回原因
- 详情页同时展示红色提示块，含驳回原因和合约层说明

## 十一、状态流转图

### 11.1 订单主状态流转

```
                    [Purchased 事件]
                          │
                          ↓
                       created
                          │
                   [ReturnRequested 事件]
                          │
                          ↓
                  return_requested
                          │
              ┌───────────┴───────────┐
              │                       │
       [ReturnApproved]         [ReturnRejected]
              │                       │
              ↓                       ↓
         returned               return_rejected
        (终态，不可逆)               │
                                 (可再 returnRequest)
                                      │
                                      ↓
                              return_requested
```

### 11.2 物流/卡密态并行流转

```
实物:  pending_shipment → shipped → delivered  （与主状态并行）
虚拟:  pending_redeem → redeemed                （与主状态并行）
```

## 十二、状态组合示例

### 实物订单完整流程

```
初始:     主状态=created,           物流派=pending_shipment
矿工发货: 主状态=created,           物流派=shipped
确认收货: 主状态=created,           物流派=delivered（已完成）
申请退货: 主状态=return_requested,   物流派=delivered
批准退货: 主状态=returned,           物流派=delivered（码作废 codeStatus=3）
```

### 虚拟商品退货流程

```
初始:     主状态=created,         卡密态=redeemed
申请退货: 主状态=return_requested, 卡密态=redeemed
批准退货: 主状态=returned,         卡密态=redeemed（码作废 codeStatus=3）
```

## 十三、核心总结

| 维度 | 设计 |
|---|---|
| 主状态数量 | **4 态**（created / return_requested / returned / return_rejected） |
| 主状态来源 | 合约 `exists` + `returned` + `ReturnReq.open` 派生 |
| 辅助状态 | 物流态（实物）/ 卡密态（虚拟），独立字段，不影响主状态 |
| 终态 | `returned`（合约 returned=true，不可逆） |
| 待付款 | **无**（合约 buy 是原子收款） |
| 退货可逆性 | returned 不可逆；return_rejected 可再申请；return_requested 可撤销 |
| 用户可见状态 | 实物 6 态 / 虚拟 5 态 / 服务 4 态 |
| Tab 分类 | 全部 / 进行中 / 已完成 / 退货（语义互斥） |
| 默认 Tab | "进行中"（用户最需操作） |
| 退货前置 | 必须先退回已领奖励（前端硬编码校验） |
| 详情页不展示 | 奖励明细（直写奖励/上线分润）、订单状态时间线 |
| 详情页仅退货展示 | 退货流程时间线（含驳回原因） |
| 地址管理 | 支持新增/编辑/删除/设为默认，从结算页进入保存后自动回填 |

**一句话**：主状态 4 态严格对齐合约（exists/returned/ReturnReq.open），物流和卡密等纯链下流程作为独立辅助字段，不与合约态混淆。用户看到的 6 个状态是合约 4 态 + 链下辅助态的组合呈现，合约态是真相源，链下态是体验补充，两者分层不混淆。Tab 分类语义互斥（进行中/已完成/退货），退货全流程统一归入"退货"分类。详情页聚焦用户可见信息，奖励明细和内部时间线不向用户暴露。
