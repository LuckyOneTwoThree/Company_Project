## 一、产品定位

### 1.1 核心定位
- **统一商品池商城**：所有用户（游客/买家/代理/矿工）看到同一商品池
- **级差返利体系**：购买触发沿 E 链上溯 N 层级差分润
- **等级驱动收益**：代理收益由自身 rank（1..10）决定，与买家无关
- **无代销/无层级商品池**：商品由矿工统一上架、统一定价、统一管库存

### 1.2 核心设计哲学
| 哲学 | 体现 |
|---|---|
| 等级唯一 | `level[addr]` 0..10，无"个人等级/团队等级"之分 |
| 积分双轨 | 个人积分（basis=0）/ 团队积分（basis=1），逐级配置 |
| 自身达标 | A 是 L10 不会抬高上线等级，普众公平 |
| 动态压缩 | 未达标上线跳过、名额上卷，避免名额浪费 |
| 普众参与 | rank=0 也可购买，仅影响"自己作为上线时是否合格" |

## 二、角色与状态模型

### 2.1 四种用户状态

| 状态 | E 链绑定 | rank | 可见功能 |
|---|---|---|---|
| **游客** | ❌ 未绑定 | - | 商城浏览 + 购买（首次购买触发归因绑定） |
| **买家** | ✅ 已绑定 | 0 | 商城浏览 + 购买 + 我的订单 + 我的持有码 |
| **代理** | ✅ 已绑定 | 1..10 | 买家全部功能 + 代理中心 + 我的返利 + 升级管理 |
| **矿工** | - | - | 全部用户功能 + 矿工后台（上架/审核/配置） |

### 2.2 关键澄清

**rank=0 的语义**：
- ✅ 可以正常购买（合约层 buy 无 rank 限制）
- ✅ 购买触发上线链分润（上线是否拿返佣取决于**上线自身 rank**）
- ❌ 自己作为别人上线时无法拿返利（compression 跳过）
- ❌ 无代理中心入口

**等级与积分的关系**：
- 等级只有**一个**：`level[addr]` ∈ 0..10
- 积分有**两种**：个人积分（AgentPoints.balanceOf）+ 团队积分（teamPoints）
- 门槛基准**逐级配置**：`thresholdBasis[level]` 0=个人 / 1=团队
- 低级（1-2）通常看个人积分，高级（3-10）通常看团队积分（防光杆司令）

### 2.3 双视角模型

| 视角 | 颜色标识 | 含义 | 展示位置 |
|---|---|---|---|
| 🛒 购买视角 | 蓝色 | 我买东西时**我的上线**赚多少 | 商品详情 / 结算页 / 商城首页身份卡 |
| 💰 上线视角 | 绿色 | **别人买东西**我作为上线赚多少 | 代理中心 / 我的返利 |

## 三、商品模型

### 3.1 商品字段（createProduct）

```solidity
struct Product {
    bool exists;
    bool active;           // 上下架
    bool secretCode;        // 保密商品开关
    uint256 minOrderQty;    // MOQ 起订量
    uint256 resaleFeeBps;   // 二手转卖手续费(bps)
    uint256 pointsPerUnit;  // 每件送积分(升级燃料)
    bool feedTeamPoints;    // 是否喂团队积分
    string name;
}
```

### 3.2 商品定价

- **多币定价**：`price[productId][token]`，0 表示不接受该币
- **统一价**：全平台同价，不分代理层级
- **数量折扣阶梯**：`tiers[]=(minQty, bps)`
  - bps = 支付原价比例（7000=70%、6000=60%）
  - 取满足条件的最高 minQty 那档
  - 默认 10000=原价

### 3.3 商品类型分类

| 类型 | pointsPerUnit | feedTeamPoints | secretCode | 典型场景 |
|---|---|---|---|---|
| **实物商品** | 0 | false | false | 硬件设备 |
| **虚拟商品** | 0 | false | true | 卡密/激活码 |
| **级别服务商品** | >0 | true | false | 升级服务包 |
| **积分商品** | >0 | false | false | 纯积分包 |

### 3.4 商品奖励配置（rewards[]）

```solidity
struct RewardCfg {
    address claim;        // RewardClaim 实例地址
    uint8 mode;            // 0=固定×qty / 1=按成交比例bps
    uint256 amountOrBps;   // mode 0=固定金额 / mode 1=bps(500=5%)
}
```

**业务场景**：
- mode 0：买硬件送 100 USDR（每件固定，按 qty 倍乘）
- mode 1：买会员卡返 5% USDR（按 **net 成交价**比例，非 gross 原价）

**注意**：直写奖励是给**买家自身**的，独立于级差返利（上线返利）。

**⚠️ 严重风险（无 try/catch 保护）**：

> 直写奖励配置的 `RewardClaim.addReward` 调用**没有 try/catch 保护**，与 AgentPoints/AgentLevel/AgentReward 的韧性设计不同。如果 RewardClaim 奖池余额不足（触发 `RC: underfunded` revert），**整个购买交易将 revert**，买家无法完成购买。

**前端必须监控**：
- 每个商品配置的 RewardClaim 实例的 `shortfall()`
- 不足时立即通知 miner 充值奖池
- 或商品下架，避免购买失败

**配置不可单独删除**：
- `clearRewardCfg(productId)` 删除商品的全部 rewards 配置
- **不能单独删除某条**
- 如需调整，先 clear 再重新 addRewardCfg

### 3.5 保密商品（secretCode）

- 商品级开关 `secretCode`
- **`productCodes(productId)` 视图的访问限制**：合约第409-412行 `require(!products[productId].secretCode || isMiner[msg.sender], "GM: secret")`
  - 非保密商品：所有人可读可售码列表
  - 保密商品：**仅 miner 可读**（其他人调 `productCodes` 会 revert "GM: secret"）
- 合约层 `secretCode` 仅作为标记位，**链上数据本质公开**（链上存储的 bytes32 仍可被直接读取）

**⚠️ 严重风险：链上明文流转的 calldata 扫描攻击**

> `importCodes(productId, bytes32[])` 的 calldata 中**包含明文 codeId**。任何人都可以通过 Etherscan 或自建节点扫描 `importCodes` 的历史交易 calldata，**完整还原所有保密商品的码列表**，绕过 `productCodes` 视图限制。

**攻击路径**：
1. 攻击者扫描所有 `GoodsMarket.importCodes` 历史交易
2. 解析 calldata 提取 `bytes32[]` 数组（即明文 codeId）
3. 对每个 codeId 查 `codeProduct` → 确定所属商品
4. 若商品 `secretCode=true`，攻击者拿到所有"保密"码体
5. 等买家购买后，用 codeId 去 `codeOwner` 查询，获取真实卡密信息

**P1 级硬性约束（必须执行，非建议）**：

| 约束 | 说明 |
|---|---|
| **绝不上链明文** | 保密商品的 `bytes32` 必须是哈希值（如 `keccak256(真实卡密)`），**绝不能是明文 codeId** |
| **链下映射表** | 矿工后台维护"链上 hash ↔ 链下真实卡密"映射表，存数据库 |
| **发货链下完成** | 用户购买后通过链下 API 凭 refId 领取真实卡密（链下校验链上 codeStatus=2） |
| **核销链上验证** | 链下 API 调用前校验 `codeOwner[codeId] == buyer && codeStatus[codeId] == 2` |
| **importCodes 用 hash** | `importCodes` 传入的 bytes32 用哈希值，攻击者扫描 calldata 只能拿到无意义哈希 |

**推荐码生成方案**：

```solidity
// 链上存哈希（非明文）
bytes32 publicCodeHash = keccak256(abi.encodePacked(realCodeString));
// importCodes 传入 publicCodeHash 而非 realCodeString
goodsMarket.importCodes(productId, [publicCodeHash1, publicCodeHash2, ...]);

// 链下数据库存映射
db.table('secret_codes').insert({
  codeHash: publicCodeHash,
  realCode: 'ABCD-1234-EFGH-5678',  // 真实卡密
  productId: 42,
  status: 'available'  // available / sold / returned
});

// 用户购买后凭 refId 领取真实卡密
// 链下 API 流程：
// 1. 用户调 /api/redeem-code?refId=xxx&buyer=0x...
// 2. 链下校验：查 orderCodes(refId) 拿到 codeId 列表
// 3. 链上校验：codeOwner[codeId] == buyer && codeStatus[codeId] == 2
// 4. 链下匹配：codeHash = codeId（链上存的哈希），查 db.secret_codes 拿到 realCode
// 5. 返回 realCode 给用户
```

**业务场景**：高价值卡密、激活码、会员卡号


### 3.6 商品图与元数据（链下方案）

合约层无图片字段，链下方案：
- 图片存储：IPFS / 对象存储
- 链下 API：`/api/products/{productId}` 返回图片URL、描述、分类等
- 前端组装：链上读价格/库存 + 链下读元数据

## 四、唯一码库存模型

### 4.1 状态机

```
0 未设 (unset) → 1 可售 (available) → 2 已售 (sold) → 3 已退 (returned)
```

**关键事实**：
- 500 库存 = 500 个唯一码
- 退货后状态变 3，**永久作废**（合约无重置 codeStatus 的方法，importCodes 要求 codeStatus=0，已退码无法再次导入）
- 合约层提供 `productCodes(productId)` 视图返回 `_available[productId]`（**可售库存码列表**，非全部历史码）
- 对保密商品（`secretCode=true`），`productCodes` 视图仅 miner 可读（合约第409-412行 `require(!products[productId].secretCode || isMiner[msg.sender], "GM: secret")`）
- 链上数据本质公开，保密方案需配合"链上存哈希 + 链下映射真实码体"

### 4.2 关键方法

| 方法 | 谁可调 | 功能 |
|---|---|---|
| `importCodes(productId, bytes32[])` | 仅 miner | 批量导入唯一码（要求 codeStatus=0） |
| `availableStock(productId)` | 所有人 | 查询可售库存数量 |
| `productCodes(productId)` | 所有人/受限 | 查询商品的**可售码列表**；保密商品仅 miner 可读 |
| `myCodes()` | 所有人(本人) | 查询自己的持有码 |
| `ownedCodesOf(addr)` | **gated：仅本人或 miner** | 查询某地址的持有码（合约校验 `msg.sender == a || isMiner`） |
| `orderCodes(refId)` | 所有人 | 查询某订单包含的码列表 |
| `codeStatus(codeId)` | 所有人 | 查询单个码状态（0/1/2/3） |
| `codeProduct(codeId)` | 所有人 | 查询码所属商品 |
| `codeOwner(codeId)` | 所有人 | 查询码当前持有人 |
| `productCount()` | 所有人 | 商品总数 |
| `sold(productId)` | 所有人 | 商品已售数量 |
| `quote(productId, qty, payToken)` | 所有人 | 预览总价（返回 gross + net） |
| `tiersOf(productId)` | 所有人 | 查询商品折扣阶梯配置 |
| `rewardsOf(productId)` | 所有人 | 查询商品奖励配置 |
| `orders(refId)` | 所有人 | 查询订单详情（buyer/productId/qty/payToken/paid/exists/returned） |
| `listings(codeId)` | 所有人 | 查询挂单详情（seller/payToken/price/active） |
| `getReturnRequest(id)` | 所有人 | 查询退货申请（buyer/productId/payToken/paid/open） |
| `returnRequestCount()` | 所有人 | 退货申请总数 |

### 4.3 码生成方案

合约层只存 `bytes32`，生成方案由业务层决定：

| 方案 | 适用 | 示例 |
|---|---|---|
| 哈希 | 通用 | `keccak256(abi.encode(productId, serial, salt))` |
| UUID | 链下生成 | `uuid v4` 转 bytes32 |
| 序号+盐 | 简单 | `keccak256(abi.encode(productId, index, secret))` |

## 五、购买流程

### 5.1 单次购买的数据流（合约层）

```
用户 buyer.buy(productId, qty, payToken)
   │
   ├─① 校验序列（按合约顺序）：
   │   ├─ 黑名单校验 `!banned[msg.sender]`（GM: banned）
   │   ├─ 白名单校验（whitelistEnabled 时 `whitelist[msg.sender]`，GM: not whitelisted）
   │   ├─ 商品存在且上架 `p.exists && p.active`（GM: product na）
   │   ├─ MOQ 校验 `qty > 0 && qty >= p.minOrderQty`（GM: below MOQ，**qty 不能为 0**）
   │   ├─ 币种校验 `price[productId][payToken] > 0`（GM: token not accepted）
   │   └─ 库存校验 `avail.length >= qty`（GM: insufficient stock）
   ├─①b 阶梯折扣算价：gross = unit * qty；net = gross * tierBps / 10000
   ├─①c transferFrom 收款到 **GoodsMarket 合约本身**（非 treasury；treasury 仅是 miner `withdraw` 提利目标地址）（GM: pay fail）
   ├─①d 订单生成：`orderCounter++`；`refId = keccak256(abi.encode(block.chainid, productId, orderCounter))`；`orders[refId] = Order(buyer, productId, qty, payToken, net, true, false)`
   ├─② 从唯一码台账分配 qty 个码给 buyer（codeStatus: 1→2）
   ├─③ 若商品配 rewards[] → 逐条 RewardClaim.addReward(buyer) // 买家自身奖励（⚠️ 无 try/catch，失败则整单 revert）
   ├─④ 若 pointsPerUnit > 0 → AgentPoints.mint(buyer, points) // 升级燃料（try/catch）
   │     └─ feedTeamPoints=true → AgentLevel.recordPoints() // 沿 E 链 teamDepth 层累加团队积分（try/catch）
   └─⑤ AgentReward.onPurchase(buyer, productId, gross, net, payToken, refId)（**整体被 buy 的 try/catch 包裹**，失败仅 emit RebateHookFailed）
         └─ 沿 ReferralRegistry(E) 上线链取 N 层（默认3层）
              └─ 每层按"该层上线自身等级"查 rebateBps[rank][layer]
              └─ compression 开：跳过 level=0 的未达标上线，名额上卷
              └─ 逐层 RewardClaim.addReward(agent, rebate) // **onPurchase 内部无 try/catch，但 onPurchase 整体被 buy 的 try/catch 捕获**，失败仅 emit RebateHookFailed
```

**⚠️ 韧性设计差异（重要）**：

| 钩子 | 失败处理 | 失败后果 |
|---|---|---|
| 直写奖励（rewards[]） | **无 try/catch** | addReward revert → buy 整单 revert → 购买失败 |
| AgentPoints.mint | try/catch | 主交易成功，仅积分未发 |
| AgentLevel.recordPoints | try/catch | 主交易成功，仅团队积分未累加 |
| AgentReward.onPurchase | **整体被 buy 的 try/catch 包裹** + emit RebateHookFailed | 主交易成功（购买+发码+直写奖励均生效），仅返利未发 |

**关键结论（两种"无 try/catch"的失败行为完全不同）**：

- **直写奖励**（rewards[]）：addReward 在 buy 函数内**直接调用**，没有 try/catch。RewardClaim 奖池资金不足时 → addReward revert → **buy 整单 revert** → 购买失败、码未分配、付款回滚
- **上线返利**（onPurchase 内部）：addReward 在 onPurchase 函数内调用，onPurchase 内部无 try/catch，**但 onPurchase 整体被 buy 的 try/catch 包裹**（合约第 219-223 行 `try agentReward.onPurchase(...) catch { emit RebateHookFailed(refId); }`）。RewardClaim 奖池资金不足时 → addReward revert → **onPurchase revert** → **被 buy try/catch 捕获** → emit RebateHookFailed → **主交易成功**（购买+发码+直写奖励均生效）

**前端必须区分的告警**：
- `RebateHookFailed` 事件 → 仅返利未发，运营补打返利即可（不影响买家）
- 直写奖励/购买的 revert → 购买失败，前端提示买家重试或换支付币种

**`onPurchase` 的 `productId` 参数实际未使用**（合约第 119 行 `productId; // kept for event/interface symmetry`），仅用于接口对称，返利计算不区分商品。

### 5.2 购买前置操作

1. **授权**：买家先调 `IERC20.approve(GoodsMarket, amount)` 授权代币
2. **预览**：调 `quote(productId, qty, payToken)` 预览总价
3. **绑定检查**（前端）：查询 `referrerOf(buyer)`
   - 未绑定：结算页提示"本次购买将触发归因绑定到邀请人"
   - 已绑定：结算页展示上线链 + 返利预览

### 5.3 返利预览（previewRebate）

合约方法：`AgentReward.previewRebate(buyer, base)`
- 返回三个数组：`agents[]`（上线地址）、`amounts[]`（返利金额）、`ranks[]`（各层 rank）
- 前端据此渲染返利预览卡

**前端渲染要素**：
- 上线短号 + 姓名
- 上线 rank 徽章
- 返利金额 + 比例（从 REBATE_MATRIX[rank][layer] 读取）
- 跳过层（compression）用琥珀色 + 删除线
- 上卷层用绿色 + "↑上卷"徽章

## 六、级差返利体系

### 6.1 两个维度（核心）

| 维度 | 方向 | 范围 | 决定 |
|---|---|---|---|
| **等级 rank** | 横向（个人） | 0..10 | 返利比例 `rebateBps[rank][layer]` |
| **层级 layer** | 纵向（订单） | 1..rebateLayers | 分润深度位 |

### 6.2 返利矩阵（rebateBps）

```solidity
rebateBps[rank][layer]  // rank 1..10 × layer 1..rebateLayers
```

**配置规则**：
- 单元上限 10000 bps = 100%
- 建议**高 rank 行 ≥ 低 rank 行**（叠加更多权益）
- `rebateLayers` 默认 3，硬上限 `MAX_REBATE_LAYERS=10`
- `basis`：0=原价 gross（默认）/ 1=成交价 net

**示例矩阵**（rank 1..10 × layer 1..3）：

| rank | L1 返利 | L2 返利 | L3 返利 |
|---|---|---|---|
| 1 | 15.0% | 8.0% | 2.0% |
| 2 | 16.0% | 8.5% | 2.2% |
| 3 | 17.0% | 9.0% | 2.5% |
| 4 | 18.0% | 9.5% | 2.8% |
| 5 | 19.0% | 10.0% | 3.0% |
| 6 | 20.0% | 10.5% | 3.3% |
| 7 | 21.0% | 11.0% | 3.6% |
| 8 | 22.0% | 11.5% | 4.0% |
| 9 | 23.0% | 12.0% | 4.4% |
| 10 | 25.0% | 13.0% | 5.0% |

### 6.3 动态压缩（compression）

```solidity
bool public compression = true;  // 默认开
```

**行为**：
- **开**：某层上线 `level=0`（未达标/未激活）→ 跳过，名额上卷给上面下一个合格上线
- **关**：该层作废（浪费一个名额）

**配置**：
- `maxCompressionSkips = 20`（默认，硬上限 100，防 gas 爆炸）

**场景示例**：
```
买家 X 购买 100U 商品，上线链：
  ├─ L1 张三 rank=0 → ❌ 跳过(compression)
  ├─ L2 李四 rank=3 → ✅ 拿 L1 份额(上卷，按李四 rank3 取 layer1 比例 = 17%)
  └─ L3 王五 rank=5 → ✅ 拿 L2 份额(上卷，按王五 rank5 取 layer2 比例 = 10%)
```

### 6.4 多币路由

```solidity
mapping(address => address) public claimFor;  // payToken => RewardClaim
```

- 每个支付币种部署一份独立 RewardClaim 实例（单币）
- `AgentReward.claimFor[payToken]` 路由到对应实例
- 返利与支付同币、精度一致

### 6.5 安全护栏

| 护栏 | 字段 | 默认值 | 作用 | 校验时机 |
|---|---|---|---|---|
| `minRebate` | 去尘阈值 | 0 | 低于此值不发，省 gas | 每层 addReward 前 |
| `maxRebatePerLayer` | 单层封顶 | 0(不限) | 防异常大额 | 每层 addReward 前（amount > cap 则 amount = cap） |
| `maxTotalPerOrder` | 整单池封顶 | 0(不限) | 防资金异常 | **循环外**（整单完成后校验 totalPaid <= cap，超额则 onPurchase 整体 revert） |
| `maxCompressionSkips` | 压缩上卷步数 | 20（硬上限 100） | 防 gas 爆炸 | while 循环的 guard 上限 `maxWalk = rebateLayers + maxCompressionSkips` |

**`maxTotalPerOrder` 校验在循环外**（重要）：
- while 循环内不校验 totalPaid，可能已超额写入 addReward
- 循环结束后才校验 `maxTotalPerOrder == 0 || totalPaid <= maxTotalPerOrder`（`AR: over order cap`）
- 超额时 onPurchase 整体 revert（所有状态回滚，包括已写入的 addReward）
- 由于 onPurchase 被 buy 的 try/catch 包裹，最终 emit RebateHookFailed，**主交易仍成功**

**`maxWalk` 计算**（gas 护栏核心）：
- `maxWalk = rebateLayers + maxCompressionSkips`（合约第 130 行）
- 这是 while 循环的 guard 上限，**不是 maxCompressionSkips 单独**
- 例：rebateLayers=3、maxCompressionSkips=20 → maxWalk=23，总步数不超过 23
- 即使 compression 跳过很多层，总步数受限

### 6.6 防自推与无环

- `cur != buyer`：防自推
- E 链为树结构，天然无环
- guard 步数上限硬保护

## 七、等级与升级体系

### 7.1 等级字段

```solidity
uint256 public constant MAX_LEVEL = 10;
mapping(address => uint256) public level;  // 0..10
```

- 等级 0：未达标代理（无返利资格）
- 等级 1..10：合格代理（按 rank 取 rebateBps）
- **等级是状态**，积分是累积量

### 7.2 升级燃料

| 积分 | 合约 | 来源 | 用途 |
|---|---|---|---|
| **个人积分** | AgentPoints (Soulbound ERC20, decimals=6) | GoodsMarket 购买时 mint / miner 手动 mint | basis=0 时作判据 |
| **团队积分** | AgentLevel.teamPoints | recordPoints 沿 E 链 teamDepth 层累加（含本人） | basis=1 时作判据 |

**AgentPoints 特性**：
- Soulbound：transfer/approve 全 revert（`AP: soulbound, non-transferable` / `AP: soulbound, approvals disabled`）
- mint/burn 按 refId 幂等（`AP: refId used`）
- `mintBatch(to[], amount[], refId[])` 批量铸造：校验 `to.length == amount.length == refId.length`（`AP: len mismatch`，三个数组长度必须一致）；任一 refId 已用即整笔 revert
- mint 时 emit `Transfer(address(0), to, amount)` + `Minted(...)` 事件（ERC20 兼容，钱包/浏览器可显示流水）
- burn 时 emit `Transfer(from, address(0), amount)` + `Burned(...)` 事件
- decimals=6（1.5 积分 = 链上 1500000）
- burn 不受 paused 影响（保证随时可纠错）
- mint/mintBatch 受 paused 影响（`AP: paused`）

**团队积分累加**：
- `teamDepth` 默认 10（可配，范围 1..50）
- 沿 E 链向上累加 teamDepth 层（含本人）
- 由 GoodsMarket 调用（feedTeamPoints=true 时）

### 7.3 升级门槛（双基准）

```solidity
mapping(uint256 => uint256) public threshold;        // 每级门槛值
mapping(uint256 => uint8) public thresholdBasis;     // 每级基准 0=个人 / 1=团队
```

**配置示例**：

| level | threshold | basis | 含义 |
|---|---|---|---|
| 1 | 100 | 0 | 100 个人积分 |
| 2 | 500 | 0 | 500 个人积分 |
| 3 | 1000 | 1 | 1000 团队积分（开始需要团队） |
| 4 | 5000 | 1 | 5000 团队积分 |
| 5 | 20000 | 1 | 20000 团队积分 |
| ... | ... | 1 | 高级都看团队 |
| 10 | 1000000 | 1 | 100 万团队积分 |

**设计哲学**：
- 低级（1-2）：**个人达标** — 自己买货升级即可
- 高级（3-10）：**团队达标** — 必须团队贡献达标才能升级
- **防光杆司令**：高级别必须带团队，不能靠个人消费冲级

### 7.4 升级流程

```
1. 用户 requestUpgrade(targetLevel)
   ├─ 校验 targetLevel > 当前 level 且 ≤ MAX_LEVEL
   ├─ 取目标级 basis:thresholdBasis[targetLevel]
   ├─ 按 basis 取当前 metric:
   │   ├─ b=0: 个人积分 = agentPoints.balanceOf(msg.sender)
   │   └─ b=1: 团队积分 = teamPoints[msg.sender]
   ├─ 快照 metric + basis 入队 UpgradeRequest
   └─ emit UpgradeRequested

2. miner 审核队列(可读 upgradeRequests)
   ├─ 凭快照判断(可信任)
   └─ 或调当前值判断(更严格)

3. miner approveUpgrade(id, enforceThreshold)
   ├─ enforceThreshold=true: 强制链上校验当前 metric >= threshold
   ├─ enforceThreshold=false: 信任 miner 链下审核(凭快照或主观)
   ├─ level[user] = targetLevel
   └─ emit UpgradeApproved

4. 或 miner rejectUpgrade(id)
   └─ emit UpgradeRejected

5. 或 miner minerSetLevel(user, level) 直接设定
   └─ 用于购买级别服务商品审核 / 手动补录
```

**快照防作弊**：
- 申请时快照 metric
- miner 审核期间即使积分波动，也能凭快照判断
- `enforceThreshold` 可选是否强制链上校验当前值

### 7.5 积分 burn（回收）

| 场景 | 是否自动 burn | 处理 |
|---|---|---|
| 退货时已 mint 的积分 | ❌ 不自动（try/catch，mint 失败不影响主交易） | 待业务确认是否手动 burn |
| 纠错场景 | ❌ 不自动 | miner 手动 burn（不受 paused 影响） |
| 降级场景 | ❌ 不自动 | miner 手动 burn |

**burn 方法**：
```solidity
function burn(address from, uint256 amount, bytes32 refId) external onlySource
```

### 7.6 团队积分不回退（重要）

> **合约层没有扣减 teamPoints 的方法**。`recordPoints` 只加不减，退货时**不会自动扣减团队积分**。已累计的团队积分**永久保留**。

**影响**：
- 退货后已累加的团队积分仍在
- 防刷策略需在前端/后端层实现（如限制频繁退货）
- 或 miner 通过 `rejectUpgrade` 驳回升级申请来间接控制

### 7.7 等级不自动降级（重要）

> **等级 `level[addr]` 只能通过 `minerSetLevel(user, newLevel)` 手动调整**。即使个人积分或团队积分低于当前 level 门槛，**等级不会自动降级**。

**影响**：
- 用户达标升级后，即使后续积分被 burn，等级仍保留
- 降级需 miner 主动调 `minerSetLevel`
- 矿工责任重大，需要监控异常情况

## 八、奖励领取体系（RewardClaim）

### 8.1 额度制模型

```solidity
mapping(address => uint256) public allocation;     // 净额度
mapping(address => uint256) public claimedAmount;  // 已领
// claimable = allocation - claimedAmount
```

- 用户随时自领（claim）
- **无中继、无 miner 手动发放**
- 单币实例：构造锁定一个 `token`

### 8.2 两类撤销

| 撤销类型 | 方法 | 场景 | 行为 | 校验细节 |
|---|---|---|---|---|
| **未领撤销** | `revokeReward(refId)` | 活动到期/防刷单 | 只回收未领部分，已领动不了 | 校验用户整体 `unclaimed = allocation[user] - claimedAmount[user] >= r.amount`（`RC: already claimed`）；非 miner rewarder 同时扣减 `spent[rewarder] -= r.amount`（返还预算额度） |
| **已领退回** | `returnReward(refId, amount)` | 退货退款前置 | 用户主动转回已领奖励币 | 校验 `amount > 0 && r.returnedAmount + amount <= r.amount`（`RC: over return`）；支持分多次部分退回，累计不超过奖励金额 |

**重要行为说明**：
- `revokeReward` 校验的是**用户整体 unclaimed**，不是**单条奖励的 unclaimed**。如果用户有多条奖励且整体 unclaimed 充足，即使这条特定奖励已被领取，revokeReward 也不会 revert（需注意此语义）
- `revokeReward` 对非 miner rewarder 会扣减 `spent`（恢复预算），miner rewarder 调用的奖励不扣减（miner 不受 budget 限制）
- `returnReward` 不校验 `r.revoked` 状态（即使奖励已撤销，用户仍可 returnReward，详见 19.10）

### 8.3 预算护栏

```solidity
mapping(address => uint256) public budget;  // 每个 rewarder 上限
mapping(address => uint256) public spent;    // 已用
// addReward 时 spent + amount <= budget（miner 除外）
// revokeReward 时 spent -= r.amount（仅非 miner rewarder 且 spent >= r.amount）
```

### 8.4 偿付会计

| 字段 | 含义 |
|---|---|
| `totalAllocated` | 已分配总额 |
| `totalClaimed` | 已领取总额 |
| `totalReturned` | 已退回总额 |
| `outstanding` | 未领额度 = 已分配 - 已领 |
| `shortfall()` | 偿付缺口（>0 表示奖池资金不足） |

**addReward 内置偿付校验**：
```solidity
require(token.balanceOf(address(this)) >= totalAllocated - totalClaimed, "RC: underfunded");
```
- 合约必须已充值到能覆盖全部未领额度
- 否则拒绝写入

### 8.5 盈余回收

```solidity
function rescue(uint256 amount) external onlyMiner
```
- 只能提走"余额 - 未领额度"的盈余
- 动不了用户应得
- 提至 treasury

### 8.6 多币部署

- 每个支付币种一份 RewardClaim 实例
- 由 `AgentReward.claimFor[payToken]` 路由
- RewardClaim.token 必须等于 payToken
- 精度一致

## 九、退货流程

### 9.1 完整流程

```
1. 买家 returnRequest(refId, codeId)
   ├─ 校验 `o.exists && !o.returned`（GM: bad order）
   ├─ 校验 `o.buyer == msg.sender`（GM: not buyer，只有买家能申请）
   ├─ 校验 `codeOwner[codeId] == msg.sender && codeProduct[codeId] == o.productId`（GM: bad code）
   ├─ 创建 ReturnReq 入队
   └─ emit ReturnRequested

2. 买家前置（**业务流程要求，非合约硬条件**）: 若已领奖励,先 returnReward(refId, amount)
   ├─ 需先 approve RewardClaim 合约(让 returnReward 内部 transferFrom)
   ├─ 调 RewardClaim.returnReward(refId, amount) 转回已领奖励币
   ├─ 校验 `amount > 0 && r.returnedAmount + amount <= r.amount`（RC: over return，可分多次部分退回）
   └─ RewardClaim 记 returnedAmount

3. miner 审核 getReturnRequest(id)
   ├─ 查退货申请详情
   ├─ **业务责任**：miner 应先检查 returnReward 状态，确认已领奖励已退回
   └─ 决定 approveReturn 或 rejectReturn

4. miner approveReturn(id, refundAmount)
   ├─ **状态标记先于 revokeOrder**（隐藏行为，重要）：
   │   ├─ `r.open = false`（合约第 283 行，先标记关闭）
   │   └─ `o.returned = true`（合约第 285 行，先标记整单已退）
   ├─ 调 `try agentReward.revokeOrder(r.refId) {} catch {}`（**try/catch 保护**，失败不影响 approveReturn）
   │   └─ revokeOrder 内逐层 try/catch RewardClaim.revokeReward
   │       ├─ 已领的层自动跳过（revokeReward revert `RC: already claimed`）
   │       └─ 未领的层自动撤销
   ├─ 回收唯一码(codeStatus: 2→3, codeOwner 清空)
   ├─ 退款 transfer 到买家（refundAmount > 0 时；= 0 时跳过 transfer）
   └─ emit ReturnApproved

5. 或 miner rejectReturn(id)
   └─ emit ReturnRejected
```

### 9.1.1 ⚠️ P0 漏洞：直写奖励在退货时无法自动撤销（严重）

**合约事实**：

- **直写奖励的 refId 生成**（GoodsMarket.buy 第 206 行）：
  ```solidity
  IRewardClaim(rc[i].claim).addReward(msg.sender, amt, keccak256(abi.encode(refId, uint8(82), i)));
  ```
  - 直写奖励的 `directRefId = keccak256(abi.encode(refId, 82, i))`，其中 `i` 是 rewards[] 数组下标
  - 该 `directRefId` **只传给 RewardClaim.addReward，不会写入 AgentReward._orderRefIds**

- **approveReturn 的撤销逻辑**（GoodsMarket.approveReturn 第 286 行）：
  ```solidity
  if (address(agentReward) != address(0)) { try agentReward.revokeOrder(r.refId) {} catch {} }
  ```
  - approveReturn 只调 `agentReward.revokeOrder(refId)`
  - `revokeOrder` 遍历的是 `AgentReward._orderRefIds[refId]`（[AgentReward 第 165 行](file:///d:/HelloWorld/Company_Project/Node/pm/文档库/03-方案/AgentReward.md#L165)）
  - **该数组只 push 级差返利的 layerRefId**（onPurchase 内第 147 行），**完全不包含直写奖励的 directRefId**

**后果**：
- 商品配置了 `addRewardCfg` 直写奖励 → 买家购买后获得直写奖励额度
- 买家申请退货 → 矿工 approveReturn → `revokeOrder` 只撤销级差返利，**直写奖励完全不会被撤销**
- 买家仍可去 RewardClaim 领走该直写奖励 → **项目资金流失**

**P0 级修复方案（矿工后台硬性流程）**：

矿工在 `approveReturn` 之前必须执行以下流程，**前端硬编码、不可跳过**：

```
1. 查商品配置：rewardsOf(productId) 拿到所有 RewardCfg.claim 实例地址
2. 对每条配置计算 directRefId：
   for (uint i = 0; i < rewards.length; i++) {
       bytes32 directRefId = keccak256(abi.encode(refId, uint8(82), i));
       address claim = rewards[i].claim;
3. 查每条直写奖励状态：RewardClaim(claim).rewards(directRefId)
   ├─ 已 revoked=true → 跳过
   ├─ 未 revoked 且 returnedAmount < amount → 需处理
4. 对未撤销的直写奖励，尝试 revokeReward：
   ├─ 若 unclaimed >= amount → 调 RewardClaim(claim).revokeReward(directRefId) 强制撤销
   └─ 若 unclaimed < amount（用户已 claim 部分/全部）→ 必须 returnReward（用户主动退回）
       ├─ 用户不配合 → 禁用 approveReturn 按钮，转人工处理
       └─ 用户 returnReward 后 → 校验 returnedAmount >= amount → 解禁 approveReturn
5. 所有直写奖励均 revoked=true 或 returnedAmount>=amount → 才允许 approveReturn
```

**关键边界**：
- `revokeReward` 要求 `unclaimed >= r.amount`（RewardClaim 第 139 行），即奖励必须完全未领才能强制撤销
- 已 claim 部分的奖励只能通过 `returnReward` 让用户主动退回
- **矿工后台前端必须严格校验 `returnedAmount >= amount`**，否则 approveReturn 后该部分奖励永久无法追回

### 9.1.2 ⚠️ P1 漏洞：approveReturn 不校验奖励已退回状态

**合约事实**：

`approveReturn` 源码（第 280-293 行）：
- **完全没有校验** `RewardClaim.rewards[refId].returnedAmount`
- **完全没有校验** `RewardClaim.rewards[refId].revoked`
- 直接执行 `transfer(r.buyer, refundAmount)`

更严重的是：`revokeOrder` 内部对 `revokeReward` 的 try/catch：
```solidity
for (uint256 i = 0; i < ids.length; i++) {
    try IRewardClaim(claim).revokeReward(ids[i]) {} catch {}  // ← 失败被吞
}
```

- 已 claim 的奖励调 revokeReward 会 revert `RC: already claimed`
- 该 revert 被 try/catch 吞掉，approveReturn 继续执行退款
- **用户既拿奖励又拿退款，合约层完全不阻止**

**P1 级修复方案（r9-admin 前端硬编码校验）**：

```typescript
// 矿工审核退货前的强制校验逻辑
async function canApproveReturn(refId: string, productId: number): Promise<{ok: boolean; reason?: string}> {
  // 1. 校验级差返利是否已撤销/已退回
  const layerRefIds = await agentReward.orderRefIdsOf(refId);
  for (const layerRefId of layerRefIds) {
    const r = await rewardClaim.rewards(layerRefId);
    if (!r.revoked && r.returnedAmount < r.amount) {
      return { ok: false, reason: `上线返利 ${layerRefId} 未退回` };
    }
  }

  // 2. 校验直写奖励是否已撤销/已退回（见 9.1.1）
  const rewardCfgs = await goodsMarket.rewardsOf(productId);
  for (let i = 0; i < rewardCfgs.length; i++) {
    const directRefId = keccak256(encodePacked(refId, 82, i));
    const r = await RewardClaim(rewardCfgs[i].claim).rewards(directRefId);
    if (r.user !== ZeroAddress && !r.revoked && r.returnedAmount < r.amount) {
      return { ok: false, reason: `直写奖励 #${i} 未退回` };
    }
  }

  return { ok: true };
}

// 矿工界面按钮状态
<Button disabled={!canApproveReturn.ok} onClick={approveReturn}>
  {canApproveReturn.ok ? '同意退货' : `阻止：${canApproveReturn.reason}`}
</Button>
```

### 9.2 关键约束

- **"已领奖励必须先退回"是业务流程要求，非合约硬条件**：
  - 合约层 `approveReturn` **不校验**已领奖励是否已退回
  - 如果 miner 未确认就 approveReturn，revokeOrder 内的 revokeReward 对已领层 revert（`RC: already claimed`），但被 try/catch 捕获跳过
  - **后果**：用户可能既拿了奖励又拿了退款（合约不阻止，依赖 miner 审核责任）
  - **前端必须**：在 miner 审核界面明确展示"已领奖励状态"，并要求 miner 勾选"已确认用户已退回已领奖励"才能继续 approveReturn
- **approveReturn 隐藏行为**：`r.open = false` 和 `o.returned = true` 在 `revokeOrder` 之前设置，即使 revokeOrder 失败也标记为已退
- **关系不变**：E 链 referrerOf 永久，退货不退关系
- **码状态变 3**：退货后**永久作废**，合约无重置方法，无法再次 importCodes
- **refundAmount 由 miner 决定**：合约不校验金额合理性，可以是 0、部分、全额、超额，矿工责任重大
- **refundAmount 来源**：从 GoodsMarket 合约余额中转给买家（非 treasury）
- **refundAmount 超额受合约余额限制**：若 refundAmount > GoodsMarket 该 token 余额，`IERC20.transfer` 失败 → revert `GM: refund fail`
- **refundAmount=0 的行为**：跳过 transfer，但 approveReturn 其他操作正常执行（标记关闭、回收码、emit ReturnApproved），适用于"仅回收码不退款"场景

### 9.3 部分退货的严重限制（重要）

> **合约层 `returnRequest` 只支持单码退货，且 approveReturn 后整个订单标记为 `returned=true`，后续其他码无法再申请退货。**

**合约事实**（approveReturn 第284-285行）：
```solidity
Order storage o = orders[r.refId];
o.returned = true;  // 整单标记为已退
```

**实际行为**：
- 买家可以批量 `returnRequest` 多个码入队
- 但只要 miner 审核通过一个 `approveReturn`，整个订单标记为 returned
- 后续其他码的 `returnRequest` 会因 `!o.returned` 校验失败而 revert
- **实际只能退一个码**

**前端设计建议**：
- 退货流程改为"整单退货"概念
- 一个订单只允许提交一次退货申请
- 如需部分退货，矿工通过 `refundAmount` 控制退款金额（如只退该码对应金额）

**⚠️ 致命红线：revokeOrder 是按整个订单撤销返利的**

> Gemini 审查指出的核心风险：`revokeOrder(refId)` 输入的是订单 refId，**不是 codeId**。如果合约层允许部分退货，approveReturn 会无差别撤销整个订单的全部返利。

**当前合约已通过 `o.returned` 标记防止部分退货**：
- 第一次 returnRequest + approveReturn → `o.returned = true`
- 后续 returnRequest → revert `GM: bad order`
- **所以"5 件退 1 件导致全部 5 件返利被撤销"的场景在合约层不会发生**

**但业务兜底方案必须明确**（应对买家坚持只退部分）：

| 方案 | 流程 | 优劣 |
|---|---|---|
| **方案 A：整单退 + 重新买剩余** | 1. 矿工 approveReturn 整单退款<br>2. 买家重新购买剩余 qty-1 件<br>3. 钱货两清后重新发码 | ✅ 合约支持<br>❌ 用户体验差，需两次交易 |
| **方案 B：矿工按比例退款** | 1. 矿工 approveReturn(id, refundAmount=单件价格×1)<br>2. 整单标记 returned<br>3. 码全部回收（含未退的 4 件） | ✅ 一次操作<br>❌ 矿工需手动计算退款<br>❌ 买家损失剩余 4 件码（需链下补偿） |
| **方案 C：纯链下处理** | 1. 矿工直接转币给买家（不走 approveReturn）<br>2. 链上码状态不变<br>3. 链下记录退货 | ✅ 不影响链上状态<br>❌ 完全信任矿工<br>❌ 返利无法自动撤销 |

**推荐方案 A**：
- 业务上对外宣传"整单退货"
- 买家坚持只退部分 → 引导走方案 A（整单退 + 重新买剩余）
- 方案 B/C 仅作应急方案，不在常规流程中提供

**绝对禁止**：
- ❌ 前端不要提供"部分退货"按钮（即使合约层有 returnRequest）
- ❌ 不要尝试通过多次 returnRequest + 多次 approveReturn 实现部分退货（合约已禁此路径）

### 9.4 挂单中的码退货问题

**合约漏洞**：returnRequest 不检查 `listings[codeId].active`
- 买家把已购买码挂单后，仍可申请退货
- approveReturn 后 `listings[codeId].active` 仍为 true，但 `codeOwner=0`
- 后续 `buyListed` 会因 `codeOwner[codeId] == l.seller` 校验失败而 revert

**前端必须处理**：
- 申请退货前检查码是否挂单中
- 若挂单中，提示先 `cancelListing`
- 或在 UI 层禁止挂单中的码申请退货

## 十、二手转卖市场

### 10.1 转卖两种方式

| 方式 | 方法 | 是否收费 | 场景 |
|---|---|---|---|
| **直转** | `transferItem(codeId, to)` | ❌ 不收费 | 赠送 / 私下交易 |
| **挂单** | `listItem(codeId, payToken, price)` + `buyListed(codeId)` | ✅ 收取 `resaleFeeBps` | 公开二手市场 |

**buyListed 手续费公式**（与 [20.5](#205-buylisted-的-fee-计算公式) 对齐）：

```solidity
uint256 fee = (l.price * products[pid].resaleFeeBps) / 10000;  // 基于"挂单价"而非原商品价
uint256 toSeller = l.price - fee;                                // 卖家实得
// 两个 transferFrom：
// 1. transferFrom(买家 → 卖家, toSeller)   "GM: pay seller fail"
// 2. transferFrom(买家 → treasury, fee)     "GM: pay fee fail"（fee=0 时跳过）
```

**关键点**：
- `fee` 基于**挂单价** `l.price`，不是原商品价
- `resaleFeeBps` 是商品级配置（`createProduct` / `updateProduct` 时设置）
- 买家需先 `IERC20.approve(GoodsMarket, l.price)` 授权代币，**授权金额需覆盖整个挂单价**（含手续费部分）
- `fee=0` 时跳过第二个 transferFrom（避免无意义调用）
- **buyListed 不生成新订单**：不调 `orderCounter++`，不写 `orders[refId]`，仅触发 `ItemResold` 事件

### 10.2 挂单流程

```
1. 卖家(码持有人) listItem(codeId, payToken, price)
   ├─ 创建 Listing{seller, payToken, price, active=true}
   └─ 码仍挂在卖家名下,但标记为"挂单中"

2. 买家 buyListed(codeId)
   ├─ transferFrom(买家 → 卖家, price - fee)
   ├─ transferFrom(买家 → treasury, fee)
   ├─ 码从卖家 → 买家(_moveCode)
   ├─ Listing.active = false
   └─ emit ItemResold

3. 或卖家 cancelListing(codeId)
   └─ Listing.active = false
```

### 10.3 关键特性

- **不触发分润**：转卖不走 `AgentReward.onPurchase`，沿 E 链不分润
- **不触发归因**：转卖不调 bindOnPurchase，关系不变
- **手续费可配**：`resaleFeeBps` 逐商品配置（如 500=5%）
- **自由定价**：卖家自定价格，无区间限制
- **多币支持**：挂单时指定 `payToken`

### 10.4 转卖前置操作与限制

**buyListed 前置**：
- 买家需先 `IERC20.approve(GoodsMarket, price)` 授权代币
- 授权金额需覆盖 `price`（含手续费部分）
- 与购买商品 `buy` 的授权一致

**transferItem 限制**：
- **不能转挂单中的码**（合约校验 `!listings[codeId].active`）
- 必须先 `cancelListing` 才能转赠
- 已退货的码（codeStatus=3）无法转赠

**buyListed 限制**：
- **卖家不能自买**（`msg.sender != l.seller`）
- 挂单信息与码所有权必须一致（`codeOwner[codeId] == l.seller`）

### 10.5 转卖市场 UI

- 筛选：商品分类 / 价格区间 / 支付币种
- 列表：瀑布流展示挂单
- 详情：卖家短号 + 码状态 + 价格 + 手续费
- 购买：调 `buyListed` 一步完成

## 十二、部署与依赖

### 12.1 部署顺序（依赖链）

```
1. AgentPoints（无依赖）
2. RewardClaim（无依赖，每币一份）
3. AgentLevel（依赖 AgentPoints + E）
4. AgentReward（依赖 E + AgentLevel + RewardClaim）
5. GoodsMarket（依赖以上全部；最后回填）
```

### 12.2 部署后回填

**双向授权链路**（缺一不可，否则对应钩子 revert）：

- `GoodsMarket.setHooks`：回填 AgentReward / AgentPoints / AgentLevel 地址
- `AgentReward.setRegistry` / `setAgentLevel`：回填依赖地址
- `AgentReward.setClaimFor(payToken, claim)`：路由每个支付币到对应 RewardClaim
- **`AgentReward.setRewarder(GoodsMarket, validUntil)`**：授权 GoodsMarket 触发 `onPurchase`（**遗漏此项会导致 GoodsMarket.buy 调 onPurchase 时 revert `AR: not rewarder`，被 try/catch 捕获后 emit RebateHookFailed，返利无法触发**）
- `AgentLevel.setAgentPoints` / `setRegistry`：回填依赖地址
- `AgentLevel.setFeeder(GoodsMarket, validUntil)`：授权 GoodsMarket 喂团队积分
- `AgentPoints.setPointsSource(GoodsMarket, validUntil)`：授权 GoodsMarket 铸造积分
- `RewardClaim.setRewarder(AgentReward, validUntil)`：授权 AgentReward 写额度
- `RewardClaim.setRewarder(GoodsMarket, validUntil)`：授权 GoodsMarket 直写奖励

**RewardClaim 资金补充**（部署后必须）：
- 向每个 RewardClaim 实例充值对应 token（`token.transfer(RewardClaim_addr, amount)`）
- 充值后 `shortfall()` 应返回 0
- 充值不足会导致 `addReward` revert `RC: underfunded`（直写奖励场景导致整单 revert，上线返利场景导致 emit RebateHookFailed）

### 12.3 灵活部署能力

```solidity
function setHooks(...) external onlyMiner
```

- GoodsMarket 部署时可先传 0x0
- 事后用 `setHooks` 回填联动合约地址
- **允许分阶段上线**

### 12.4 多 miner 管理

- `MAX_MINERS = 3`
- 至少保留 1 个 miner
- `setMiner(addr, bool)` 增减

### 12.5 授权时窗

```solidity
rewarderValidUntil / pointsSourceValidUntil / feederValidUntil
```

| validUntil 值 | 语义 |
|---|---|
| 0 | 撤销授权 |
| max (type(uint256).max) | 长期有效 |
| 自定义时间戳 | 限时授权 |

## 十四、钩子失败处理

### 14.1 try/catch 韧性设计

GoodsMarket.buy 中调 AgentPoints / AgentLevel / AgentReward 用 try/catch：
- **主交易（购买+发码）原子成功**
- 钩子失败仅 emit `RebateHookFailed(refId)`
- 买家已付款但上线未拿返利

### 14.2 失败补救方案

| 方案 | 操作 | 适用 |
|---|---|---|
| **方案 A：miner 手动补录** | miner 调 `AgentReward.onPurchase` 重试 | 链上钩子异常 |
| **方案 B：miner 直接发奖励** | miner 调 `RewardClaim.addReward` 直接写额度 | 钩子完全不可用 |
| **方案 C：线下补偿** | 链下对账后线下转账 | 链上无法补救 |

### 14.3 前端感知

- 监听 `RebateHookFailed` 事件
- 矿工后台显示失败列表
- 矿工审核后手动补救

### 14.4 ⚠️ P1 漏洞：AgentPoints/AgentLevel 静默失败（无事件可监听）

**合约事实**（GoodsMarket.buy 第 213-215 行）：

```solidity
try agentPoints.mint(msg.sender, pts, refId) {} catch {}      // ← 空 catch，无 emit
try agentLevel.recordPoints(msg.sender, pts) {} catch {}        // ← 空 catch，无 emit
```

**与 AgentReward.onPurchase 失败对比**：

| 钩子 | 失败时的事件 | 前端能否感知 |
|---|---|---|
| AgentReward.onPurchase | `emit RebateHookFailed(refId)` | ✅ 可监听 |
| **AgentPoints.mint** | **无任何事件** | ❌ 完全静默 |
| **AgentLevel.recordPoints** | **无任何事件** | ❌ 完全静默 |

**后果**：
- 购买主交易成功（已收款、已发码、已触发直写奖励）
- 但**个人积分和团队积分未下发**，且矿工**完全无感知**
- 用户可能购买多次但积分一直为 0，影响升级

**P1 级修复方案（后端异步对账任务）**：

由于合约层无法修改抛出事件，**必须由后端建立对账任务**：

```typescript
// 异步对账任务（每小时/每区块执行）
async function reconcilePointsMint() {
  // 1. 拉取所有 Purchased 事件
  const purchasedEvents = await goodsMarket.queryFilter('Purchased', startBlock, endBlock);

  for (const evt of purchasedEvents) {
    const { refId, buyer, productId, qty } = evt.args;

    // 2. 计算理论应发积分
    const product = await goodsMarket.products(productId);
    if (product.pointsPerUnit === 0) continue;
    const expectedPts = product.pointsPerUnit * qty;

    // 3. 查同区块同 refId 的 AgentPoints.Minted 事件
    const mintedEvents = await agentPoints.queryFilter('Minted', evt.blockNumber, evt.blockNumber);
    const matched = mintedEvents.find(e => e.args.refId === refId && e.args.to === buyer);

    if (!matched) {
      // 4.1 个人积分未下发 → 告警
      logger.error(`AgentPoints.mint 静默失败: refId=${refId}, buyer=${buyer}, expected=${expectedPts}`);
      // 5.1 由 source 调用 mint 用新 refId 重发（refId 已 used 不能重用）
      // 注意：需要后端记录原始 refId 对应关系，使用新 refId = keccak256(abi.encode(refId, "retry", retryCount))
    }

    // 6. 查同区块的 AgentLevel.PointsRecorded 事件
    if (product.feedTeamPoints) {
      const recordedEvents = await agentLevel.queryFilter('PointsRecorded', evt.blockNumber, evt.blockNumber);
      const matchedTeam = recordedEvents.find(e => e.args.member === buyer && e.args.amount === expectedPts);

      if (!matchedTeam) {
        // 7.1 团队积分未累加 → 告警
        logger.error(`AgentLevel.recordPoints 静默失败: refId=${refId}, member=${buyer}, expected=${expectedPts}`);
        // 8.1 由 feeder 调用 recordPoints 重发（recordPoints 无 refId 幂等，可直接重发相同 amount）
      }
    }
  }
}
```

**对账关键点**：
- `AgentPoints.mint` 成功时 emit `Minted(to, amount, refId)` + `Transfer(0, to, amount)`，可查事件验证
- `AgentLevel.recordPoints` 成功时 emit `PointsRecorded(member, amount, msg.sender)`，可查事件验证
- 重发时 `AgentPoints.mint` 需用**新 refId**（原 refId 已 used，会 revert `AP: refId used`）
- 重发时 `AgentLevel.recordPoints` 可直接重发相同 amount（无幂等校验）

**告警阈值**：
- 单次静默失败 → 告警 + 自动重发
- 连续多次静默失败 → 升级告警，检查 AgentPoints/AgentLevel 是否被暂停

| **AgentPoints** | mint / mintBatch | **burn 不受影响**（保证纠错） / setPointsSource / setMiner / setPaused / 读取视图 |
| **AgentLevel** | requestUpgrade | **approveUpgrade / rejectUpgrade / minerSetLevel 不受影响**（保证审核可继续） / **recordPoints 不受影响**（内部 require isFeeder，保证团队积分累加） / setRebateBps / setRebateBpsBatch / setRebateLayers / setBasis / setCompression / setTeamDepth / setThreshold / setFeeder / setAgentPoints / setRegistry / setMiner / setPaused / 读取视图 |
| **AgentReward** | onPurchase | **revokeOrder 不受影响**（保证退货撤链） / setClaimFor / setKnobs / setRewarder / setRegistry / setAgentLevel / setMiner / setPaused / previewRebate / 读取视图 |
| **RewardClaim** | addReward / claim | **returnReward 不受影响**（保证退货退款） / **revokeReward 不受影响**（保证撤销） / setRewarder / setBudget / setTreasury / rescue / setMiner / setPaused / 读取视图 |

**应急流程**：
1. 发现异常 → 暂停对应合约（不影响该合约的关键运维函数）
2. 矿工评估影响
3. 修复后解除暂停
4. 手动补录失败钩子

**暂停语义说明**：
- 暂停是 **业务熔断**，不是 **运维锁定**。暂停期间矿工仍可配置参数、审核退货、撤销奖励、补充资金
- GoodsMarket 暂停时，**已挂单的 cancelListing 仍可调**（用户可取消挂单）
- GoodsMarket 暂停时，**returnRequest / approveReturn / rejectReturn 仍可调**（退货流程不中断）
- RewardClaim 暂停时，**returnReward / revokeReward 仍可调**（退货退款与撤销链路不中断）
- AgentReward 暂停时，**revokeOrder 仍可调**（退货撤链不中断）

## 十九、已知漏洞与限制（合约层）

> 本章节严格基于合约源码，列出所有设计限制和潜在漏洞，前端/后端必须据此设计防护。

### 19.1 两种"无 try/catch"的失败行为完全不同（严重）

**核心区分**：直写奖励与上线返利虽然都是"addReward 内部无 try/catch"，但因为**调用层级不同**，失败后果完全相反。

| 调用 | 调用层级 | addReward 失败的 revert 传播路径 | 最终结果 |
|---|---|---|---|
| 直写奖励 `RewardClaim.addReward` | buy 函数内**直接调用** | addReward revert → **buy revert**（无 try/catch 拦截） | 整单 revert，购买失败、码未分配、付款回滚 |
| 上线返利 `RewardClaim.addReward` | onPurchase 内调用，**onPurchase 被 buy 的 try/catch 包裹** | addReward revert → onPurchase revert → **被 buy 的 try/catch 捕获** → emit RebateHookFailed | **主交易成功**（购买+发码+直写奖励均生效），仅返利未发 |

**对比**：AgentPoints.mint / AgentLevel.recordPoints / AgentReward.onPurchase 都有 try/catch 保护；直写奖励是 buy 内唯一无 try/catch 的钩子，**最危险**。

**防护**：
- 前端实时监控所有 RewardClaim 的 `shortfall()`
- 矿工及时充值奖池
- 商品配置错误时立即下架
- 监听 `RebateHookFailed` 事件 → 返利未发但购买成功，运营补打返利
- 直写奖励/购买 revert → 购买失败，前端提示买家重试或换支付币种

### 19.2 退货后的码永久作废

**合约事实**：`importCodes` 要求 `codeStatus==0`，已退码 `codeStatus==3` 无法再次导入，合约无重置方法。

**影响**：退货后的码永久作废，矿工只能 importCodes 新码补货。

### 19.3 部分退货实际不支持

**合约事实**：`approveReturn` 后 `orders[refId].returned=true`，后续 `returnRequest` 因 `!o.returned` 校验失败。

**影响**：一个订单只能退一个码，无法多码退货。

### 19.4 挂单中的码退货状态不一致

**合约事实**：`returnRequest` 不检查 `listings[codeId].active`，`approveReturn` 不清理 listings。

**影响**：挂单中的码被退货后，挂单信息残留，后续 `buyListed` revert。

### 19.5 团队积分与等级不自动回退

**合约事实**：
- `recordPoints` 只加不减，无扣减方法
- 退货时不扣减 teamPoints
- `level` 只能 `minerSetLevel` 手动调整

**影响**：刷单者可通过频繁购买+退货累加 teamPoints 升级，需前端限制。

**⚠️ 真实刷单攻击路径（必读）**：

```
1. 刷子用 100 个小号（L4-L103）注册到大号 L3 名下
2. 大号 L3 是所有小号的直接上线 → teamPoints[L3] 快速累积
3. 100 个小号分别买货 → 每次购买 recordPoints 沿 E 链累加到 L3
4. teamPoints[L3] 达标 → L3 升级到 L8/L9/L10
5. 小号整单退货 → 钱退回，但 teamPoints[L3] 不扣减
6. 大号 L3 保持高 rank，享受高比例分润
7. 后续真实买家进入 L3 名下 → L3 持续拿高额返利
```

**P2 级风控方案（r9-admin 后台必须建立）**：

| 风控维度 | 校验逻辑 | 触发动作 |
|---|---|---|
| **退货率监控** | 同一上线名下下级退货率 > 60% | 标记可疑，审核升级申请时 enforceThreshold=true |
| **升级阈值强制校验** | 可疑地址 requestUpgrade 时 | miner 调 approveUpgrade(id, true) 强制校验当前 teamPoints 是否达标 |
| **teamPoints 与实际消费背离** | teamPoints[X] 远大于 X 名下非退货订单总额 | 标记可疑，调 minerSetLevel 降级 |
| **批量小号识别** | 同一上级名下短期内绑定大量下级（如 1 小时内 50+） | 标记刷单团伙 |
| **退货后降级** | 矿工审核确认刷单 | 调 `AgentLevel.minerSetLevel(刷子地址, 0)` 强制降级 |
| **退货冷却期** | 买家购买后 N 天内不得退货 | 前端限制（业务规则，非合约） |

**关键提醒**：
- 合约层无法自动扣减 teamPoints，**所有风控必须在矿工后台链下实现**
- `minerSetLevel` 是唯一的链上降级手段，矿工必须有权限且敢于使用
- 建议每周/每月跑一次 `teamPoints[addr] / 实际有效订单金额` 比例扫描，识别异常地址

### 19.6 previewRebate race condition

**合约事实**：previewRebate 调用时的上线 rank 可能与 onPurchase 实际执行时不一致（区块链 inherent）。

**影响**：前端展示的返利预览可能与实际不符，需提示"以链上实际分润为准"。

### 19.7 矿工权限过大（信任模型）

**合约事实**：
- `refundAmount` 完全由 miner 决定
- `enforceThreshold=false` 可通过未达标升级申请
- `minerSetLevel` 可直接设定任意用户等级
- `withdraw` 可提取合约全部余额

**⚠️ 真实攻击场景：approveReturn 抽干合约攻击**

> 这是最严重的资金安全风险。miner 钱包被盗或内部作恶，可瞬间抽干 GoodsMarket 合约全部余额。

**攻击路径**：
1. 攻击者控制 miner 钱包（钱包被盗或内部作恶）
2. 攻击者用小号买 1 件便宜商品 → 创建订单 refId
3. 攻击者用小号 returnRequest 申请退货
4. 攻击者用 miner 身份调 `approveReturn(id, refundAmount=GoodsMarket合约全部USDT余额)`
5. 合约校验：`refundAmount > 0` 且 `IERC20.transfer(r.buyer, refundAmount)` 成功（因为合约余额足够）
6. **整个 GoodsMarket 合约余额被转到攻击者小号**

**合约层无任何防护**：
- `approveReturn` 不校验 `refundAmount` 上限
- `approveReturn` 不校验 `refundAmount` 与订单金额的关系
- `approveReturn` 不校验 `refundAmount` 与 GoodsMarket 余额的关系（仅 transfer 失败才 revert）

**P1 级修复方案（必须执行）**：

| 防护层 | 措施 | 说明 |
|---|---|---|
| **多签钱包** | miner 地址必须是多签钱包（如 Gnosis Safe 2/3） | 单个私钥泄露无法操作 |
| **refundAmount 上限校验** | r9-admin 前端硬编码：`refundAmount <= 订单 paid * 1.5` | 防止超额退款 |
| ** approveReturn 冷却期** | 同一 miner 1 小时内 approveReturn 金额 > 阈值 → 需第二 miner 复核 | 大额操作双人确认 |
| ** withdraw 多签** | `withdraw` 必须走多签提案+延迟执行（如 24h timelock） | 防止瞬间抽干 |
| **操作审计** | 所有 miner 操作上链 + 链下日志双重记录 | 事后追溯 |
| **miner 数量限制** | 合约 `MAX_MINERS=3`，建议实际部署 3 个多签钱包 | 避免单点故障 |

**多签钱包部署建议**：
- 使用 Gnosis Safe（以太坊主流多签方案）
- 阈值设为 2/3（3 个 signer 中需 2 个同意）
- signer 由不同人员保管（如 CEO + CTO + 财务）
- 所有 miner 操作都通过多签合约发起，不直接用 EOA



### 19.8 配置类操作的覆盖式语义

**合约事实**：
- `setTiers`：先 delete 再 push，覆盖整个折扣配置
- `clearRewardCfg`：删除全部奖励配置
- `updateProduct`：不能改 name

**影响**：配置变更需谨慎，建议前端确认弹窗 + 二次校验。

### 19.9 teamDepth 与 rebateLayers 不同步

**合约事实**：
- `teamDepth` 默认 10（团队积分累加层数）
- `rebateLayers` 默认 3（分润层数）

**影响**：团队积分可能累加给 rebateLayers 之外的上线（即不分润但累加积分），这是设计如此。

### 19.10 revoked 奖励仍可 returnReward

**合约事实**：`returnReward` 不检查 `r.revoked` 状态。

**影响**：已撤销未领的奖励（allocation 已扣减），用户仍可主动退回已领部分，语义容易混淆但功能正常。

## 二十、附录：GoodsMarket internal 函数与算法实现

> 本章节列出 GoodsMarket 合约的 4 个 internal 辅助函数及其算法实现细节，是码台账维护、阶梯折扣计算、码转移的核心。

### 20.1 `_checkAccess(address a)` — 黑白名单校验

```solidity
function _checkAccess(address a) internal view {
    require(!banned[a], "GM: banned");
    if (whitelistEnabled) require(whitelist[a], "GM: not whitelisted");
}
```

**调用方**：`buy / transferItem / listItem / buyListed`
**逻辑**：先校验黑名单（恒久拉黑），再校验白名单（whitelistEnabled 开启时才校验）
**默认行为**：`whitelistEnabled=false` 时只校验黑名单，所有人可买

### 20.2 `_tierBps(productId, qty)` — 阶梯折扣选择算法

```solidity
function _tierBps(uint256 productId, uint256 qty) internal view returns (uint256) {
    Tier[] storage t = _tiers[productId];
    uint256 bps = 10000;          // 默认原价
    uint256 bestMin = 0;
    for (uint256 i = 0; i < t.length; i++) {
        if (qty >= t[i].minQty && t[i].minQty >= bestMin) {  // 双重条件
            bestMin = t[i].minQty;
            bps = t[i].bps;
        }
    }
    return bps;
}
```

**算法关键点**：
- **默认 bps=10000**（原价），无任何阶梯时返回原价
- **双重条件**：`qty >= t[i].minQty`（达到该档起购量）**且** `t[i].minQty >= bestMin`（该档比起之前匹配的档更高）
- **遍历所有 tiers**：不是 break 在第一个匹配，而是遍历整个数组找**最高 minQty 那档**
- **不保序**：tiers 数组无需按 minQty 排序，算法会自动找最高
- **示例**：tiers=[(100,7000),(50,8000),(200,6000)]，qty=150 → 匹配 (100,7000) 和 (50,8000)，bestMin=100，bps=7000

### 20.3 `_removeOwned(owner_, codeId)` — swap-and-pop 删除算法

```solidity
function _removeOwned(address owner_, bytes32 codeId) internal {
    bytes32[] storage arr = _ownedCodes[owner_];
    for (uint256 i = 0; i < arr.length; i++) {
        if (arr[i] == codeId) {
            arr[i] = arr[arr.length - 1];  // swap：末尾元素换到当前位置
            arr.pop();                      // pop：删除末尾
            break;                          // break：找到第一个就停止
        }
    }
}
```

**算法关键点**：
- **swap-and-pop**：不是 splice（保序删除），而是把末尾元素换到要删的位置再 pop
- **O(n) 查找 + O(1) 删除**：查找是线性遍历，删除是常数时间
- **不保序**：删除后数组顺序会变化（末尾元素移到被删位置）
- **break 找到第一个就停止**：同一码在同一 owner 数组中只出现一次，break 优化性能
- **前端影响**：查询 `ownedCodesOf(addr)` 返回的码顺序会因删除操作变化，前端不应依赖顺序

### 20.4 `_moveCode(codeId, from, to)` — 码转移完整流程

```solidity
function _moveCode(bytes32 codeId, address from, address to) internal {
    _removeOwned(from, codeId);        // 步骤1：从原持有人数组移除（swap-and-pop）
    codeOwner[codeId] = to;            // 步骤2：更新 codeOwner
    _ownedCodes[to].push(codeId);      // 步骤3：push 到新持有人数组末尾
}
```

**调用方**：
- `transferItem(codeId, to)` — 直转/赠送
- `buyListed(codeId)` — 挂单购买后转移

**算法关键点**：
- **3 步原子操作**：移除 → 更新 owner → push
- **不修改 codeStatus**：codeStatus 保持 2（已售），只是 owner 变化
- **不修改 codeProduct**：码所属商品不变
- **不触发事件**：事件由调用方触发（`ItemTransferred` / `ItemResold`）
- **注意**：`approveReturn` 中码回收**不调 `_moveCode`**，而是直接 `codeOwner[codeId] = address(0)` + `codeStatus[codeId] = 3`
