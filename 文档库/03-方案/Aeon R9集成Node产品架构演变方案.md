## 1. 方案概述

### 1.1 背景

Node 产品当前为"纯 Web3 自管钱包 App",包含两大一级模块:
- **Tab 1 冷钱包舱**:资产看板/Swap/Faucet/收发/钱包管理
- **Tab 2 服务舱**:福利特权(空投/资产/互动)+ 保险库 + 数字身份通行证

现引入 Aeon R9 冷钱包上下级永久绑定方案,核心能力是**基于链上地址的永久上下级关系绑定 + 5 渠道归因 + 多级佣金分账 + 治理迁移**。

该方案的本质是"以地址为身份的关系网络管理",与 Node 现有"单地址资产操作"模型存在身份粒度差异,需要架构层面的整合。

### 1.2 核心矛盾

| 维度 | Node 现状 | Aeon R9 需要 |
|------|-----------|--------------|
| 身份粒度 | 单地址为活动主体,App 全局只有一个"当前钱包" | 多地址并存,每个地址有独立关系网络,需切换查看 |
| 功能性质 | 围绕地址的资产/权益/凭证操作 | 围绕地址的关系网络管理 |
| 身份角色 | 身份是"操作主体"(谁在签名) | 身份是"数据视角"(在看谁的推广树) |
| 是否需切换 | 不需要(全局单地址) | 需要(用户有多个钱包,各有独立上下级) |

**一句话**:Node 现在是"单身份驱动的资产 App",Aeon R9 需要的是"多身份可切换的账号服务"。这两个模型的身份粒度不同。

### 1.3 方案目标

1. 将 Aeon R9 的关系网络能力完整落地到 Node 产品
2. 不破坏 Node 现有 Tab 1/2 的功能与交互
3. 通过架构重组,让 Node 从"2 Tab 单身份"进化为"3 Tab 多身份可切换"
4. 明确技术对接所需的接口、服务、合约清单

### 1.4 方案范围

- **包含**:Tab 3 新增设计、Tab 1/2 调整说明、身份切换器、推广/团队/邀请/佣金模块、与现有模块的集成关系、后端服务清单、链上合约层、实施路径
- **不包含**:各模块的最终 UI 细节(后续 demo 确认)、后端服务的接口字段级设计、合约审计清单

## 2. 架构决策

### 2.1 三条主线的本质区分

Node 的功能按"身份角色"重新分线:

```
线1:资产操作线  → 操作"当前地址的链上资产"   → 不涉及身份切换
线2:身份权益线  → 享受"当前地址作为身份的权益" → 不涉及身份切换
线3:账号服务线  → 管理"多个身份的关系网络"    → 核心是身份切换
```

### 2.2 三 Tab 重组方案

```
┌──────────────────────────────────────────────────┐
│  Tab 1: 冷钱包 (纯资产操作)                       │
│   资产看板 / Swap / Faucet / 发送 / 接收 / 钱包管理 │
│   [保持纯粹,不引入任何业务模块]                    │
├──────────────────────────────────────────────────┤
│  Tab 2: 身份 (Web3身份的权益与凭证)  ★重命名       │
│   福利特权(空投/资产/互动)                         │
│   保险库(设备指纹+权益舱)                          │
│   数字身份通行证(钱包+凭证管理)                    │
├──────────────────────────────────────────────────┤
│  Tab 3: 团队 (Aeon R9 关系网络)  ★新增             │
│   ┌─设备指纹绑定(前置,Tab 2 保险库)──────────────┐ │
│   ├ 推广中心(短号/上级/团队/二维码/邀请/团队申请)  │ │
│   ├ 我的团队(上下级关系树+L1/L2/L3明细)           │ │
│   ├ 邀请中心(定向邀请+状态机)                     │ │
│   ├ 佣金明细(L1/L2/L3分账+年费分润)              │ │
│   └ 待分配池(仅代理/公司可见)                     │ │
│   └────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘
```

### 2.3 已确认的架构决策

| # | 决策点 | 结论 | 理由 |
|---|--------|------|------|
| 1 | Tab 1 是否引入业务模块 | **不引入** | 冷钱包本质是纯资产工具,参考主流 Web3 钱包(MetaMask/Phantom/Trust)Tab 1 均不掺杂推广/关系/社交逻辑 |
| 2 | 绑定上级入口位置 | **Tab 3 推广中心内** | 绑定是"加入推广体系",属账号服务,非资产操作;签名能力是 Node 全局能力,Tab 3 可直接拉起 PIN 码签名弹窗 |
| 3 | Tab 2 重命名 | "服务舱"→"身份"(待最终考究) | 福利/保险库/DID 本质都是"当前 Web3 身份的权益与凭证" |
| 4 | Tab 3 命名 | **"团队"**(已定稿) | 核心是邀请制关系网络管理,设备指纹绑定唯一地址,不提供多账号切换 |
| 5 | 身份切换器 | **已移除** | 改为设备指纹绑定唯一地址(DeviceRegistry),不提供多账号切换,防女巫。2026-07-14 进一步优化:设备指纹不再前置检测,与关系绑定一起在确认上链时完成 |
| 6 | Tab 1/2 是否跟随 Tab 3 | **不跟随** | Tab 3 使用设备指纹绑定唯一地址,Tab 1/2 保持全局单地址模式 |
| 7 | 邀请返利归属 | **明细全在 Tab 3** | 邀请关系管理 + 返利明细都是团队视角,内聚在 Tab 3 |
| 8 | 保险库角色 | **仍展示在 Tab 2,向 Tab 1/3 暴露校验接口** | 保险库升级为全 App 安全基座 |

### 2.4 待最终考究的命名

| Tab | 当前候选 | 说明 |
|-----|----------|------|
| Tab 1 | 冷钱包 / 资产 / 钱包 | "冷钱包"已确认本质 |
| Tab 2 | 身份 / 权益 / 凭证 | "身份"较能涵盖权益+凭证 |
| Tab 3 | **团队**(已定稿) | 涵盖推广+团队+佣金,设备指纹绑定唯一地址,不提供多账号切换 |

> 命名不阻塞方案推进,可在 demo 出来后用一段时间再定稿。

## 3. Tab 1 调整说明:保持冷钱包纯粹性

### 3.1 设计原则

参考主流 Web3 钱包(MetaMask / Phantom / Trust Wallet / Rainbow / Coinbase Wallet)的共性:

| 钱包 | Tab 1 核心 | 是否有推广/邀请/社交 |
|------|-----------|---------------------|
| MetaMask | 资产+发送+接收+Swap+DApp | 无 |
| Phantom | 资产+收发+NFT+DApp | 无 |
| Trust Wallet | 资产+DApp+Staking | 无 |
| Rainbow | 资产+收发+Swap | 无 |

**共识**:冷钱包的 Tab 1 就是纯资产操作工具,不掺杂业务/关系/推广逻辑。

### 3.2 Tab 1 功能清单(不变)

| 子模块 | 功能 | 状态 |
|--------|------|------|
| 资产看板 | 总估值 + 代币列表(RC/USDRs/HRCs/RSTs) | 原型完成 |
| Swap 兑换 | 自主链代币两两兑换 + 滑点控制 | 原型完成,联调中 |
| Faucet 领取 | 每24h领5 RC,EIP-2771免Gas | 原型完成,联调中 |
| 币种详情 | 余额 + 价格走势 + 交易记录 | 原型完成 |
| 发送/接收 | 链上转账 | 占位 |
| 钱包管理 | 创建/导入/重命名/导出私钥/注销 | 原型完成 |

### 3.3 Tab 1 不引入的内容

- ✗ 绑定上级入口(移至 Tab 3 推广中心)
- ✗ 推广/团队/邀请任何业务模块
- ✗ 任何关系网络逻辑

## 4. Tab 2 重命名说明:从"服务"到"身份"

### 4.1 重命名理由

Tab 2 现有三大功能(福利特权/保险库/DID通行证)的本质都是"当前 Web3 身份的权益与凭证":
- 福利特权 = 身份的权益(空投/资产/互动)
- 保险库 = 身份的安全(设备指纹+权益舱)
- DID通行证 = 身份的仓库(管理多个钱包与凭证)

"服务舱"这个名字暗示"给当前地址提供服务",无法体现"身份"这一核心。重命名为"身份"更准确。

### 4.2 Tab 2 功能清单(不变,仅命名调整)

```
Tab 2: 身份
├ 福利特权(空投/资产/互动)
├ 安全与保障
│   ├ 保险库(设备指纹+权益舱)  ← 升级为全App安全基座
│   └ 数字身份通行证(钱包+凭证管理)  ← Tab 3 身份切换器的数据源
└ DApp 探索(占位)
```

### 4.3 保险库的角色升级

| 维度 | 现状 | Aeon R9 后 |
|------|------|-----------|
| 定位 | Tab 2 内的安全功能 | 全 App 的安全基座 |
| 职责 | 防女巫、权益舱 | 防女巫、权益舱 + 向 Tab 3 提供设备校验 |
| 接口 | 仅本地展示 | 暴露 `isBoundAddress(user)` 供 Tab 3 绑定前校验 |

**校验流程**:
```
Tab 3 推广中心发起绑定上级 → 检查 DeviceRegistry.isBoundAddress(user) →
  ├ 已绑定设备 → 允许绑定(走 bindWithSig 签名)
  └ 未绑定设备 → 引导跳转 Tab 2 保险库激活设备指纹
```

### 4.4 DID Pass 的新角色

| 组件 | 职责 | 位置 |
|------|------|------|
| DID Pass | 身份的**存储与管理**(管理多个钱包/Web2凭证) | Tab 2 |
| 身份切换器 | 身份的**使用与切换**(选择当前活动身份) | Tab 3 顶部 |

DID Pass 是"仓库",身份切换器是"选择器"。切换器的身份列表**来源于 DID Pass 管理的钱包地址**。

### 5.2 身份切换器

**核心交互**:
```
Tab 3 顶部固定区:
┌─────────────────────────────────────────┐
│  当前身份  #100001 · 0x71C7...98A5   ▾  │
│  上级:#100000 · L1深度                  │
└─────────────────────────────────────────┘

点击 ▾ 展开:
┌─────────────────────────────────────────┐
│  ◉ #100001 · 0x71C7...98A5  (当前)      │
│    团队50人 · 本月$45.20                │
│  ○ #100088 · 0x3B2f...71D4              │
│    团队3人 · 本月$2.10                  │
│  ───────────────────────────────────    │
│  + 关联新身份(从DID通行证选择钱包地址)    │
└─────────────────────────────────────────┘
```

**设计约束**:
- 身份切换器**仅切换 Web3 钱包地址**(关系在链上以地址为真身)
- 切换的是"当前查看的视角",**不改变任何链上关系**
- 切换后,Tab 3 的推广/团队/邀请/佣金数据全部跟随切换
- **Tab 1 和 Tab 2 不受切换影响**(它们保持全局单地址模式)
- 身份列表**来源于 DID Pass 管理的钱包地址**

**关联新身份流程**:
```
点击"+ 关联新身份" → 拉起 DID Pass 钱包选择器 →
选择钱包地址 → 加入 Tab 3 身份切换器列表 →
查询该地址的链上关系(是否有上级/下级) → 展示数据
```

**两种状态设计**:

**未绑定状态**(首次进入或该地址无上级):

┌─────────────────────────────────┐
│  推广中心                        │
│  ┌─────────────────────────┐    │

│  │  [🔗 扫码绑定上级]        │    │
│  │  [输入邀请码]            │    │
│  └─────────────────────────┘    │
└─────────────────────────────────┘
```

**已绑定状态**（2026-07-20 短号区重构版，LX/LY 命名）:
```
┌─────────────────────────────────┐
│  推广中心                        │
│  ┌──────────┬──────────┐         │
│  │ 上级短号  │ 我的短号  │         │
│  │ #100028  │ #100068 💎│         │
│  │ LY·张三  │ 吉尾号·展示│         │
│  │ [查看链路]│  [管理]   │         │
│  └──────────┴──────────┘         │
│  ┌──────┬──────┬──────┐         │
│  │二维码│ 邀请 │团队申请│        │
│  └──────┴──────┴──────┘         │
│  (三按钮均需邀请能力白名单校验)  │
│  绑定时间:2026-07-09            │
└─────────────────────────────────┘
```

**上级层级命名约定**（2026-07-20 定稿）:
- **LX** = 上上级（grandparent，离我更远的一级）
- **LY** = 上级（parent，我的直接上级）
- **链路格式**：`LX.LY`（如 `100000.100028`，上上级.直接上级）
- App 内只展示这两级，更深层级不在 App 内展示，可前往区块浏览器查询
- 推广中心顶部"上级短号"卡显示 LY（直接上级）短号；点击"查看链路"弹窗按 `LX → LY` 顺序展示两级

**短号区两段式布局**（2026-07-20 重构）:
- **左：上级短号卡** —— 展示 LY 直接上级短号（短号链路较长，5-8 位 × 两级），点击"查看链路"弹窗，弹窗内按 LX → LY 顺序展示上上级 + 直接上级 两级，底部说明链路格式 `LX.LY`（如 100000.100028）。
- **右：我的短号卡** —— 展示当前选中的展示短号 + 类型徽章（💎 靓号 / 🎁 免费号），点击"管理"进入我的短号管理子页。

**我的短号管理子页**（复用 DID 身份页短号服务设计，DID 那边功能保留，非迁移）:
- 三 Tab：**💾 我的短号** / **💎 购买靓号** / **🎁 免费号**
- 我的短号：列出已绑定的全部短号（一个身份可绑定多个靓号 + 1 个免费号），每张卡片显示类型徽章 + 获取日期 + 链，可"设为展示"切换当前展示短号（仅影响顶部展示，不影响链上绑定关系）
- 购买靓号：查价输入框 + 位数筛选 Pills（5/6/7/8 位）+ 推荐列表（换一批）+ 定价规则折叠区（5位基价1000U，每多一位×0.9；豹子×50/顺子×20/四连同×10/葫芦×8/双对×5/吉尾×3）+ 支付确认弹窗（网络/币种/PIN）
- 免费号：随机生成 10 个 10-12 位候选号（自动避开靓号段）+ 换一批 + 领取选中号；每个身份仅可免费领取 1 次

> 推广中心三按钮：**二维码**（展示我的推广码）、**邀请**（发起定向邀请，可选预设 gas）、**团队申请**（双 Tab：我邀请的 / 加我的，合并主动邀请和接收申请两类记录）。gas 转账不作为邀请/申请状态机一环，是否成功由链上校验；审批/邀请时可选"不发送 gas"。

**绑定上级流程**(2026-07-17 优化版，设备指纹后置上链):
```
1. 未加入团队的用户在初始页通过 扫码 / 搜索短号 找到上级
2. 确认上级信息后发送申请(不上链)
3. 上级在"团队申请·加我的"Tab 收到申请 → 审批(接受/拒绝)
4. 接受后可选转 gas(默认0.05可自定义/可不转)
5. 下级收到"已同意"通知 → 申请进度页直接展示确认详情(设备指纹+关系绑定)
6. 下级点击"确认加入" → 拉起 PIN 码签名 → EIP-712 离线签名
7. 设备指纹绑定 + 关系绑定一起上链完成 → 进入团队主页
```

**5 渠道归因汇聚点**:所有渠道(扫码/邀请链接/Deep Link/购买归属/客服归属)的信号最终汇聚到推广中心的绑定确认页,用户知情确认后才上链。

### 5.4 我的团队

**展示内容**:
```
我的团队
├ 上级信息
│   ├ 短号/地址/绑定时间
│   └ 我的层级深度

## 6. 与现有 Node 模块的集成关系

### 6.1 签名能力复用

Node 现有签名链路(App Connect Auth):
```
外部App发起挑战 → Node展示授权弹窗 → 用户选身份 → 输PIN码 →
本地私钥签名Challenge → 返回Signature Proof
```

Aeon R9 需要的签名链路(bindWithSig):
```
归因服务算出referrer → Tab 3 展示绑定确认页 → 用户确认 →
本地私钥签EIP-712 Bind(user,referrer,deadline) → Relayer代提交bindWithSig
```

**复用方案**:
- 复用 Node 的 EIP-712 签名基础设施
- 新增一个"绑定签名"的授权面板(与现有 App Connect Modal 同级)
- Tab 3 绑定时直接拉起 PIN 码签名弹窗,不依赖 Tab 1

**关键**:Node 已有"输入PIN → 本地私钥签名 → 返回Proof"完整链路,Aeon R9 只需新增一个 Bind 类型的签名场景,不破坏现有签名架构。

### 6.2 保险库作为安全基座

```
Tab 3 绑定上级 → 检查 DeviceRegistry.isBoundAddress(user)
  ├ 已绑定 → 允许绑定
  └ 未绑定 → 引导跳转 Tab 2 保险库激活
```

**演进方案**:
| 阶段 | 做什么 |
|------|--------|
| 现状 | Goose Vault 是 Node 本地的设备指纹绑定展示 |
| 演进 | Vault 扩展为对链上可见的 DeviceRegistry,绑定状态上链 |
| 接口 | 暴露 `isBoundAddress(user)` 供 ReferralRegistry 调用 |

**架构原则冲突点**:
- Node 设计原则是"云端无状态"
- DeviceRegistry 需要链上有状态(绑定关系上链)
- **建议**:DeviceRegistry 只记录"设备已注册"的布尔值,不存地址↔设备映射(保持隐私,与 Node 原则一致)

### 6.3 DID Pass 作为身份仓库

```
Tab 3 身份切换器 ← 读取 → DID Pass 管理的钱包地址列表
Tab 3 关联新身份 → 拉起 DID Pass 钱包选择器
```

**数据流**:
- DID Pass 管理用户的所有钱包地址(Web3)+ Web2 凭证
- Tab 3 身份切换器**只取 Web3 钱包地址**(Web2 凭证不参与 Tab 3 任何流程,详见 6.4)
- 切换身份后,Tab 3 所有模块按新地址查询链上关系

### 6.4 Web2 账号与链上地址的关系对齐

**当前暂定决策**:Web2 账号**不参与**上下级绑定与推广体系,此服务仅对 Web3 钱包地址开放。该决策**有待考究**,已列入 12.1 待确认项(第 7 条)。

**暂定立场下的边界**:
- 上下级关系在链上以地址为真身,Web2 凭证不进入关系绑定链路
- Tab 3 身份切换器只取 Web3 钱包地址,DID Pass 中的 Web2 凭证与 Tab 3 完全无关
- Web2 用户即使持有 Node 账号,也**暂不引导**其关联钱包以建立永久上下级(原"首购激活引导关联钱包"流程暂不启用)

**待考究的开放问题**(留待后续决策,不在本版方案定案):
- Web2 用户作为"消费者下级"是否完全无法让上级获得返利
- 未来是否开放"Web2 关联钱包"通道,以及开放后的合规与归因处理
- 若最终允许参与,需补充关联流程、风控与归因优先级设计

## 7. 后端服务新增清单

Node 目前是"本地客户端为主、云端无状态"的架构。Aeon R9 需要以下后端服务,这是 Node 体系最大的新增部分:

| 服务 | 职责 | 与 Node 的关系 | 优先级 |
|------|------|---------------|--------|
| **归因服务 Attribution** | 5渠道信号汇聚 + 优先级裁决 | 全新,Node 无归因能力 | P2 |
| **邀请服务 Invitation** | pending邀请表 + 状态机 + 30天窗口 | 全新,Node 无邀请体系 | P2 |
| **Relayer/Bridge** | 持miner key代提交 bindWithSig + 代付gas | Node 有签名回调但无代付能力 | P2 |
| **Indexer** | 监听Bound事件 → closure table 落库 | 全新,Node 无链上事件监听 | P1 |
| **结算服务** | L1/L2/L3佣金 + 年费分润 | 全新,Node 无佣金体系 | P2 |

**架构原则说明**:这些后端服务与 Node"云端无状态"原则不冲突——它们管的是链上关系的索引和归因,不是用户私钥/凭证。用户身份真身仍在链上(`referrerOf`)和本地(私钥),后端只是加速查询和代提交。

### 7.1 数据库表设计建议(Indexer 侧)

| 表 | 用途 |
|---|---|
| `referral_relations` | 地址↔上级↔深度↔短号,镜像链上 |
| `referral_closure` | 闭包表,便于查 N 级下线/上线 |
| `orphan_pool` | 待分配池,镜像 `inPendingPool` |
| `migration_log` | 迁移记录,镜像链上事件 |
| `attribution_signals` | 归因信号原始记录,30天窗口 |
| `invitation_records` | 邀请记录 + 状态机 |

## 8. 链上合约层

### 8.1 合约清单

| 合约 | 职责 | 状态 |
|------|------|------|
| **ReferralRegistry** | 永久上下级关系(set-once)+ 迁移治理 | 参考实现已写,待审计 |
| **DeviceRegistry** | 设备指纹绑定状态(供 ReferralRegistry 校验) | 需新增设计 |

### 8.2 ReferralRegistry 核心方法

| 方法 | 用途 | 调用方 |
|------|------|--------|
| `bind(referrer)` | 普通绑定(热钱包) | 用户直接调用 |
| `bindWithSig(user, referrer, deadline, v,r,s)` | 离线签名绑定(冷钱包) | Relayer 代提交 |
| `bindOrphan()` | 孤儿进池 | 系统调用 |
| `claimOrphan(orphan, newReferrer)` | 认领孤儿 | 代理/公司 |
| `bindOnPurchase(buyer, sellerCode)` | 购买时绑定 | 商城合约调用 |
| `executeMigration(old, new)` | 治理迁移 | miner 多签+时间锁 |
| `resolve(a)` | 迁移重定向(8次上限) | 查询用 |
| `getUplines(user, n)` | 查 N 级上线 | 结算服务 |

### 8.3 审计重点关注

| 风险点 | 严重度 | 缓解措施 |
|--------|--------|----------|
| `resolve()` 8次上限被突破 | 中 | Indexer 层无界 resolve 兜底 |
| EIP-712 重放(无 nonce) | 低 | set-once 天然兜底,第二次 revert |
| 防环 `_noCycle` 128次上限 | 低 | 治理层约束 depthOf 最大值 |
| `bindOnPurchase` 静默跳过 | 低 | 关键正确决策,保证下单不失败 |
| miner 私钥泄露 | 高 | 多签+时间锁+硬件钱包+操作审计 |

## 9. 5 渠道归因裁决优先级

| 优先级 | 信号 | 强度 | 场景 | 落点 |
|--------|------|------|------|------|
| 1 | 购买商品归属分销商 | 最强(成交) | 买家已绑定则跳过 | 商城→bindOnPurchase |
| 2 | 会话内显式扫码/接受邀请 | 强(当面/点对点) | 覆盖历史归因 | Tab 3 推广中心扫码 |
| 3 | 邀请链接/Deep Link | 中(窗口30天 last-touch) | 远程裂变 | Tab 3 邀请中心 |
| 4 | 无 | 无 | 进孤儿池 | 系统自动 bindOrphan |

**设计精髓**:因为关系 set-once 永久,归因裁决是唯一能"改"关系的时机——所有信号收敛到"首购激活/结算页"这一个确认点,用确定性优先级预填候选上级,用户知情确认后才上链。

## 10. 迁移通道(唯一可动关系的口子)

```
proposeMigration(eta=+3天) → approveMigration(≥2 miner) → executeMigration(eta到期)
```

**三层防护**:
1. **多签**(2/2 miner)→ 防单点作恶
2. **时间锁**(3天)→ 给社区异议窗口
3. **事件公示**(链上 MigrationProposed/Approved/Executed)→ 全程可审计

**下线自动跟随**:靠 `supersededBy[old] = new` + `resolve()` 重定向,无需逐个改下线关系。

**触发场景**:仅"丢私钥换地址",换机不影响(地址不变,走 DeviceRegistry 换绑设备)。

## 13. 总结

### 13.1 核心判断

Node 现有框架与 Aeon R9 方案的契合度很高——**地址即身份、EIP-712签名、设备指纹**三大底层能力已具备,集成本质是"在 Node 基座上叠加关系层",不是重构。

### 13.2 三大架构动作

1. **Tab 1 保持纯粹**:冷钱包不引入任何业务模块,参考主流 Web3 钱包设计惯例
2. **Tab 2 重命名**:服务→身份,明确它是"Web3 身份权益线",保险库升级为全 App 安全基座
3. **Tab 3 新增**:团队(Aeon R9 落点),核心是设备指纹绑定 + 推广/团队/邀请/佣金模块

### 13.3 最大改造点

不在前端(Node UI 框架能自然容纳 Tab 3),而在:
1. **后端服务新增**(归因/Relayer/Indexer/结算)
2. **两处架构对齐决策**(DeviceRegistry 上链粒度、Web2 账号是否参与本服务——暂定不参与,待确认,见 6.4)
3. **身份模型的升级**(从单地址到多身份可切换)

### 13.4 落地路径

先跑通"合约部署 + Vault 演进 + Indexer + EIP-712 签名面板 + Tab 3 骨架"这条 P1 最小闭环,验证一个地址能通过 Node 签名绑定到另一个地址并落库可查,再逐步叠加渠道和结算。
