## 0. MVP 调整说明(v1.1 新增)

### 0.1 调整背景

v1.0 方案设计完整但范围过大,MVP 阶段需做减法。核心原则:**前期以自主 App 上架为主,第三方应用占位待接入**。本次调整针对三个关键问题:① iOS/Android 平台差异;② 减法清单;③ DApp 使用方式定位。

### 0.2 关键决策记录

| # | 决策点 | v1.0 方案 | v1.1 MVP 调整 | 理由 |
|---|--------|---------|--------------|------|
| 1 | DApp 使用方式 | 内嵌浏览器 + 钱包 provider 注入(MetaMask 模式) | **收录导航模式**:Tab5 只做卡片收录,点击"打开"跳转浏览器/Tab1 钱包浏览器 | Tab5 职责纯粹为应用分发,钱包注入能力归 Tab1 冷钱包;iOS 内嵌 WebView 有审核风险 |
| 2 | iOS/Android 差异 | 未区分 | **分平台处理**:iOS 只能跳 App Store,无法检测已装应用;Android 可做 APK 分发 + 已装检测 | iOS 系统限制无法检测设备已装应用,无法侧载;Android 自由度高 |
| 3 | 第三方 App 区域 | 填充大量第三方假数据 | **占位"即将开放"**:IM/电商分类保留入口但显示斜纹占位卡,不填充假数据 | 前期以自主 App 为主,避免空架假数据降低可信度 |
| 4 | "我的应用" | 钱包状态卡 + 已装列表 + 抽成账单入口 | **最近打开历史**:移除钱包卡和抽成入口,统一改为打开历史记录(不锚定身份) | 主要检测设备上的应用使用情况,不需要绑定钱包身份;iOS 无法检测已装,统一用历史记录 |
| 5 | 抽成账单 | 完整抽成账单视图(view-revenue) | **整体移除** | 自主 App 不抽成,第三方接入前用不到 |
| 6 | 上架申请 | 完整审核流程 + 抽成比例展示 + 审核周期承诺 | **简化为意向收集表单**:新增联系方式必填,移除抽成比例/审核承诺,提交后"3 工作日内联系" | MVP 不做自动审核流程,只做表单收集人工跟进 |
| 7 | App 详情页 | 评分下载 + 截图轮播 + 用户评价 + 版本更新 | **精简**:仅保留图标/名称/徽章/简介/特性/权限声明 | 评分评价等 MVP 不做,自主 App 阶段数据无意义 |
| 8 | 排行榜 | App 下载榜 / DApp 活跃榜 | **移除** | 自主 App 数量少,排行无意义 |
| 9 | 归因参数 | Deep Link 携带 source=node 归因参数 + 链上事件索引 | **移除归因参数**:前期以自主 App 为主,不做抽成分润,无需归因追踪 | 归因依赖第三方接入与抽成体系,前期不涉及;后续第三方接入后再启用 |

### 0.3 iOS / Android 分平台差异清单

| 差异点 | iOS 实现 | Android 实现 |
|--------|---------|-------------|
| **应用分发能力** | 只能跳转 App Store(欧盟 DMA 侧载除外),不能分发 APK | 可直接分发 APK / 走 Google Play / 国内商店 |
| **深链协议** | Universal Links | App Links |
| **"打开"按钮逻辑** | 检测 Universal Link,失败跳 App Store | 检测 App Link,失败跳下载页/APK |
| **"我的应用"检测** | 无法检测,仅显示打开历史 | 可通过 PackageManager 查已装列表(MVP 暂统一用历史) |
| **DApp 浏览器** | 跳系统浏览器或 Tab1 浏览器 | 可内嵌 WebView(但 MVP 统一走跳转) |
| **上架申请表单** | 相同(纯表单收集) | 相同 |

> ⚠️ **关键结论**:iOS 上 Tab5 退化为"应用导航站 + DApp 收录",Android 上才是真正的"应用市场"。MVP 阶段两端 UI 一致,差异仅在"打开"按钮的跳转逻辑和"我的应用"的检测能力。

### 0.4 DApp 收录导航模式(替代 v1.0 的内嵌浏览器方案)

**原 v1.0 方案**(4.5.3 节):Tab5 内置 DApp 浏览器,注入 `window.ethereum` provider,拦截签名请求。

**v1.1 调整**:Tab5 不做内嵌浏览器,DApp 走"收录导航"模式:

```
用户动线(v1.1):
Tab5 商城 → DApp 详情页 → [打开 DApp]
  → 跳转系统浏览器或 Tab1 冷钱包的 DApp 浏览器
  → 钱包连接在 Tab1 完成(Node 钱包 provider 注入)
```

**优势**:
- Tab5 职责纯粹(应用分发),不混入钱包能力
- 钱包注入能力归属 Tab1,职责清晰
- 规避 iOS WebView 钱包注入的审核风险
- 降低 MVP 开发复杂度(无需做 WebView provider 桥接)

**代价**:
- DApp 使用体验略逊于内嵌(需跳出 Tab5)
- 前期不做归因追踪,后续第三方接入与抽成体系就绪后再启用

## 1. 方案概述

### 1.1 背景

Node 产品已规划 5 Tab 架构(Tab1 冷钱包 / Tab2 身份 / Tab3 团队 / Tab4 商品商城 / Tab5 应用市场)。其中 Tab5 此前仅作占位,本方案将其具体化为「**应用市场**」,承载第三方应用分发业务。

**核心商业逻辑**:合作方(开发者/商家/服务商)将 App 上架到我们的商城,用户通过商城进入/下载/连接这些 App,平台从中抽取佣金。**本方案不涉及分销/上下级绑定,纯平台抽成模式**。

### 1.2 与 Tab4 商品商城的边界

| 维度 | Tab4 商品商城 | Tab5 应用市场(本方案) |
|------|--------------|----------------------|
| **标的物** | 实物/虚拟/服务商品(单次交易) | 第三方应用(持续分发) |
| **上架方** | 分销商(需绑定上下级) | 合作方(开发者/商家,无分销关系) |
| **归因机制** | bindOnPurchase 成交型永久绑定 | 平台抽成,不绑定上下级 |
| **佣金流向** | L1/L2/L3 多级分账 | 平台单方抽成(无分销链路) |
| **用户关系** | 买家→分销商(永久上下级) | 用户→App(使用关系,无归属) |
| **结算周期** | 成交即结算 | 周期结算(T+7/T+30) |
| **典型品类** | 硬件钥匙/权益包/服务包 | IM/跨境电商/Web3 DApp |

### 1.3 商业化价值

| 维度 | 价值 |
|------|------|
| **流量变现** | 把 Node 钱包的用户流量转化为 App 分发收入 |
| **生态卡位** | IM/跨境电商/Web3 三类 App 覆盖用户核心场景,增强 App 打开率 |
| **数据资产** | 用户 App 使用偏好数据反哺 Tab1-4 的运营 |
| **合作杠杆** | 与第三方 App 建立分润关系,换取资源互换(流量/品牌/技术) |
| **低边际成本** | App 分发不涉及库存/物流,毛利率高 |

### 1.4 方案目标与范围

- **包含**:Tab5 定位、三类 App 差异化设计、接入方式、上架审核、抽成模式、归因追踪、结算机制、与 Node 现有模块的集成
- **不包含**:具体抽成比例(待决策)、App SDK 字段级设计、法币支付通道、税务合规

## 2. 调研启示(决策依据)

基于对 15+ 产品的调研,提炼出对本方案的关键启示:

### 2.1 抽成比例的行业光谱

| 抽成区间 | 代表产品 | 适用场景 | 对我们的参考 |
|---------|---------|---------|-------------|
| **0%** | TapTap、Shopify App Store | 流量入口免费,靠增值服务变现 | 上架免费是吸引开发者的最强诱饵 |
| **10%** | Discord App Directory | IM/社交平台分发数字商品 | IM 类 App 的参考基准 |
| **15-30%** | Apple/Google(小开发者档) | 数字商品内购 | Web3 DApp/虚拟商品的参考上限 |
| **3-10%** | Amazon Associates | 跨境电商联盟 | 跨境电商跳转分润的参考区间 |
| **50%** | 国内安卓联运(华为/小米) | 游戏联运 | 反面教材,伤害开发者,不可取 |

### 2.2 三类 App 的接入范式

| App 类型 | 主流接入方式 | 代表参考 | 我们的可选路径 |
|---------|------------|---------|--------------|
| **Web3 类(App 为主)** | App:深链跳转 / DApp:内嵌浏览器 + WalletConnect | Web3 钱包/GameFi App / MetaMask Snaps / Phantom | App:深链跳转 + 首启归因 / DApp:内嵌 WebView + 钱包签名注入 |
| **IM 类** | 深度内嵌(TMA 模式) / 跳转下载 | Telegram Mini Apps / Discord | 深链跳转 + 首启归因 |
| **跨境电商** | 跳转独立站 / 官方市场 | Amazon Associates / Shopify | 跳转 + Affiliate ID + Cookie 窗口 |

### 2.3 归因追踪的 Web3 优势

传统联盟的痛点是「cookie 失效 / 平台篡改 / 归因窗口短」。Web3 环境下,我们可以用**钱包地址 + 链上交易哈希**做更硬的归因:

- **Web3 App**:首启 deep link 带 `source=node + wallet`,SDK 回传 tx hash 做终身归因
- **Web3 DApp**:用户钱包 connect 时携带 `referrer=node`,链上交易可验证
- **跨境电商**:跳转链接带 `affId=node`,成交回传(API/Webhook)
- **IM 类**:首启 deep link 带 `source=node`,激活回传

### 2.4 三条关键结论

1. **走低抽成路线**(0-15%),避开国内安卓 50% 联运的反面教材,靠规模和增值服务变现
2. **三类 App 走三条接入路径**,不强行统一,因为它们的形态差异太大
3. **归因链路优先用链上数据**,传统 cookie 作为补充

## 3. 架构决策

### 3.1 Tab5 在 5 Tab 中的定位

```
┌──────────────────────────────────────────────────┐
│  Tab 1: 冷钱包 (资产操作)                         │
├──────────────────────────────────────────────────┤
│  Tab 2: 身份 (权益与凭证)                         │
├──────────────────────────────────────────────────┤
│  Tab 3: 团队 (关系网络)                           │
├──────────────────────────────────────────────────┤
│  Tab 4: 商品商城 (成交型归因,分销体系)            │
├──────────────────────────────────────────────────┤
│  Tab 5: 应用市场 (平台抽成,无分销)  ★本方案       │
│   IM / 跨境电商 / Web3 DApp 三大类应用分发        │
└──────────────────────────────────────────────────┘
```

### 3.2 已确认决策

| # | 决策点 | 结论 | 理由 |
|---|--------|------|------|
| 1 | Tab5 是否独立 | **独立 Tab5** | App 分发与商品交易逻辑差异大,独立更清晰 |
| 2 | 是否走分销体系 | **不走** | 纯平台抽成,不绑定上下级,简化链路 |
| 3 | 是否涉及 bindOnPurchase | **不涉及** | 应用市场不参与 Aeon R9 关系绑定 |
| 4 | 上架是否收费 | **免费上架** | 参考 TapTap/Shopify,0 上架费吸引合作方 |
| 5 | 抽成模式 | **平台单方抽成** | 合作方→平台,无 L1/L2/L3 分账 |
| 6 | 自主 App 是否上架 | **上架,官方直营身份** | 自主 App 是商城种子内容与流量入口,必须占位 |
| 7 | 自主 App 是否抽成 | **不抽成(内部结算)** | 自营业务无需自我抽成,走财务内部划账即可 |

### 3.3 App 来源体系(双轨制)

应用市场的 App 来源分两条轨道,**自主 App 优先、第三方 App 扩展**:

| 维度 | 自主 App(官方直营) | 第三方 App(合作方) |
|------|------------------|------------------|
| **身份标识** | 「官方」金色徽章 | 「已认证」蓝色徽章 / 无徽章 |
| **上架流程** | 内部立项→产品验收→直接上架 | 资质审核→安全审核→人工 Review |
| **审核要求** | 内部质量门禁(无需资质/审计) | 按风险分级走完整流程 |
| **抽成** | 不抽成(财务内部结算) | 按品类抽成(5-15%) |
| **结算** | 不走抽成结算,收入直接归公司 | T+30 周期结算 |
| **推荐位** | 优先占位(种子期免费) | 可购买 Boost 推荐位 |
| **数据归属** | 全量数据归公司 | 数据按合作协议共享 |
| **下架机制** | 内部决策下架 | 风险触发自动下架 |
| **战略角色** | 种子内容 + 标杆 + 流量入口 | 生态扩展 + 抽成收入 |

**自主 App 的战略价值**:
1. **冷启动种子**:商城上线初期第三方 App 不足时,自主 App 填充内容避免空架
2. **标杆示范**:向合作方展示"我们自己的 App 也在这里分发",增强平台信任
3. **流量入口**:自主 App 与 Node 主 App 形成矩阵,互相导流
4. **体验把控**:自主 App 可深度集成 Node 钱包/DID,作为集成最佳实践范本

### 3.4 待决策点(需后续确认)

| # | 决策点 | 候选方案 | 倾向 |
|---|--------|---------|------|
| 1 | 抽成比例 | 统一 10% / 分品类(IM 8% / 电商 5% / Web3 12%) / 阶梯式 | 分品类(待定具体值) |
| 2 | 结算周期 | T+7 / T+30 / 月结 | T+30(降低对账成本) |
| 3 | 结算币种 | USDRs / 法币 / 双轨 | USDRs 为主,法币可选 |
| 4 | 小开发者优惠 | 无 / 年 GMV<$10W 降档 | 待定 |
| 5 | 推荐位是否售卖 | 是 / 否 | 是(增值服务) |
| 6 | 是否发 Token 做分红 | 是 / 否 | 暂不发,后续评估 |

## 4. 自主 App 产品矩阵与三类 App 差异化设计

### 4.1 自主 App 产品矩阵(官方直营)

基于 Node 产品形态,自主 App 按三类分布,作为商城种子内容:

| App 类型 | 自主产品(示例) | 上架形态 | 说明 |
|---------|--------------|---------|------|
| **IM 类** | Node IM 工具(若有独立 IM App) | 深链跳转/内嵌 | 若有自主 IM 产品,作为官方 IM 占位 |
| **跨境电商** | Node 自营电商(若有官方周边/硬件商城) | 跳转独立站 | 官方硬件钥匙、周边商品的自营电商 |
| **Web3 类** | Node 官方 Web3 App 套件 | App 跳转为主 + DApp 内嵌为辅 | 自研 Web3 应用(原生 App + DApp 两种形态) |
| **跨类** | Node 主 App 本身 | 深链跳转 | 主 App 在商城内可"打开/更新",作流量回流入口 |

**自主 App 的上架原则**:
- **不占第三方配额**:推荐位、Banner 可优先展示自主 App
- **深度集成**:自主 App 必须接入 Node 钱包 + DID + 设备指纹,作为集成范本
- **版本同步**:自主 App 在商城的版本与官方渠道(App Store/Google Play)同步
- **数据回流**:自主 App 的用户行为数据全量归公司,用于优化商城推荐

> ⚠️ **待规划**:自主 App 的具体产品清单需与产品团队确认,本方案仅明确"必须有自主 App 占位"的原则。若当前无自主 IM/电商产品,可先以 Web3 应用套件(官方 Swap/质押等)作为种子内容。

### 4.2 三类 App 总览对比(含自主/第三方)

| 维度 | IM 类 | 跨境电商 | Web3 类(App 为主,含 DApp) |
|------|------|---------|----------|
| **接入方式** | 深链跳转 + 首启归因 | 跳转独立站 + Affiliate ID | App:深链跳转 / DApp:内嵌浏览器 + WalletConnect |
| **用户动线** | 商城→跳转下载/打开→使用 | 商城→跳转商家站→下单→回传成交 | App:跳转下载→使用 / DApp:内嵌打开→connect→链上交易 |
| **归因锚点** | 首次激活(deep link source) | 成交订单(affId 回传) | App:首启激活 / DApp:钱包 connect + 链上 tx hash |
| **抽成对象(第三方)** | 订阅费/内购(若有) | 成交 GMV | App:内购/订阅 / DApp:链上交易额/协议费 |
| **抽成对象(自主)** | 不抽成 | 不抽成 | 不抽成 |
| **参考基准** | Discord 10% | Amazon 3-10% | MetaMask 0% / Apple 15% / 行业 10-15% |
| **抽成倾向(仅第三方)** | 8-10% | 5-8% | 10-15% |
| **审核重点(第三方)** | 账号互通合规、内容安全 | 资质合规、支付安全、售后 | App:钱包集成安全 / DApp:合约审计、权限声明 |
| **审核(自主)** | 内部产品验收即可 | 内部产品验收即可 | 内部安全评审即可 |
| **典型合作方** | Telegram TMA 开发者、IM 工具 | 跨境独立站、亚马逊卖家 | Web3 钱包/GameFi 原生 App + DEX/Lending/NFT DApp |
| **典型自主产品** | Node IM 工具(若有) | Node 自营电商(若有) | Node 官方 Web3 套件(App + DApp) |

### 4.3 IM 类 App 设计

**接入方式**:深链跳转 + 首启归因

```
用户动线:
Tab5 商城 → IM App 详情页 → [打开 App / 下载 App]
  ├ 已安装:Deep Link 唤起,携带 source=node&affId=xxx
  │         → App 首启上报归因 → 平台记录
  └ 未安装:跳转 App Store / Google Play
            → 安装后首启,SDK 回传 source=node
            → 平台记录归因
```

**归因机制**:
- Deep Link 携带 `source=node&affId={合作方ID}`
- App 端 SDK 首启上报(已装)或 Deferred Deep Link(未装)
- 归因窗口:**30 天**(参考行业惯例)
- 用户后续在 App 内的订阅/内购,按比例抽成回传

**抽成对象**:
- IM App 的 Premium 订阅
- IM App 内的数字商品购买(如贴纸/表情/会员)
- 不抽:纯通讯功能(无付费)

**审核重点**:
- 账号体系是否合规(是否支持钱包/DID 登录)
- 内容审核机制(是否接入第三方内容安全)
- 隐私合规(用户数据使用范围)

**典型场景**:
- Telegram Mini App 上架(走 TMA 内嵌或跳转)
- Web3 社交 App(如 Lens/ Farcaster 客户端)
- IM 工具类(如加密通讯 App)

### 4.4 跨境电商 App 设计

**接入方式**:跳转独立站/官方市场 + Affiliate ID + Cookie 窗口

```
用户动线:
Tab5 商城 → 电商 App 详情页 → [立即选购]
  → 跳转商家独立站/亚马逊店铺,URL 带 affId=node
  → 用户浏览/下单
  → 商家通过 API/Webhook 回传成交数据
  → 平台按 GMV 抽成
```

**归因机制**:
- 跳转 URL 携带 `?affid=node&campaign={商城活动}`
- Cookie 窗口:**24 小时**(直接成交)/ **90 天**(加购物车后成交),参考 Amazon
- 商家通过回传 API 报送:`{orderId, amount, affid, timestamp}`
- 平台对账:按 affid 汇总月度 GMV,计算抽成

**抽成对象**:
- 成交订单 GMV(扣除退款/取消)
- 不抽:未成交的浏览、加购

**审核重点**:
- 商家资质(营业执照/跨境资质)
- 支付安全(是否支持合规支付通道)
- 售后能力(退换货政策)
- 商品合规(禁售品清单)

**典型场景**:
- 跨境独立站(Shopify 商家)
- 亚马逊/速卖通店铺
- Web3 电商平台(如去中心化市场)

### 4.5 Web3 类 App 设计(App 为主,DApp 为辅)

Web3 类以**原生 App 为主形态**,DApp(网页应用)作为补充子形态。两者并存,覆盖不同形态的 Web3 应用。

#### 4.5.1 形态划分

| 子形态 | 定义 | 典型产品 | 接入方式 |
|--------|------|---------|---------|
| **Web3 App(主)** | 原生 App(iOS/Android),内置钱包连接能力 | Web3 钱包、GameFi 原生 App、Web3 社交 App、Move-to-Earn App | 深链跳转 + 首启归因 |
| **Web3 DApp(辅)** | 网页应用,运行在 DApp 浏览器内,需钱包注入 | DEX、Lending、NFT Market、质押看板 | 内嵌 DApp 浏览器 + WalletConnect |

> **设计原则**:Web3 类的金刚位与列表展示以 App 为主,DApp 单独设子分类或标签筛选,避免 DApp 淹没 App 的主形态地位。

#### 4.5.2 Web3 App 子形态设计(主)

**接入方式**:深链跳转 + 首启归因(与 IM 类路径一致,但携带 Web3 特有参数)

```
用户动线:
Tab5 商城 → Web3 App 详情页 → [打开 App / 下载 App]
  ├ 已安装:Deep Link 唤起,携带 source=node&wallet=0x...
  │         → App 首启上报归因(含钱包地址)→ 平台记录
  └ 未安装:跳转 App Store / Google Play
            → 安装后首启,SDK 回传 source=node + 钱包地址
            → 平台记录归因
```

**归因机制**:
- Deep Link 携带 `source=node&appId={合作方ID}&wallet={用户钱包}`
- App 端 SDK 首启上报(已装)或 Deferred Deep Link(未装)
- App 内的链上交易通过 SDK 回传 tx hash,平台索引校验
- 归因窗口:**30 天首启 + 终身钱包绑定**(首次 connect 后终身归因)

**抽成对象**:
- App 内购(如 GameFi 道具、会员、能量)
- App 内链上交易的协议费(若 App 自带协议)
- App 订阅费
- 不抽:App 内纯转账(无协议费)

**审核重点**:
- 钱包集成安全(WalletConnect / 自建签名方案的安全性)
- 权限声明(App 调用哪些钱包方法)
- 链兼容性(是否支持 Node 主链)
- App 安全扫描(反恶意代码、反钓鱼)
- 风险披露(若涉金融属性)

**典型场景**:
- Web3 钱包类(如多链钱包、隐私钱包)
- GameFi 原生 App(Move-to-Earn、链游客户端)
- Web3 社交 App(Lens/Farcaster 客户端)
- Web3 工具 App(税务计算、仓位管理)

#### 4.5.3 Web3 DApp 子形态设计(辅)

**接入方式**:内嵌 DApp 浏览器 + WalletConnect + 链上归因

```
用户动线:
Tab5 商城 → DApp 详情页 → [打开 DApp]
  → 内嵌 WebView 打开 DApp URL
  → 注入 Node 钱包 provider(类似 MetaMask 注入)
  → 用户在 DApp 内 connect 钱包
  → 链上交易时,DApp 携带 referrer=node
  → 平台通过链上事件/索引服务捕获交易
  → 按交易额或协议费抽成
```

**归因机制**(最硬,链上可验证):
- DApp 接入时,平台分配 `appId` + `api_key`
- 用户 connect 时,DApp 前端携带 `referrer=node` 参数
- 链上交易 calldata 或 event 中标记来源(若 DApp 配合)
- 平台索引服务监听 DApp 合约事件,按 `appId` 归因
- 归因窗口:**终身**(钱包地址绑定,无 cookie 限制)

**抽成对象**:
- DApp 的协议费(如 DEX 的 swap fee、Lending 的利差)
- DApp 内购(NFT Mint / 功能解锁)
- 不抽:纯链上转账(无 DApp 协议费)

**审核重点**:
- 合约安全审计(要求提供审计报告)
- 权限声明(合约会调用哪些钱包权限)
- 风险披露(是否高风险金融产品)
- 链兼容性(是否支持 Node 主链)

**典型场景**:
- DEX(Swap 类)
- Lending(借贷类)
- NFT Market
- 质押/Staking 看板

#### 4.5.4 两种子形态的并列展示

商城前端在 Web3 类目下,通过标签区分两种子形态:

```
Web3 类目
├ 筛选标签:[全部] [App] [DApp]
├ 推荐区:热门 Web3 App(原生 App 卡片,带「App」标签)
├ 推荐区:精选 DApp(DApp 卡片,带「DApp」标签)
└ 排行榜:App 下载榜 / DApp 活跃榜(分榜)
```

**展示规则**:
- 默认列表以 App 优先排序(原生 App 在前,DApp 在后)
- 用户可切换「仅看 App」/「仅看 DApp」
- App 卡片显示下载量,DApp 卡片显示 24h 活跃地址数
- 详情页明确标注形态(App / DApp),DApp 详情页额外标注「需钱包连接」

## 5. 接入方式技术设计

### 5.1 三种接入路径

```
┌─────────────────────────────────────────────────────┐
│  路径 A:深链跳转(IM App / Web3 App / 原生 App)       │
│   - 生成带 source=node 的 Deep Link                  │
│   - 已装:Universal Link / App Link 唤起              │
│   - 未装:跳应用商店 + Deferred Deep Link 找回         │
│   - App SDK 上报首启归因(Web3 App 额外回传钱包)      │
├─────────────────────────────────────────────────────┤
│  路径 B:内嵌 DApp 浏览器(仅 Web3 DApp 子形态)        │
│   - WebView 加载 DApp URL                            │
│   - 注入 window.ethereum / wallet provider           │
│   - 拦截签名请求 → 拉起 Node 钱包签名                 │
│   - 索引服务监听链上事件做归因                        │
├─────────────────────────────────────────────────────┤
│  路径 C:网页跳转(跨境电商 / 独立站)                  │
│   - 生成带 affid=node 的跳转 URL                     │
│   - 浏览器打开商家站                                 │
│   - Cookie 24h/90d 归因窗口                          │
│   - 商家 Webhook 回传成交数据                        │
└─────────────────────────────────────────────────────┘
```

> 路径 A 覆盖所有原生 App 形态(IM 类、Web3 类的 App 子形态),路径 B 仅服务于 Web3 类的 DApp 子形态。

### 5.2 Web3 DApp 内嵌浏览器技术要点

参考 MetaMask / Phantom 的实现:

| 要点 | 设计 |
|------|------|
| **Provider 注入** | WebView `evaluateJavascript` 注入 `window.ethereum` 对象,桥接 Node 钱包签名能力 |
| **签名拦截** | DApp 调用 `eth_requestAccounts` / `eth_sendTransaction` → 拉起 Node PIN 码确认 |
| **网络切换** | DApp 请求切换链 → 校验是否 Node 支持的链 → 用户确认 |
| **DApp 白名单** | 仅允许已上架审核的 DApp 域名加载,防止钓鱼 |
| **归因标记** | DApp 详情页分配 `appId`,WebView UA 携带 `X-Node-AppId`,索引服务按此归因 |
| **安全沙箱** | 禁止 DApp 访问 Node 本地数据,签名需用户主动确认 |

### 5.3 归因追踪服务设计

```
归因数据模型:
{
  attribution_id: "uuid",
  user_wallet: "0x...",          // 用户钱包(若可用)
  device_id: "xxx",              // 设备指纹
  app_id: "合作方ID",
  app_type: "im|ecommerce|web3",
  trigger: "connect|install|purchase|tx",
  amount: 123.45,                // 成交金额(若有)
  tx_hash: "0x...",              // 链上交易(若 Web3)
  timestamp: 1234567890,
  status: "pending|confirmed|settled"
}
```

**归因优先级**(多渠道冲突时):
1. 链上交易哈希(最硬,Web3)
2. 成交订单回传(电商)
3. 首启激活(IM)
4. 点击归因(兜底)

## 6. 抽成模式设计

### 6.1 抽成模型

```
合作方上架(免费)
  ↓
用户通过商城进入 App
  ↓
归因服务记录来源
  ↓
用户产生付费行为(订阅/成交/链上交易)
  ↓
按品类抽成比例计算平台佣金
  ↓
周期结算(T+30),扣除退款
  ↓
合作方收款(USDRs / 法币)
```

### 6.2 抽成比例建议(待决策)

| App 类型 | 建议抽成 | 理由 |
|---------|---------|------|
| **IM 类** | 8-10% | 参考 Discord 10%,略低以吸引上架 |
| **跨境电商** | 5-8% | 参考 Amazon Associates 3-10%,中位数 |
| **Web3 DApp** | 10-15% | 行业无统一标准,参考 Apple 15% 小开发者档 |
| **小开发者优惠** | 降 3-5% | 年 GMV < $10W 的合作方降档,鼓励生态 |

### 6.3 增值变现(非抽成收入)

| 方式 | 说明 | 参考产品 |
|------|------|---------|
| **推荐位/Boost** | 首页 Banner、分类置顶、搜索竞价 | DappRadar Boost |
| **官方认证标** | 付费获得「官方认证」徽章,增强信任 | 各大应用商店 |
| **数据分析服务** | 向合作方提供用户画像/转化漏斗报告 | Shopify Analytics |
| **优先技术支持** | 付费享受 SDK 对接优先级、专属客服 | Apple Developer |

### 6.4 结算机制

| 维度 | 设计 |
|------|------|
| **结算周期** | T+30(自然月结算上月已确认订单) |
| **结算币种** | USDRs 为主;法币结算后续评估 |
| **对账方式** | 平台生成结算单 → 合作方确认 → 链上转账/法币打款 |
| **退款处理** | 扣除退款订单,按净 GMV 结算 |
| **最低结算额** | 设最低门槛(如 100 USDRs),低于则累计到下月 |

## 7. 上架审核与安全

### 7.1 上架流程(双轨制)

**路径 A:自主 App 上架(内部简化流程)**

```
内部产品立项 → 产品验收(功能/体验/安全)
  ↓
内部安全评审(DApp 需合约内部审计)
  ↓
直接上架,标记「官方」金色徽章
  ↓
持续运营(无需风控监控,自主可控)
```

**路径 B:第三方 App 上架(完整审核流程)**

```
合作方提交申请
  ↓
资质审核(营业执照/KYC/开发者身份)
  ↓
App 安全审核(合约审计/内容合规/权限声明)
  ↓
测试环境验证(归因链路/抽成回传/签名流程)
  ↓
人工 Review(产品体验/风险披露)
  ↓
上架(默认「未认证」状态,可申请「已认证」蓝色徽章)
  ↓
持续监控(用户举报/异常交易/合规风险)
```

### 7.2 三类 App 的审核清单(仅第三方)

| 审核项 | IM 类 | 跨境电商 | Web3 DApp |
|--------|------|---------|----------|
| **主体资质** | 公司/个人开发者 | 营业执照+跨境资质 | 公司/DAO/开发者 |
| **安全审计** | 账号体系安全评估 | 支付安全评估 | 合约审计报告(必备) |
| **内容合规** | 内容审核机制 | 商品合规(禁售品) | 风险披露 |
| **权限声明** | 数据使用范围 | 用户数据保护 | 合约权限清单 |
| **归因对接** | SDK 集成 | Webhook/API 对接 | referrer 参数集成 |
| **售后能力** | 用户投诉通道 | 退换货政策 | 紧急暂停机制 |

> 自主 App 无需走上述清单,由内部产品团队按公司质量门禁验收即可。

### 7.3 风险分级(参考 MetaMask Snaps)

| 等级 | 适用 | 审核要求 |
|------|------|---------|
| **L1 严格审核** | 涉及资产管理/转账的 DApp、电商 | 强制合约审计 + 人工 Review + 保证金 |
| **L2 标准审核** | IM、工具类、信息类 | 资质审核 + 自动化扫描 + 抽样 Review |
| **L3 开放** | 纯展示/查询类 DApp | 自动化扫描即可上架 |

### 7.4 下架机制

触发条件:
- 用户举报率达阈值(如 5%)
- 安全漏洞未及时修复
- 合规风险(涉黄/涉赌/涉诈)
- 抽成分润长期拖欠对账
- 合作方主动下架

## 8. 防女巫与反作弊

### 8.1 风险场景

| 场景 | 风险 | 应对 |
|------|------|------|
| **虚假成交** | 合作方刷单骗平台流量补贴 | 链上交易验证 + 人工抽查 + 退款率监控 |
| **归因劫持** | 用户被其他渠道截胡归因 | 多信号归因(首启 + 成交 + 链上)优先级裁决 |
| **重复激活** | 同一用户多设备激活骗 CPA | 设备指纹去重(DeviceRegistry) |
| **虚假 App** | 冒充知名 App 骗用户 | 官方认证标 + 域名白名单 |
| **合约后门** | DApp 合约藏后门盗资产 | 强制审计 + 权限白名单 + 紧急暂停 |

### 8.2 防女巫技术栈

```
设备层:DeviceRegistry 设备指纹(复用 Tab2 保险库能力)
身份层:钱包地址 + 可选 KYC(合作方侧)
行为层:链上行为聚类分析(异常交易模式识别)
归因层:多信号交叉验证(首启/成交/链上三重校验)
```

## 9. 与 Node 现有模块的集成

### 9.1 集成关系图

```
Tab5 应用市场
  ├← Tab1 冷钱包:提供钱包地址 + 签名能力(DApp connect)
  ├← Tab2 保险库:提供设备指纹校验(反女巫)
  ├← Tab2 数字身份:可选,合作方接 DID 登录
  ├→ 独立于 Tab3 团队:不走 Aeon R9 关系绑定
  └→ 独立于 Tab4 商城:不走 bindOnPurchase 分销
```

### 9.2 与各 Tab 的交互

| 模块 | 交互方式 |
|------|---------|
| **Tab1 冷钱包** | DApp 内嵌时,注入钱包 provider,签名走 Tab1 的 PIN 码流程 |
| **Tab2 保险库** | 上架审核时校验合作方设备指纹;用户首次进入 App 时反女巫校验 |
| **Tab2 数字身份** | 可选:合作方 App 接入 Node DID 登录(增强信任) |
| **Tab3 团队** | **不交互**(本方案不涉及上下级关系) |
| **Tab4 商品商城** | **不交互**(独立业务线) |

### 9.3 用户身份模型

| 维度 | 规则 |
|------|------|
| **浏览身份** | 无需登录,任何用户可浏览 应用市场 |
| **使用身份** | 打开 DApp 时,跟随 Tab1 全局钱包(只读,不可在 Tab5 切换) |
| **归因身份** | 设备指纹 + 钱包地址(若可用),用于追踪用户来源 |
| **结算身份** | 合作方在 B 端后台注册的账户,与用户身份分离 |

## 14. 风险与应对

| 风险 | 严重度 | 应对 |
|------|--------|------|
| **DApp 合约漏洞导致用户资产损失** | 高 | 强制审计 + 权限白名单 + 紧急暂停 + 风险披露 |
| **合作方刷单骗抽成** | 中 | 链上验证 + 退款率监控 + 异常交易告警 |
| **抽成比例过高导致合作方流失** | 中 | 走低抽成路线 + 小开发者优惠 + 增值服务替代 |
| **DApp 浏览器性能差** | 中 | WebView 优化 + DApp 白名单(仅高质量) |
| **合规风险(电商/IM 内容)** | 高 | 资质审核 + 内容安全 + 下架机制 |
| **归因链路被合作方绕过** | 中 | 多信号交叉验证 + 抽查 + 合同约束 |
