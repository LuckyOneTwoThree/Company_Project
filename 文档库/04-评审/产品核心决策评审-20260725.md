## P0-1：烧断机制的佣金去向

### 决策描述

返佣烧断机制中，当上层 rank 小于下层 rank 时触发烧断，烧断的佣金去向如何处理？

### 现状

现有 compression 机制：`rank == 0`（完全未达标）时跳过该层，佣金上卷给下一个合格上线（不销毁）。

烧断机制是新增方向：`上层 rank < 下层 rank`（弱上级吃强下级）时触发，现有合约无此逻辑。

### 建议方案：B+D 组合（上卷优先 + 找不到则转积分给被烧断的下级）

**具体规则**：
1. 沿 E 链向上找第一个 `rank ≥ 触发烧断的下层 rank` 的上线 → 上卷发放
2. 若 `maxBurnSkips`（建议 10 步）内找不到合格者 → 等值转化为 `AgentPoints` 铸给**被烧断的下级**（即买单的实际推广者），作为补偿
3. 资金不流出生态（不进 treasury、不进黑洞）

### 决策理由

- **上卷优先**：保留激励属性，让"努力升级的上级"获得额外收益，符合代理体系激励逻辑
- **转积分兜底**：避免纯销毁导致生态通缩，同时补偿"被弱上级拖累的强下级"，激励强下级继续推广
- **不归平台**：避免中心化色彩，维护 Web3 Native 定位
- **不进黑洞**：避免生态资金净流出

### 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 上卷搜索增加 gas 成本 | `maxBurnSkips=10` 硬上限，与 compression 的 20 步对齐 |
| 转积分铸币权集中在 AgentReward | AgentReward 已是 `onlyRewarder` 授权调用方，无需新增权限 |
| 强下级获得双倍补偿（既拿自己层返佣又拿烧断补偿） | 烧断补偿仅铸积分（不直接发币），且积分有升级用途限制，不会形成现金流双倍 |

### 实施要点

- `AgentReward._payReward` 内新增烧断分支
- `AgentPoints.mint` 新增 `burnCompensation` refId 类型，标记来源
- 前端 `previewRebate` 需展示烧断后的实际返佣分布（透明化）

### 待团队确认

- [ ] 是否同意 B+D 组合方案？
- [ ] `maxBurnSkips` 步数建议值（10 步）是否合理？
- [ ] 烧断补偿铸积分是否需要设上限（如单笔不超过成交价的 X%）？

## P0-2：烧断是否保留 layer1 兜底

### 决策描述

烧断机制是否从 layer1 开始，还是保留 layer1（直推上级）兜底，从 layer2 开始烧断？

### 现状

现有 compression 从所有层开始触发（`rank == 0` 即跳过）。

### 建议方案：保留 layer1 兜底，从 layer2 开始烧断

**具体规则**：
- `burnStartLayer = 2`（即 layer1 永远不烧断）
- 直推上级无论 rank 高低，都拿 layer1 返佣
- layer2、layer3 才进入烧断检查

### 决策理由

- **保障基本推广动力**：直推关系是代理体系的核心动力源，若 layer1 也烧断，代理可能因"上级太弱"而完全拿不到返佣，丧失推广积极性
- **避免关系网络断裂**：直推上级是用户进入团队体系的"引路人"，保留其收益有助于维护关系网络稳定性
- **行业惯例**：传统直销/分销体系中，直推佣金通常是无条件保障的，layer2+ 才是级差激励层

### 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 弱上级仍可吃 layer1，激励效果打折 | layer1 返佣比例本身较低（如 15%），影响有限 |
| 强下级仍可能觉得"上级躺平吃我一层" | 通过双视角浮层透明展示，让强下级感知"我升级后能拿更多" |

### 实施要点

- `AgentLevel` 新增 `burnStartLayer` 配置（默认 2，miner 可调）
- 烧断检查逻辑：`if (burnEnabled && filled + 1 >= burnStartLayer)`

### 待团队确认

- [ ] 是否同意 layer1 兜底？
- [ ] `burnStartLayer` 默认值（2）是否合理？
- [ ] 是否需要支持 miner 按运营调整 `burnStartLayer`？

## P0-3：返佣时间期限具体值

### 决策描述

返佣时间期限机制中，确认收货后多长时间才下发佣金？

### 现状

现有返佣：购买成交同交易内 `onPurchase` 立即写额度，用户可立即 `claim()` 领取。

**核心坏账风险**：买家立即领取佣金后退货，平台无法强制追回（现有 `returnReward` 依赖买家主动配合）。

### 建议方案：确认收货后 7 天，按商品价格分级

**具体规则**：
- 默认冻结期：**7 天**（确认收货后 7 天内佣金处于 pending，不可领）
- 高价商品（单价 ≥ 500 USDT）冻结期：**14 天**
- 超高价商品（单价 ≥ 2000 USDT）冻结期：**30 天**
- 冻结期由商品级配置 `rebateDelayDays` 字段控制，miner 可按商品设置

### 决策理由

- **7 天参考行业惯例**：淘宝联盟 15 天、京东 16 天、拼多多 15 天；Node 作为 Web3 平台，7 天已能覆盖绝大多数退货场景，同时不过度压缩代理现金流
- **分级配置平衡风险**：高价商品退货损失更大，延长冻结期合理；低价商品 7 天足够
- **代理可预期**：佣金明细页明确展示"确认收货后 X 天可领"，代理可做现金流规划

### 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 代理现金流延迟，影响推广积极性 | 1) 佣金明细页展示 pending 佣金+预计可领时间；2) rank≥5 代理可申请"提前结算"作为等级权益（miner 审核后缩短冻结期） |
| 高价商品 30 天冻结，代理可能流失 | 30 天仅针对超高价（≥2000U），常规商品仍 7 天 |
| 平台需托管 pending 资金 | RewardClaim 合约本身已持币（`requireFunded` 约束），新增 `pendingAllocation` 字段即可，无需额外资金池 |

### 实施要点

- `GoodsMarket.Product` 新增 `rebateDelayDays` 字段
- `RewardClaim.addReward` 新增 `releaseTime` 参数
- 确认收货时计算 `releaseTime = block.timestamp + rebateDelayDays`

### 待团队确认

- [ ] 默认 7 天是否合理？是否需要调整为 10 天/14 天？
- [ ] 高价商品分级阈值（500U/2000U）是否合理？
- [ ] "提前结算"等级权益是否纳入首期？
- [ ] 冻结期内佣金是否计息？（建议：不计息）

## P0-4："确认收货"动作如何上链

### 决策描述

返佣时间期限的起点是"确认收货"，这个动作如何在链上触发？

### 现状

现有合约无"确认收货"概念，`fulfillmentStatus`（实物）和 `redeemStatus`（虚拟）是辅助态，不影响主状态。

### 建议方案：买家主动确认 + N 天自动确认兜底

**具体规则**：
1. **买家主动确认**：买家调 `GoodsMarket.confirmReceive(refId)`，触发佣金 `releaseTime` 开始计时
2. **自动确认兜底**：发货后 **15 天**未确认，系统自动确认（需链下 keeper 或 miner 手动触发 `autoConfirmReceive(refId)`）
3. 虚拟商品（卡密类）：发货即确认（无物流，`fulfillmentStatus` 直接置为 delivered，立即开始冻结计时）

### 决策理由

- **买家主动确认**：符合电商习惯，让买家有"验收"主动权
- **自动确认兜底**：避免买家不确认导致代理永远拿不到佣金，15 天参考主流电商自动确认周期
- **虚拟商品特殊处理**：虚拟商品无物流验收环节，发货即确认合理

### 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 买家恶意不确认 | 15 天自动确认兜底，代理最晚 T+15+7=22 天可领 |
| keeper 故障导致自动确认未触发 | miner 可手动 `autoConfirmReceive`；前端展示"待确认"状态提醒 |
| 虚拟商品发货即确认，买家无验收期 | 虚拟商品退货走 `returnRequest` 流程，确认后仍可退货（期限内） |

### 实施要点

- `GoodsMarket` 新增 `confirmReceive(refId)` 方法（买家调用）
- `GoodsMarket` 新增 `autoConfirmReceive(refId)` 方法（miner/keeper 调用，需校验发货时间+15 天）
- `confirmReceive` 触发 `AgentReward.startRebateTimer(refId, releaseTime)`
- 虚拟商品发货时自动调用 `confirmReceive`

### 待团队确认

- [ ] 自动确认兜底周期（15 天）是否合理？
- [ ] 虚拟商品"发货即确认"是否合理？是否需要给买家 24h 验收期？
- [ ] keeper 机制由谁实现？平台还是矿工？

## P0-5：二级市场交易是否触发团队返利

### 决策描述

二级市场（流转市场）的 5 个渠道成交时，是否触发代理返佣链路？

### 现状

- GiftChannel（赠送）：明确不触发（合约铁律）
- RentalChannel（租赁）：明确不触发（使用权分离，非所有权转移）
- FixedPriceMarket（一口价）/ AuctionHouse（拍卖）/ TimedExchange（限时动态价）：**未明确**

### 建议方案：分渠道差异化处理

| 渠道 | 是否触发返利 | 返利基准 | 理由 |
|---|---|---|---|
| GiftChannel（赠送） | ❌ 不触发 | - | 即时过户，非交易行为（现有铁律） |
| FixedPriceMarket（一口价） | ✅ 触发 | 成交价（net） | 标准交易，应纳入代理激励 |
| AuctionHouse（拍卖） | ✅ 触发 | 成交价（net） | 标准交易，应纳入代理激励 |
| RentalChannel（租赁） | ❌ 不触发 | - | 使用权分离，非所有权转移（现有设计） |
| TimedExchange（限时动态价） | ✅ 触发 | 成交价（net） | P3 落地时纳入 |

### 决策理由

- **一口价/拍卖触发返利**：二级市场是代理推广的重要场景（如短号流转、虚拟品倒卖），若不返利则代理无动力引导用户进入二级市场
- **租赁不触发**：租赁是使用权临时转移，非所有权变更，与一级购买语义不同（现有设计已明确）
- **赠送不触发**：赠送是非交易行为，且可能被刷（互赠套利），现有铁律保留

### 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 二级市场返利基数（成交价）可能远低于一级市场 | 返利比例可独立配置（`rebateBps` 按渠道差异化） |
| 短号流转触发返利，可能推高短号炒作 | 短号流转返利比例可设较低（如 5%），或短号类商品单独配置不返利 |
| 代理可能引导用户频繁倒卖套利 | 引入"持有期"约束：持有 < 7 天的二级市场交易返利减半 |

### 实施要点

- `FixedPriceMarket.buyListed` / `AuctionHouse.settle` 内调用 `AgentReward.onPurchase(buyer, skuId, 0, price, payToken, refId)`
- `AgentLevel` 新增 `channelRebateBps[channelId]` 配置，按渠道差异化返利比例
- 短号类 SKU 可标记 `rebateExempt=true` 豁免返利

### 待团队确认

- [ ] 是否同意分渠道差异化方案？
- [ ] 二级市场返利比例是否低于一级市场？（建议：是，如一级 15%，二级 5%）
- [ ] 短号流转是否豁免返利？
- [ ] "持有期"约束（持有<7天返利减半）是否纳入首期？

## P0-6：社区制 Faucet 是否保留基础 Faucet

### 决策描述

水龙头社区制（任务激励平台）升级后，是否保留现有基础 Faucet（每 24h 领 5 RC）？

### 现状

现有 Faucet：每地址每 24h 领 5 RC，资金池 50,000 RC，免 Gas 代发（EIP-2771），防刷三重（设备指纹+IP 频次+nonce 防重放）。

社区制是全新方向：可以发布需求，别人接受任务可以获得奖励。现有文档无任何设计。

### 建议方案：方案 A——保留基础 Faucet + 叠加社区制任务奖励

**具体规则**：
1. **基础 Faucet 保留**：每地址每 24h 领 5 RC 不变（新用户入门保障）
2. **社区制叠加**：任务奖励为额外渠道，不影响基础领取
3. **任务发布方**：首期仅平台 + 代理（rank≥3）可发布，普通用户仅接受任务
4. **首期任务类型**：地推类（邀请绑定）+ 体验类（首次 Swap/绑定短号/激活保险库）
5. **奖励来源**：平台任务走 Gas Tank；代理任务走代理预算（需锁定押金）

### 决策理由

- **保留基础 Faucet**：新用户无 Gas 则无法启动任何链上操作，基础领取是入门保障，取消会阻断新用户漏斗
- **叠加社区制**：任务激励提升活跃度，但不破坏现有入门流程
- **首期限定发布方**：避免普通用户滥发任务，降低审核成本
- **首期聚焦地推+体验**：地推直接对接团队邀请链路，体验任务引导用户完成核心操作（Swap/短号/保险库）

### 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 代理发布任务预算不足 | 代理需锁定押金（如 50 USDT），任务完成后从押金扣 |
| 任务核验链下行为易伪造 | 首期仅做链上可验证任务（地推绑定/首次 Swap），链下任务（内容创作）后续再上 |
| 任务奖励与团队积分重复计算 | 任务奖励仅发 RC（不发积分），避免与购买返佣的积分双算 |

### 实施要点

- 新增 `TaskFaucet` 合约（或扩展 Faucet 合约）
- 任务发布需 `deposit(uint256 amount)` 锁定押金
- 任务完成触发 `Faucet.drip(to, amount)`（复用 EIP-2771 免 Gas 机制）
- 代理任务完成同步触发 `referrerOf` 绑定（地推任务复用团队邀请链路）

### 待团队确认

- [ ] 是否同意方案 A（保留基础+叠加）？
- [ ] 任务发布方首期是否仅限平台+代理（rank≥3）？
- [ ] 首期任务类型是否聚焦地推+体验？
- [ ] 代理押金金额（50 USDT）是否合理？
- [ ] 任务奖励代币是 RC 还是 USDRs？（建议：RC，与基础 Faucet 一致）

## P0-7：Swap 白名单与团队等级的具体映射

### 决策描述

Swap 部分操作需要白名单，白名单如何与团队等级（rank）映射？

### 现状

现有 Swap：自建 AMM 流动性池，两代路由，滑点保护 4 档，所有 Swap 无白名单限制。

### 建议方案：双维度白名单（团队等级 + 持仓门槛）

| Swap 操作 | 白名单要求 | 理由 |
|---|---|---|
| RC ↔ USDRs（同链基础） | 无白名单 | 入门级，新用户必备 |
| USDT ↔ USDRs（跨链入金） | 无白名单 | 入金主通道，不应设卡 |
| HRCs 相关 Swap | rank≥3 | 生态联合 Token，需生态贡献门槛 |
| 大额 Swap（≥1000 USDT 等值） | rank≥5 OR 持仓≥5000 USDR | 防风控 + 反洗钱 |
| 超大额 Swap（≥10000 USDT 等值） | rank≥7 OR 持仓≥20000 USDR | 严风控 |

### 决策理由

- **基础 Swap 无门槛**：RC↔USDRs 和 USDT↔USDRs 是用户入门和入金主通道，设卡会阻断漏斗
- **HRCs 需 rank≥3**：HRCs 是生态联合 Token，rank≥3 需要团队积分，标志用户有生态贡献
- **大额 Swap 双维度**：rank OR 持仓，避免"低 rank 但高净值用户"被卡（如纯持仓用户未参与团队）

### 风险与缓解

| 风险 | 缓解措施 |
|---|---|

## P0-8：Node 是否计划国内应用商店上架

### 决策描述

Node 涉及加密货币交易（Swap/Faucet/代币），国内应用商店上架策略如何？

### 现状

- 国内：自 2023 年起所有 APP 必须完成 ICP 备案，Web3 钱包在国内使用受限
- 国际：Apple/Google 2025 年起 Web3 应用政策收紧，带交易/投资属性的功能只能在已持证的国家/地区开放
- 国内上架必备资质：软著 + ICP 备案 + ICP 许可证（"三剑客"）

### 建议方案：国内不上架，仅海外（Google Play 国际区 + App Store 国际区）

**具体规则**：
1. **国内不上架**：Node 涉及加密货币交易（Swap/Faucet/代币），不符合国内监管要求
2. **海外上架**：优先 Google Play 国际区 + App Store 国际区（美国/新加坡/香港等）
3. **国内用户访问**：通过官网下载 APK（Android）/ TestFlight（iOS）灰度
4. **区域灰度**：按 Apple/Google Web3 政策分区域开放功能
5. **合规准备**：申请新加坡 MAS 牌照或香港 SFC 牌照（视业务落地区域）

### 决策理由

- **国内监管风险**：我国政府对加密货币交易严格限制，Web3 钱包在国内使用受限，上架必被拒
- **海外市场机会**：Web3 钱包在海外（尤其东南亚/北美）接受度高，且 Apple/Google 已开放 Web3 应用上架政策
- **国内用户灰度**：通过官网 APK + TestFlight 满足国内核心用户，不依赖应用商店
- **牌照合规**：海外上架涉及加密货币功能需金融牌照，新加坡 MAS/HK SFC 是较友好的选择

### 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 国内用户获取成本高（无应用商店流量） | 1) 官网 SEO + 社群运营；2) TestFlight 灰度；3) 团队代理地推 |
| 海外上架 Apple Web3 政策收紧 | 1) 定位为"自管钱包工具"（非交易平台）；2) 代币功能按地区灰度（如美国区禁用 Swap）；3) 主体注册在友好辖区 |
| 牌照申请周期长 | 1) 首期以"工具类"上架，规避金融属性；2) 牌照同步申请，后续开放完整功能 |
| 国内 APK 分发安全风险 | 官网提供 SHA256 校验，签名验证 |

### 实施要点

- 主体注册：新加坡或香港设立运营主体
- 牌照申请：新加坡 MAS（DPT 牌照）/ 香港 SFC（Type 1）
- 上架策略：Apple 按"Wallet"类目提交，避免"Exchange"类目（审核更严）
- 区域灰度：按 IP/地区禁用 Swap/Faucet 功能（如中国大陆 IP 仅钱包基础功能）
- 国内分发：官网 APK + TestFlight + 团队代理地推

## P1-1：积分转移后接收方是否能用转入积分升级

### 决策描述

团队积分按百分比转移后，接收方是否能用转入的积分申请等级升级？

### 现状

`AgentPoints` 是 Soulbound ERC20（不可转让），用户要"积分转移"直接违反现有设计原则。

建议方案 A（新增 PointsTransfer 合约）：`burn(from) + mint(to, newRefId)`，转入积分标记为 transferred。

### 建议方案：转入积分不可用于升级达标

**具体规则**：
- 转入的积分标记为 `transferred`（新增 mapping）
- `AgentLevel.approveUpgrade` 时校验：转入积分不计入达标 metric
- 转入积分仅用于团队积分展示/分润，不参与等级升级

### 决策理由

- **防刷等级**：若转入积分可升级，大号转积分给小号 → 小号升级 → 出现两个高等级账号（刷等级）
- **保留升级公平性**：等级应靠自身贡献达标，不可购买/转让
- **转入积分仍有价值**：用于团队积分展示、分润权益，不影响升级但保留其他用途

## P1-2：白名单/代理资格是否支持购买特定商品后自动解锁

### 决策描述

### 现状

- 白名单由 miner `setWhitelist(Batch)` 手动配置
- 代理资格由 miner `minerSetLevel` 手动设定
- 级别服务商品购买后，miner 审核升级

### 建议方案：支持自动化，但需风控审核

**具体规则**：
1. 商品配置新增 `autoWhitelist`（bool）和 `autoRank`（uint8）字段
2. 购买 `autoWhitelist=true` 的商品 → 自动加入对应白名单
3. 购买 `autoRank>0` 的商品 → 自动升级到指定 rank（需额外风控）
4. 风控：购买后 7 天内退货 → 自动撤销白名单/降级
5. 大额代理资格商品（如 1000U 以上）仍需 miner 人工审核

### 决策理由

- **提升用户体验**：购买代理包后立即获得代理能力，无需等待 miner 审核
- **降低运营成本**：减少 miner 手动操作
- **风控保障**：退货撤销机制 + 大额人工审核兜底

## P1-5：钥匙权重模型

**具体规则**：

- 解锁条件：累计权重≥服务舱要求（虚拟权益舱=1 / 代币托管舱=3 / 冷数据存储=3 / DID 备份=3 / 实物交割=6 / 智能信托=6）

- **灵活性**：权重累计支持多种钥匙组合，不局限于固定组合
- **可扩展**：未来新增钥匙类型（如 L4）只需定义权重，无需重构权限模型
- **安全性与便利性平衡**：高安全舱可用 L3 单把快速解锁，低安全舱可用 L1+L2 组合解锁
